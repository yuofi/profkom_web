# Поставка на тест и откат

Документ описывает порядок подготовки, а не разрешение на запуск. Внешние
Git-операции, SSH, тестовый сервер, production и реальные VK/S3 требуют явного
разрешения владельца на конкретную среду и действие. См. [AGENTS.md](AGENTS.md).

Старый пошаговый cutover базы `6eb9dea`, ресурсы сервера и наблюдения 24–25 октября
сохранены в [архиве](docs/archive/operations/DEPLOY_20261025.md). Его свободное место,
образы, сеть и конфигурация не считаются текущими без проверки. Миграционная
процедура не является обычным обновлением тестового сайта.

## 1. Зафиксировать кандидат локально

1. Проверить рабочее дерево и ветку. Пользовательские файлы не включать по принципу
   «добавить всё»; согласовать состав изменения. `release-1` — линия последней
   завершённой тестовой поставки, а не автоматический выбор для любого нового релиза.
2. Выполнить проверки, соответствующие изменению, по [TESTING](backend/TESTING.md).
   Использовать синтетические данные; реальный API тестового сайта не является
   одноразовой интеграционной базой.
3. Сохранить точный commit SHA, результаты проверок и хэши исходников. Подготовить
   production-сборку frontend **из этого SHA**, для нужного origin, с отключённым демо.
   DEV-сервер с выбором ролей не выкладывается.
4. Зафиксировать состав и хэши артефактов, настройки сборки без секретов,
   требуемые миграции и проверяемое состояние до/после. Отдельно подготовить откат.

Секреты не помещаются в коммит, образ или отчёт. Backend получает настройки во время
запуска, frontend — разрешённые публичные build-time значения. Закрытые пароли,
cookies, JWT, `.env`, подписанные ссылки и персональные данные не выводятся.

## 2. Подготовить разрешённое окружение

- Проверить актуальную ревизию, dirty state, контейнеры, конфигурацию, свободное
  место и mounts. Предыдущие снимки не заменяют этот preflight.
- Различать проекты: тест `profkom-test` и рабочий сайт `profkom_web`.
  Проверять конкретные имена/пути перед изменением. Рабочий сайт не перезапускается
  как побочный эффект тестовой поставки.
- Не выполнять `docker compose down`: сеть обслуживает также существующие
  серверные зависимости. Точечная остановка/замена — только целевого сервиса.
- Не удалять образы, cache, базы и бэкапы ради сборки без согласованного объёма
  очистки. Если место не позволяет безопасную поставку, завершить подготовку локально.
- Перед остановкой построить необходимый backend-образ; frontend `dist` готовить
  локально. Конфигурация теста и Basic Auth сохраняются.

## 3. Сохранность и переключение

1. Подготовить серверную копию конфигурации, прежнего образа и frontend-артефактов.
2. Остановить только нужный backend, корректно checkpoint SQLite и создать
   согласованную резервную копию **на сервере**. Не переносить реальные базы локально.
3. До изменения сохранить проверяемые отпечатки таблиц и схемы: ID, старые значения,
   индексы/триггеры, учёт, утверждённые снимки, аккаунты и версии сессий.
4. Установить проверенные артефакты и запустить целевой backend. Проверить реальные
   startup-миграции. Новое поле не даёт основания менять прежние строки или даты.
5. Сверить сохранность со снимком, доступность статики и контракты. Не сбрасывать
   аккаунты/сессии/ККР, не подставлять выдуманные связи файлов.

При любой неполной проверке поставку не объявлять успешной. Откат восстанавливает
согласованную пару **старая БД + старый код**, frontend и изменённую конфигурацию;
сначала проверить восстановление, затем запускать прежний backend. Новый код со
старой БД и старый код с частично новой схемой не считаются проверенным откатом.

## 4. Проверить результат и записать факт поставки

- Readiness/OpenAPI, отсутствие новых startup tracebacks/5xx.
- HTTP под согласованными ролями, разрешения и отказы. При проверке реальной базы
  не создавать произвольные данные и не запускать разрушающую integration suite.
- Точная ревизия/статика, запрет демо, Basic Auth и неизменность защищённой конфигурации.
- Сохранность старых строк, вложений, учёта и аккаунтов; согласованная миграция дважды
  репетируется локально до поставки.
- Неизменность production-контейнеров, если поставка разрешена только на тест.

Записать фактические SHA до/после, время, объём проверок, место серверного бэкапа,
результат и ограничения. Не выдавать HTTP-проверку метаданных вложения за проверку
байтов S3, а тестовую выкладку — за production-релиз. Скриншоты тестовой базы
с реальными данными не делаются.

## Где искать доказательства

Локальные результаты лежат в игнорируемой `.local/logs/`; [указатель](docs/archive/README.md)
перечисляет последние поставки. Это не часть свежего клона. Исторические скрипты
привязаны к конкретному SHA/состоянию сервера; их нужно прочитать и адаптировать,
а не запускать вслепую. Последняя проверенная в этом чате поставка `12dede0`
описана в `.local/logs/attachment-layout-deploy-20261030/`; сервер в рамках
ревизии документации 31 октября повторно не опрашивался.

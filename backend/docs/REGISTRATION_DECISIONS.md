# Решение по регистрации

`GET /api/registrations/me`, список `/api/registrations` и команды рассмотрения
возвращают `RegistrationApplication.decision`:

```json
{
  "outcome": "approved",
  "actor": { "user_id": 17, "display_name": "Проверяющий", "avatar_url": null },
  "at": "2026-11-10T08:12:00+00:00"
}
```

Это проекция сохранённого `approve` / `reject` в `RegistrationORM.history_json`.
Схема БД не меняется, чтение не создаёт записи и не восстанавливает неизвестную
историю из нынешних должностей. Для `pending` поле равно `null`. Сброс лимита
не меняет последнее решение; повторная отправка скрывает его до нового решения.
У старой одобренной/отклонённой заявки без достоверной истории `actor` и `at`
равны `null`. Невалидная дата и дата без часового пояса также считаются неизвестными.

Имя автора проходит общую политику `UserReference`: сервисный аккаунт не раскрывает
свой ID, обезличенный участник остаётся обезличенным, отсутствующий автор возвращается
как `null`. Имена для списка читаются одной выборкой с контактами; запросов к S3 и
загрузки фотографий ради метаданных решения нет. Полная история и причины других
решений в этот DTO не попадают. Доступ к заявкам не расширяется.

Карточка решения видна ревьюеру сразу, без раскрытия персональных полей заявки,
и заявителю на экране отклонённой регистрации. Время отображается по Москве с
явным `МСК`; HTML `time` сохраняет исходный ISO timestamp. Автор — обычный текст,
чтобы заявителю не предлагалась недоступная ссылка на профиль сотрудника.
Неизвестные сведения подписаны явно. Тексты уведомлений и сообщений бота не меняются.

frontend `registration-decision.test.tsx`, `account-layout.test.tsx` и проверка
строгого wire-контракта в `wireContract.test.ts`.

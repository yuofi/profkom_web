# Backend: анализ продолжения работ, 2026-10-18

## Вывод

Бэкенд уже содержит реализацию значительной части BE-01–BE-04, но пока не соответствует API 1.3 и не готов для подключения реальных пользователей. BE-05 и BE-06 требуют почти полной реализации. Для продолжения нужны одновременно: закрытие обнаруженных обходов доступа, выравнивание контракта с фронтом, завершение доменной логики и безопасные миграции.

Это анализ, не отчёт об исправлениях. Прикладной код и исходное задание не менялись. Пуш и деплой не выполнялись.

## BE-05: отсутствующая функциональность

1. Регистрационная заявка: обязательные поля RegistrationFields; GET/PATCH `/registrations/me`, resubmit; очередь registrations; approve/reject/reset-attempts. Пять отправок, повтор того же аккаунта, причины и неизменяемая история. Retry/конфликт не расходуют новую попытку.
2. Членства и заявки блока: нормализованные membership/request, состояния pending_hr/pending_block/approved/rejected/withdrawn, серверное stage_entered_at, substitute_available_at. В обычный блок два одобрения, в HR одно; один человек может выполнить оба разрешённых этапа.
3. Подмена тачками после 72 часов: точная граница, новый срок только при переходе этапа, смена мастера срок не сбрасывает; audit отмечает подмену.
4. Выход `/blocks/{id}/leave` и удаление `/blocks/{id}/members/{user_id}`: обычное членство заканчивается, служебные назначения отдельно, прошлые работы сохраняются, недоступная незавершённая работа остаётся в очереди. Уведомление мастеру без дублей.
5. История участия/архива/членств и две независимые категории: global junior/activist и block junior/member; отдельная PATCH participants/category с reason/revision и ACL тачки/HR master.
6. Новая карточка Block, устойчивый ID, текст/сообщество/гайд, существующие составы и назначения. Не создавать новые блоки по старой доске. Рабочий трекер ограничен областью, информация/гайд видны всем одобренным.

Критерий BE-05: AUTH-02/REGISTRATION, BLOCK-01–05, JUNIOR-01–05 из исходного acceptance проходят через HTTP, а все старые прямые записи дают отказ или безопасно направлены в новый процесс.

## BE-06: отсутствующая функциональность

1. Material с опубликованной версией и отдельным черновиком: GET/POST/PATCH/DELETE, publish, несколько назначенных editors. Только тачки назначают редакторов; права редактора не дают доступ к аккаунтам и ККР.
2. Безопасная совместимость guides/КМБ/PGAS: неизменные старые ID и ссылки, сохранение Markdown/HTML-разметки через проверенный адаптер; явная связь guide_id→material_id. У каждого существующего блока гайд или заглушка. Прямая legacy-запись не должна обходить новую публикацию.
3. Контакты: поиск/фильтры для одобренных, GET contacts/emails; текущие пишет только владелец. Отдельные бывшие без аккаунта, POST/PATCH contacts/archive для HR/тачек, периоды участия.
4. Аватары: ≥6 presets и default, GET avatars, PUT profile/me/avatar с ровно одним preset_id или собственным file_id. Прекратить получение фото VK, мигрировать старые VK-фото без скачивания, собственные фото сохранить.
5. Архив аккаунта: accounts/archive, archive/restore только председателю, reason/audit, отзыв сессий; запрет архива действующего председателя; восстановление с разрешением master_conflicts. Отозванные глобальные роли после передачи поста не восстанавливаются.
6. Идемпотентная очистка через три года: расписание/команда, граница срока, сохранение согласованных контактов и обезличенной истории/начислений. Нынешний DELETE профиля физически удаляет user/contact — нужен адаптер к архивированию.

Критерий BE-06: GUIDE-01–04, CONTACT-01, AVATAR-01, ARCHIVE-01–04 и сохранённые сценарии PGAS проверены без реальных персональных данных.

## Миграции и эксплуатационные зависимости

Проба: старая схема из `87c886c`, 2 пользователя/контакта, HR-блок, guide и PGAS. Первый и повторные импорты текущей схемы сохранили количество записей, текст гайда и PGAS; integrity_check=ok, повторный импорт стабилен. Это полезная основа, но не приёмка миграций API 1.3: оба пользователя стали active/junior независимо от старого одобрения, master_user_id остался null, явных role_assignments нет.

Нужны:

- Версионированные идемпотентные шаги миграции и отчёт: ID/количество/хеши сохранённого контента; неоднозначные имена не превращаются в права.
- Явное сопоставление privileged users по ID, HR по устойчивому block_id; решение по состоянию/категории старых аккаунтов без выдуманного стажа и массового понижения активистов.
- Проверка всех существующих блоков, составов, руководства, текстов, PGAS и старых ссылок на файлы. Рабочая БД сначала копируется по отдельному эксплуатационному сценарию; автотесты её не используют.
- Снимки/интервалы/связи, необходимые для ККР и архива; поддержка обезличенного UserRef.user_id=null без потери учёта.
- Ограничения/индексы БД и транзакционные проверки: единственный current/planned, единственный master, уникальные назначения/членства/начисления/final, optimistic concurrency и атомарный refresh.
- Настройка DATABASE_PATH/JWT/VK/S3 через проверяемую конфигурацию без секретов в примерах; отсутствие безопасного JWT-конфига в production должно останавливать запуск, а не использовать стандартный секрет.
- Реальные private bucket, CORS PUT и временные чтения; старый public_url не обеспечивает закрытый доступ. Миграция метаданных сама по себе не делает публичный объект приватным.
- Актуальные README/TESTING/OpenAPI/разрешённые примеры ответов. Старые тесты местами фиксируют несовместимое поведение; менять ожидания по заданию, сохраняя регрессии полезных сценариев.

Импорт прежнего ККР/Google-таблиц и импорт контактов отложены заданием. Новые блоки и деплой не входят в эту работу.

## Что нужно именно для ближайшего продолжения фронта

Первые результаты должны появиться до завершения всего backend:

1. Исправленные active/pending session, capabilities и совместимые list/DTO дают возможность начать настоящее подключение существующих экранов.
2. После файлового контура проверяются сдачи и отчёты с бинарниками.
3. После BE-05 становятся рабочими регистрация, вступление, очередь заявок и карточки блоков.
4. После целостности ККР/истории отчётов принимается основной рабочий цикл.
5. После BE-06 подключаются материалы, архив и аватары.

Каждая группа сначала проходит локальные API-тесты и интеграцию с фронтом при `VITE_DEMO_MODE=false` на отдельной временной БД; затем телефон/десктоп и повторный GET после перезапуска. Нужны как минимум председатель, зам, HR master, HR deputy без глобальных прав, локальный мастер/зам, главорг/ответственный/организатор, посторонний, pending/rejected/archived.

## Решения по контракту и внешние блокеры

Новых продуктовых решений для начала реализации не требуется: основное поведение определено API 1.3. Два технических дополнения следует явно записать для обеих сторон:

- Путь/DTO чтения прежних summary versions и аудита коррекций: например список метаданных и GET версии по ID; только разрешённым глобальным ролям. Требование доступности прошлых версий уже есть, отдельный read API в карте не расписан.
- Явная связь guide_id→material_id и поведение legacy-save в новой модели публикации. Нельзя сопоставлять материалы по названию или предполагаемому равенству ID.

Для unit/API-реализации нет зависимости от реального VK/S3: используются содержательные моки. Для окончательной внешней интеграции потребуются тестовые VK-настройки и private S3 bucket/CORS, а для production-миграции — доступ к копии БД и явное сопоставление privileged IDs. Это эксплуатационные зависимости поздней приёмки, они не блокируют начало разработки.

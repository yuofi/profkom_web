# История изменений и скрытие текста версии

`history.py` даёт единый интерфейс истории объекта, а не доступ к сырому
`audit_log`. Поддерживаются `task`, `assignment`, `merit`, `season`, `block`,
`event`, `subevent`, `leadership`. Для руководства используется id `current`.

## Контракт чтения

- `GET /api/history?target_kind=task&target_id=…&cursor=…` возвращает страницу
  записей в обратном хронологическом порядке. Запись содержит автора, дату,
  разрешённые пары `before` / `after`, основание, признак скрытия и право скрыть.
- Текущий доступ к объекту проверяется заново при каждом чтении и скрытии.
  Неудачная проверка не оставляет на экране данные из предыдущего кеша.
- Публичная история задачи строится из `task_activity`. История исходных полей
  задачи, назначений, часов, оценок, личного результата ККР и замечаний появляется
  только у читателя с прежними правами просмотра ККР. Наличие доступа к задаче
  само по себе их не даёт. Публичный рабочий статус не является статусом ККР.
- Для параметров сезона, блока, мероприятия, подмероприятия и руководства
  применяется отдельный белый список полей. Контактные данные, пароли,
  вычисленные оценки и произвольные содержимое audit JSON не возвращаются.
  Пользователи разрешаются по текущей базе, имена и аватары не копируются
  в исторические снимки.

## Кто может скрыть версию

`POST /api/history/{activity|audit}/{source_id}/hide` принимает
`{"expected_revision": 1}`. Повторное скрытие возвращает конфликт версии.
Сначала проверяется текущий доступ, затем одно из оснований:

1. Автор скрывает собственную версию, в том числе после закрытия сезона.
2. Сохранённые интервалы показывают, что на дату изменения пользователь был
   руководителем автора в соответствующей области. Новое назначение не даёт
   власти над предыдущими версиями; неизвестные даты не считаются доказательством.

Для председателя и заместителя председателя нужен подтверждённый глобальный
интервал роли на дату изменения.
Прежний руководитель сохраняет такое историческое основание при текущем доступе
к объекту. Нынешняя должность не выдаёт полномочий задним числом.

Для блока историческая принадлежность роли берётся только из стабильного
`ScopeTenureORM.scope_block_id`, а не из совпадения старого названия. У
унаследованных интервалов с `NULL` нет достаточного доказательства. Новые записи
изменения руководства сразу получают стабильный id блока; переименование и
повторное использование прежнего имени не смешивают историю двух блоков.

## Что означает скрытие

Текст исходной записи и относящийся к нему `before` следующей версии удаляются
из хранилища истории. Для комментариев связь ограничена конкретным
`comment_id`; при неоднозначной старой связи код ничего не угадывает. Сохраняется
маркер `history_redactions`: первоначальный автор, скрывший пользователь и дата.
Интерфейс показывает «Версия скрыта».

Скрытие не откатывает текущую задачу или комментарий, назначения, учтённые часы,
оценки и утверждённые снимки сезона. Числовые значения исходного аудита тоже не
переписываются. Старый совместимый `/api/tasks/{id}/history` не возвращает
удалённый текст: очистка применяется к общему источнику, а не только к новой DTO.

## Источники и интеграция

Публичные события пишет трекер. Ограниченный ORM hook дополняет отсутствующую
историю параметров сезона/блока/мероприятия, фактических назначений руководства,
первых исходных полей назначения и записи выполненной работы. Hook работает
только при установленном реальном actor; миграция не приписывается человеку.
Владеющие сервисы могут передать `session.info["history_reason"]`.

`history_models` необходимо импортировать до `create_all` и учитывать
`history_redactions` при очистке тестовой базы. `history.anonymize(session,
user_id, old_participant_id, new_participant_id)` обнуляет только ссылки на
пользователя в маркерах; числовые снимки и история ККР остаются неизменными.

`HistoryPanel` используется в трекере, оценивании, выполненной работе, сезоне и
управлении руководством. `HistoryDisclosure` загружает данные только после
раскрытия. Текстовый diff экранируется как обычный текст и не исполняет Markdown
или HTML. Скрытие требует отдельного подтверждения непосредственно в записи.

## Проверки

`tests/test_unified_history.py` проверяет публичную/приватную границу, актуальный
доступ, подтверждённую историческую подчинённость, неизвестные интервалы,
переименование/повтор имён блоков, точную связь комментариев, отсутствие
побочных записей при чтении, cursor и неизменность числовых снимков при скрытии.
Frontend `history-panel.test.tsx` проверяет diff, явное подтверждение и запрет
показа кеша после отзыва доступа. Реальный HTTP/DOM сценарий находится в
`profile-features.integration.test.tsx` и работает только на синтетической базе.

# VK-чат блока/мероприятия и объявление о новой задаче

Локальная реализация `chat_announcements_v1`. Не включает доставку в каналы VK,
опросы, ЛС всем участникам или наследование чата подмероприятиями. Объекты сайта
хранят стабильный `block_id`/`event_id`; название беседы принадлежит базе HereBot,
сайт хранит только его ограниченную проекцию.

## Права и привязка

`scope.chat.manage` / `task.chat_announce`: председатель, заместители председателя,
основной мастер конкретного блока и основные ответственные конкретного мероприятия.
Заместитель мастера, куратор HR и владелец очереди сами по себе права не получают.
Сервисный аккаунт может читать, отвязать и поставить объявление в очередь, но не
может представиться пользователем VK и получить код привязки.

- `GET /api/scopes/{kind}/{scope_id}/chat` — привязка, монотонная ревизия и capabilities.
- `POST …/chat/link-code` с `expected_revision` — одноразовый `/site_bind CODE` на 10 минут.
- HereBot проверяет актуальный состав и администратора, затем вызывает служебный
  `POST /api/bot/v1/chats/confirm`. Сайт повторно проверяет исходного автора,
  подтверждённую VK-связь, права и CAS. Проверка беседы не старше 120 секунд.
- `DELETE …/chat` с `expected_revision` оставляет tombstone, повышает ревизию и
  отменяет неотправленные объявления прежней привязки. Код не может восстановить её.

Код — 128 случайных бит, в SQLite только SHA256. Новый код инвалидирует прежний
код автора для того же объекта. Лимиты долговечны: 5 выдач за 10 минут на аккаунт;
5 подтверждений за 10 минут на VK, 200 всего. Отказ подтверждения сохраняет только
счётчик попыток. Запись аудита содержит ID/ревизии, не код и не служебный токен.

## Создание и чтение

`GET /api/tasks/chat-context?queue_id=…&assignee_user_ids=1,2` возвращает доступность,
название и ревизию чата, режим `all`/`assignees`, недостающие подтверждённые VK.
Для формы без очереди допустимы `scope_kind`/`scope_id`. Это локальный GET: без VK,
создания очереди или изменения срока lease. Закрытые/private, WEBSUPPORT и KKR
очереди запрещены для общей беседы. Кандидаты проверяются на доступ к scope.

`POST /api/tasks` принимает `chat_announcement:{enabled:true,binding_revision}`.
Задача и `task_chat_announcements` создаются в общей транзакции. Обычный GL-07
idempotency key включает включённое намерение, но сохраняет прежний digest для
отсутствующего/выключенного флага. Повтор не создаёт второе объявление. Неверная
ревизия/права/получатели откатывают задачу вместе с outbox.

Чтение списка задач не обращается к таблицам чатов. Детальная задача содержит
nullable `chat_announcement` со статусом, ревизией, безопасным кодом ошибки,
автором/датой и capability повтора. Нет составов бесед в ответе сайта.

При временном offline бота с уже заявленной возможностью объявление можно
поставить в очередь. Отключённая интеграция/старый бот дают `bot_unavailable`.
Выбранные исполнители без VK **никогда** не превращаются в рассылку всем.

## Протокол доставки

Существующий BOT_API v1 остаётся совместимым. `heartbeat.features` и query
`GET /work?features=chat_announcements_v1` согласуют новый массив
`chat_announcements`; старый бот его не получает. Старый idle work/report не
делает дополнительных SQL. Site API вообще не выполняет сетевых запросов VK.

1. Work descriptor: job/task/binding/revision, community/peer, mode, VK IDs,
   initiator VK (null для сервиса), безопасный текст <=2000, task URL, SHA256,
   expiry24ч, `retry_generation`. Нет описания задачи/файлов/данных ККР.
2. `POST /chat-announcements/{job_id}/claim` принимает UUID worker и payload hash.
   Lease90с, случайный токен и возрастающий fence. Повтор того же worker возвращает
   тот же активный lease; конкурент получает409.
3. Перед **каждой** частью `POST …/authorize`: lease/fence, номер0..199,
   parts_total1..200, постоянный положительный random_id<=2^31-1 и hash части.
   Проверяются права автора, неизменность VK и состава выбранных исполнителей,
   публичность/состояние задачи/сезона и актуальность привязки. Манифест неизменяем.
   Ответ `already_sent` предотвращает повтор уже принятой сервером части.
4. `/report.chat_results` записывает sent/message_id либо retryable/failed с
   ограниченным кодом ошибки. Устаревший fence даёт409 `chat_lease_stale` для всего
   отчёта: **это не ACK**. Бот получает новый lease и подтверждает прежнюю сохранённую
   sent-часть, не повторяя VK send. Повторы результата идемпотентны.
5. `GET /chats` — keyset-пагинация привязок для фонового обновления проекций.
   `/report.chat_observations` принимает только совпавшие binding/revision/bot/peer
   с более новой датой наблюдения; переименование чата не меняет revision привязки.

Автоматические паузы: 60/300/900/3600с, затем failed/partial. Ручной
`POST /api/tasks/{id}/chat-announcement/retry` с CAS сохраняет job, части и random IDs;
увеличивает `retry_generation`, чтобы бот открыл свою завершённую запись.
TTL24ч не продлевается повтором. Если бот не присылает отчёты, чтение задачи
проецирует просроченное ожидание в cancelled (partial при уже отправленной части),
с ошибкой expired и без права повтора. GET не пишет в БД; последующая hourly
очистка сохраняет тот же конечный статус одним UPDATE с проверкой sent-частей.
Перед отправкой всё равно обязательны свежая
проверка VK, authorize и ограничения отправителя HereBot.

Heartbeat нового бота выполняет ограниченный sweep25 ожидающих объявлений
по долговечному checked_at (не чаще30с для одной записи, с ротацией):
потерявшие права/получателя/привязку/актуальность заканчиваются cancelled/partial,
а не остаются с бесконечным индикатором ожидания. GET этого не делает. Work читает не больше50 кандидатов для выдачи10 валидных,
чтобы несколько невалидных записей в начале не блокировали готовую работу.

Отвязка после authorize, когда сетевой запрос уже ушёл, не может отменить VK send.
Его sent-результат учитывается как факт; новые части не разрешаются. Неопределённый
результат send повторяется ботом только с прежним сохранённым random_id.

## Хранение и миграция

Пять добавочных таблиц `scope_chat_bindings`, `scope_chat_codes`,
`scope_chat_attempts`, `task_chat_announcements`, `task_chat_parts` создаются обычным
startup `Base.metadata.create_all`. Существующие строки не преобразуются. Индексы
защищают уникальную привязку scope, один outbox на задачу и random ID на сообщество.
Обычный SQLite write UOW сериализует CAS и захват lease. WAL для этого не требуется.

Retention аккаунта имеет отдельный callback до удаления bot_links: убирает коды,
попытки и типизированные VK/аккаунт-ID из снимков, отменяет неотправленное,
не переотправляет доставленные сообщения. Стандартный hourly report удаляет
просроченные одноразовые коды/попытки; сообщения/parts остаются историей доставки.

Проверки: `tests/test_task_chat.py`; HTTP и HereBot acceptance дополнительно в
`tests/test_task_chat_end_to_end.py`. Только синтетические пользователи/SQLite,
подменённый VK, без реальных сообщений.

# HTML-вставки в гайдах

Первый выпуск использует ограниченный HTML внутри fenced-блоков
`profkom-html id=embed-...` и формат материала `markdown-embeds-v1`.
Обычный `markdown`, включая случайные блоки `profkom-html`, сохраняет прежнее
поведение. Формат включается явным сохранением редактора, только в гайдах блоков.
Права редакторов, аудитория, отдельный черновик и публикация сохраняются.

`GUIDE_HTML_EMBEDS_ENABLED=false` по умолчанию запрещает создание/сохранение
расширенного формата и его публикацию. Чтение ранее опубликованной версии
остаётся доступным. При включении редактор получает capability
`edit_html_material`; флаг не предоставляет права сам по себе.

## API и хранение

`MaterialContent` отделён от общего `RichText` задач и комментариев:

- `format`: `markdown`, `markdown-embeds-v1` либо `journal-v1`;
- `body`: исходный текст;
- `render`: проверенное дерево, только для расширенного формата, либо `null`,
  если артефакт отсутствует, устарел или имеет неизвестную версию политики.

Редакторский `source_content` содержит только формат и исходник. Каталог
расширенных материалов не отправляет исходник и деревья: `body` пустой,
полный материал запрашивается по ID. Старые Markdown DTO не меняются.

`POST /materials/{material_id}/preview` принимает `expected_revision` и
`content`, возвращает `MaterialContent` без сохранения и изменения ревизии.
Доступен только текущему редактору. `PATCH` сохраняет исходник даже с
диагностикой синтаксиса; публикация такого черновика запрещена. Компиляция
не сообщает содержимое чужих файлов и не делает обращения к хранилищу.

Аддитивная startup-миграция добавляет `draft_format` и `published_format`
с default `markdown`. Два артефакта на материал хранятся в
`material_render_artifacts` по ключу `(material_id, slot)`: draft/published,
SHA-256 формата и исходника, JSON дерева версии схемы/политики 1 для HTML
или 2/1 для журнала. Журнал использует те же столбцы и таблицу артефактов,
не требует новой миграции и не меняет формат ранее опубликованных материалов.
Публикация атомарно переносит источник и артефакт, а существующий legacy
GuideORM по-прежнему получает исходник. Изменение аудитории/редакторов не
ломает артефакт: соответствие проверяется по хешу, а не общей ревизии.
Retention удаляет артефакты вместе с окончательно удаляемым материалом.

## Раздел каталога

`catalog_section` — отдельное необязательное поле материала (`general` либо
`guide`); без него каталог использует `kind`. Оно не меняет тип, владельца,
аудиторию, редакторов, источник и артефакт. Поэтому Journal-гайд может находиться
в «Общих документах», продолжая проверять прежние права и файлы.

Председатель, заместители и сервисный аккаунт меняют его через
`PATCH /materials/{id}` с `expected_revision` и `catalog_section`.
`null` возвращает раздел по типу. Команда отделена от редактирования текста:
другие поля в том же запросе запрещены. Она меняет только раздел и ревизию,
не создаёт черновик, не публикует его и не компилирует источник. Повтор того же
значения с текущей ревизией ничего не записывает. Startup добавляет nullable
`materials.catalog_section`; прежние строки сохраняются с `NULL`.

## Обработка, файлы и безопасность

`guide_embeds.py` разбирает Markdown через markdown-it-py и HTML5-фрагмент
через html5lib, затем строит новое ограниченное дерево. Нет переноса
произвольных атрибутов, CSS, JavaScript, iframe или внешних изображений.
Renderer использует фиксированные React-компоненты, а не исполняемый HTML.

Компиляция запускается в ограниченном дочернем процессе до захвата SQLite
writer lock. После неё запись заново проверяет сессию, права и ревизию в
транзакции. Переполнение очереди отвечает 429; превышение времени — понятной
ошибкой 422, процесс прекращается. Синхронные маршруты работают в threadpool.
GET не компилирует, не исправляет БД и не проверяет S3.

Для повторного чтения действует кэш неизменяемых проверенных моделей и готового
JSON содержания: максимум 8 артефактов и 2 MiB суммарных сериализованных ключей
и значений. Это бюджет сериализованных данных, не размер Python heap. Ключ
сравнивает формат, точный JSON артефакта и версии политики/схемы; при прогретом чтении
не требуется повторно кодировать и хешировать всё дерево. Хеш текущего исходника
проверяется на каждом чтении. Содержание включает только исходник и его дерево;
права, пользователь, сессия, метаданные и подписанные URL не кэшируются.
Писатель получает отдельную изменяемую копию. GET заново проверяет права и
валидирует динамический DTO, затем добавляет проверенные JSON-байты содержания
без повторного обхода сотен узлов. Текст автора всегда кодируется JSON-сериализатором;
подстановка сырого HTML/JSON не используется. При вытеснении или превышении
бюджета обычная сериализация сохраняет тот же контракт ответа.

Картинки адресуются только `file:<file_id>` своего материала. Сохранение
валидной вставки и публикация проверяют завершённость, принадлежность,
действующие права и MIME PNG/JPEG/WebP. Доступ читателя к вложению определяется
ссылками проверенного опубликованного дерева; примеры кода в расширенном
формате не предоставляют доступа. Для обычного Markdown сохранена прежняя
политика ссылок `file:<id>` в исходнике, без нового парсинга на чтении. Удаление
картинки из публикации прекращает доступ читателя; авторские вложения
сохраняются до существующего retention материала.

## Проверки и эксплуатация

`test_guide_embeds_materials.py` проверяет разграничение черновика/публикации,
preview без записи, повторную проверку сессии/прав/ревизии после компиляции,
непубликуемые исходники с ошибкой, независимость чтения от флага, отсутствие
компиляции на GET, приватные байты изображений и отзыв доступа, чужие и
незавершённые файлы, неподходящий MIME, старую схему дважды и integrity/FK.
Дополнительно проверяются точное совпадение оптимизированного JSON с DTO,
экранирование исходника, холодный/прогретый и не помещающийся в кэш артефакт,
отсутствие повторной сериализации дерева и свежие метаданные/права.
Корпус компилятора находится в `test_guide_embeds_compiler.py`.

## Журнальная вёрстка (`journal-v1`)

`body` — JSON-документ версии 1. Заголовок материала остаётся единственным
заголовком страницы и публикуется вместе с черновиком. Документ содержит
`eyebrow`, `intro`, необязательную обложку `cover` и разделы `sections` со
стабильными ID, подписью, заголовком и блоками. Обложка — цветной постер
с фиксированным оформлением либо загруженное изображение.

Блоки: Markdown-текст, заметка, сравнение «до/после», 2–4 факта, 2–6 шагов
с ролями, изображение, раскрываемое пояснение, 2–4 переключаемых варианта
и импорт старого материала (`legacy`). Все поля обязательны; лишние поля,
неизвестные виды и повторяющиеся ID отвергаются. `legacy.body` сохраняет
старый `markdown-embeds-v1` целиком; вложенный артефакт остаётся схемой 1/1.

`journal_contract.py` — неизменяемые модели без импорта приложения.
`journal.py` — чистый компилятор. `JournalRender` содержит:

- `schema_version: 2`, `policy_version: 1`, `source_hash`;
- `document`: проверенный документ либо `null` при ошибке;
- `legacy`: пары `block_id` / проверенный `GuideRender` для импортов;
- `diagnostics`: русские сообщения с ID блока и кодом;
- `file_ids`: все доступные по публикации файлы;
- `image_file_ids`: подмножество изображений для проверки MIME при публикации
  без повторного разбора Markdown под writer lock.

Неверный JSON и ошибки содержимого сохраняются как редактируемый черновик:
исходник не переписывается, `document` равен `null`, файлы и вложенные деревья
пусты. Публикация требует артефакт без диагностики с хешем текущего исходника.
Изменение только названия/описания переносит прежний артефакт в черновик
без компиляции. Preview и сохранение проверяют актуальные сессию, права,
ревизию и флаг повторно после компиляции. Право остаётся `edit_html_material`.

Ограничения: исходник 256 KiB, артефакт 512 KiB; 1–20 разделов, 1–20 блоков
в разделе и не больше 60 во всём документе; Markdown-поле до 8192 символов,
intro до 1000, подписи до 120, заголовки до 240. Импорт до 128 KiB UTF-8.
Символьные пределы считаются по Unicode code points, а не UTF-16 единицам.
Названия разделов, постера, шагов, раскрытий и переключателей, подписи фактов,
вариантов и сторон сравнения, а также alt изображения не могут быть пустыми
или состоять из пробелов. Необязательные подписи/надзаголовки, роль шага и
заголовок заметки допускают пустую строку.
Размеры изображений 1–4096, всего до 20 вхождений, включая обложку, галереи,
свёрнутые блоки и невидимые варианты. Всего до 512 различных файлов, включая
ссылки на документы во всех панелях и импортах. Оба компилятора делят очередь:
одна работа, два ожидающих, ожидание до 0,2 с, дочерний процесс до 1 с.
Изолированный интерпретатор импортирует только чистые схемы/парсеры,
не читает settings/.env/БД и не обращается к внешним сервисам.

Markdown-ссылки допускают HTTPS, пути сайта (кроме служебных), `file:file-ID`
и `#id` существующего раздела. Код и пропущенный HTML не предоставляют прав
на файлы. Каждое изображение/строка галереи обязано ссылаться на собственный
завершённый файл PNG/JPEG/WebP; PDF разрешён как ссылка на файл. Все панели,
включая изначально скрытые, проверяются до сохранения и повторно при публикации.
Клиент откладывает запросы изображений скрытых панелей до их открытия.

`tests/test_journal_compiler.py` проверяет все виды, пределы и протоколы,
код-примеры, скрытые ссылки, импорт и реальный изолированный процесс.
`tests/test_journal_materials.py` проверяет lifecycle через HTTP, несовпадение
ревизии и потерю прав/сессии/флага во время компиляции, файлы во всех видах
панелей, MIME, сохранность старой публикации, неизменяемый кэш, свежую ACL
и отсутствие записей/компиляции на чтении. Существующий корпус v1 остаётся
обязательной регрессией; реальные VK/S3 в этих проверках не используются.

Выкладка и включение флага требуют отдельного разрешения владельца. Перед
выкладкой применяются обычные правила SQLite backup API и репетиции startup.
После первой расширенной публикации старый бинарник без renderer не является
полноценным UI-откатом: выключают новые записи либо используют совместимую
версию с безопасным текстовым представлением. Восстановление старой БД поверх
новых изменений пользователей для отката интерфейса не требуется.

# Уточнения реализации API 1.3

Согласованные требования остаются в CODEX_FRONTEND.md/CODEX_BACKEND.md. Здесь зафиксированы технические read API и адаптеры, не расписанные отдельными путями в исходной карте.

## Версии сезонной сводной

- `GET /api/seasons/{season_id}/summary/versions` → `{items, next_cursor}`. Элемент: `version`, `changed_by: UserRef`, `changed_at`, `reason`, `previous_summary_version`.
- `GET /api/seasons/{season_id}/summary/versions/{version}` → те же метаданные + `summary: SeasonSummary`, `contributions`, `master_bonuses` — снимки этой версии.
- Только председатель, его действующие замы и мастер HR. Историческая версия не имеет прав редактирования.
- Закрытие сохраняет первую утверждённую версию. Каждая коррекция/разрешённая прямая правка closed-оценивания создаёт новую версию; состав, категории и база/получатель бонуса взяты из снимка закрытия.
- Вся команда correction выполняется одной транзакцией; объект другого сезона или ошибка любого элемента откатывают пакет полностью.

## Идентификация блоков

`block_id` — неизменяемый UUID, имя блока остаётся пользовательским названием. Новые DTO/входные данные используют UUID; совместимые старые ссылки по имени разрешаются на границе. Внутренние legacy-строки не являются источником прав. Переименование не меняет ID блока, членства или ссылки новых API.

## Привязка VK

`POST /api/auth/vk/link {access_token}` требует действующую авторизацию существующего аккаунта. Обычный VK-вход ищет только сохранённую внешнюю identity, не ФИО/совпадение почты. Фото VK не загружается.

## Legacy guides and storage

`GET /materials/legacy-guides/{guide_id}` returns `{guide_id, material_id, revision}` only after the current material read check. Old IDs and Guide rows are preserved as migration data. The duplicate `/guides` CRUD and old mapping endpoint are retired (АВ-11/37). Bookmarked `/docs/:id`, `/docs/:id/edit` and `/guides/:id` enter the current read-only material page. Draft save and explicit publication use only the material API; publication updates the same historical Guide row. See [LEGACY_GUIDE_RETIREMENT.md](LEGACY_GUIDE_RETIREMENT.md).

New PGAS entries require `file_url: "file:<file_id>"` for a completed contextual PGAS file. Its saved verified name/MIME are authoritative; arbitrary URL creation cannot bypass complete. Existing raw URLs remain readable through the legacy adapter. The response gives that reference as `/api/files/<file_id>/content` (release 1, step 8: nothing is signed for a client); old public upload URLs and other bucket keys, including `private/` and `sealed/`, stay as written and unsigned. External legacy links stay unchanged; no remote content is downloaded by migration. Existing public bucket ACLs require an operator-side private-access rollout; changing a DTO does not revoke an old public URL.

## Ревизия обычного доступа в session

GET /session возвращает access_revision — стабильный непрозрачный отпечаток
обычных членств блоков и состава организаторов подмероприятий. Эти основания
доступа хранятся отдельно от RoleAssignment. Изменение отпечатка требует
удалить закрытый клиентский кэш и пересоздать его открытых наблюдателей.
Проверка выполняется при возврате к окну и периодически раз в 60 секунд.
Сам отпечаток не предоставляет права: каждый endpoint проверяет текущий ACL.

## Подтверждение версий закрытой коррекции

POST /seasons/{id}/summary/correct возвращает прежнюю сводную и дополнительный
массив applied_revisions: [{kind, id, revision}]. Эти номера читаются в той же
транзакции, что и успешная коррекция. Клиент удерживает версию сводной вместе
с исходной revision записи и использует подтверждение для следующей команды.

## Права выпуска 1

Правила доступа собраны в одной таблице `POLICY` в `backend/access.py`.
Серверные проверки и списки `capabilities` берут правила из неё, поэтому
capability выдаётся ровно тогда, когда сервер выполнит команду. Соответствие
проверяет `tests/test_access_matrix.py`: 16 ролей × все операции.

Новые capabilities:

- `view_meeting` у мероприятия и подмероприятия: можно открыть его созвон
  (`GET …/meeting`). Ссылку на созвон клиент показывает только при ней.
- `create_shared_material` в `/session`: можно создать КМБ или общий документ.
  Гайд создаёт тот, у кого есть `edit_block` в карточке блока.

Изменения ответов:

- `PATCH /tasks/{id}` проверяет право на область задачи. Тот, кто не может
  читать задачу, получает 404, а тот, кто читает, но не руководит областью, — 403.
  Revision сверяется после проверки прав.
- `GET /assignments/unresolved` без `view_unresolved_assignments` в `/session`
  отвечает 403, а не пустым списком.
- В закрытом сезоне задачи, оценивание, заслуги, решения сводной и коррекции
  правят председатель и замы. Отказ — 403 с префиксом `Forbidden` (раньше 422).
- `manage_deputies` у руководителя мероприятия или подмероприятия закрытого
  сезона не выдаётся: состав закрытого сезона не меняется.

## Хранилище, вход через VK и очистка (выпуск 1)

Ссылки на бакет в текстах материалов и гайдов (FIX_PLAN 0.2):

- При чтении ничего не подписывается (шаг 8, раздел «Файлы» ниже): `file:<id>`
  становится адресом `/api/files/<id>/content`, ссылки на бакет — `private/`,
  `sealed/`, старые загрузки и прочие ключи — остаются как записаны, без подписи
  (решение владельца 6).
- Редактор получает поле `source_content` — сохранённый текст: черновик, а если
  его нет, опубликованный текст. В нём `file:<id>` и ссылки без подписи. Поле
  выдаётся только тем, у кого есть `edit_material`. `published_content` — только
  для показа, в нём `file:<id>` заменены адресами API.
- `POST /materials`, `PATCH /materials/{id}` и публикация
  отвечают 422, если в тексте появилась новая ссылка на
  бакет, которой нет в опубликованном тексте. Новые файлы прикрепляются как
  `file:<id>`. Подписанная ссылка на вложение этого же материала сохраняется как
  `file:<id>`, подписанная ссылка на старую загрузку — без подписи.
- `PATCH /materials/{id}` без `content` сохраняет исходный текст при
  переименовании. Старого отдельного редактора и административной панели гайдов нет.
- `scripts/repair_storage_links.py --database <путь> [--apply]` чинит тексты,
  в которые раньше попали подписанные ссылки. Без `--apply` база открывается только
  на чтение. Скрипт печатает только числа, повторный `--apply` меняет 0 строк.

Вход через VK (FIX_PLAN 0.3):

- Токен проверяет только VK ID (`id.vk.ru/oauth2/user_info` с `client_id` сайта).
  Запасной проверки через `users.get` нет (решение владельца 7). Отказ VK ID — 401,
  недоступность VK ID — 503; в обоих случаях вход не выполняется.
- `VK_CLIENT_ID` обязателен и должен совпадать с `VITE_APP_ID` сборки frontend.
  При `APP_ENV=production` без него backend не стартует, в других окружениях вход
  через VK отвечает 503. Значения по умолчанию в коде нет.

Очистка аккаунтов (FIX_PLAN 0.4): `scripts/cleanup_accounts.py --apply` атомарно
очищает БД и записывает собственные avatar-объекты в очередь. Внешнее удаление
выполняется только отдельной явной командой `--delete-pending`; без флагов
отчёт остаётся read-only. Неизвестная схема или неполный callback отменяет весь
пакет. Подробности — в `ACCOUNT_RETENTION.md`.

## Назначения, заслуги и созвоны (выпуск 1)

Решения руководителя по назначениям (FIX_PLAN 1.1):

- `POST /assignments/{id}/not-complete` и `…/cancel` принимаются только для
  нерешённых назначений: `assigned`, `in_progress`, `help_required`, `submitted`,
  `needs_revision`. Для `accepted`, `not_completed` и `cancelled` — 409, назначение
  и вклад не меняются. Принятую работу можно вернуть на доработку
  (`request-revision`) и уже затем отменить или отклонить.
- Отмена снимает оценку: у `cancelled` назначения `evaluation` всегда `null`.
  `PATCH /assignments/{id}/assessment-inputs` с `evaluation` для отменённого
  назначения отвечает 409. Часы и дата выполнения отменённого назначения правятся.
- `not-complete`, `cancel` и правка исходных данных оценивания пишут в журнал
  аудита прежние и новые `status` и `evaluation` вместе с причиной.
- Тело каждой команды содержит только её поля: `accept` — `evaluation` и
  необязательный `review_note`, `request-revision` — `review_note`,
  `not-complete` — `evaluation` и `reason`, `cancel` — `reason`. Лишнее поле — 422.

Заслуги (FIX_PLAN 1.2): `PATCH /merits/{id}` принимает только `expected_revision`,
`reason`, `title`, `description`, `assigned_at`, `deadline_at`, `criteria` и
`recipients`. Вид, сезон и область (`source_kind`, `season_id`, `scope`,
`event_id`) задаются при создании, их передача в PATCH — 422. Форма исправления
отправляет только эти поля и показывает название области, а не её ID.

Созвоны (FIX_PLAN 1.3):

- `GET /events/{id}/meeting` и `GET /subevents/{id}/meeting` без актуального
  объявления отвечают 200 с телом `null`, в том числе после `DELETE`. 404 значит,
  что нет самого мероприятия или подмероприятия; без права чтения — 403.
- Право на правку и снятие созвона — одно правило `event.meeting.edit` или
  `subevent.meeting.edit` в `POLICY`. Главный созвон правят председатель и замы, главорги и их
  замы. Созвон подмероприятия — председатель и замы, ответственные и их замы, а также главорги
  мероприятия и их замы (решение владельца по A-EVT-11). `edit_meeting` и
  `delete_meeting` в созвоне, в карточке владельца и в `/dashboard` выдаются ровно
  тем, кому PUT и DELETE ответят 200.

## История отчётов и главная страница (выпуск 1)

История серии (FIX_PLAN 2.2):

- Историю серии читает тот, кто ведёт любой её экземпляр: в открытом сезоне —
  по текущей роли, в закрытом — по снимку редакторов. Пока прошлый сезон не
  закрыт, новые руководители следующего экземпляра читают его отчёты
  (A-EVT-3). Организаторы читают текущий отчёт, но не историю (A-EVT-6).
  `GET /report-series` перечисляет ровно те серии, для которых
  `GET /report-history` отвечает 200.
- Снимок при закрытии сезона берёт все назначения руководителей, включая
  снятые и заблокированные на момент закрытия. Главорги мероприятия и их замы
  попадают в снимок подмероприятия с ролью `reader`: читают, но не правят.
- `year` в `/report-history` — год начала сезона экземпляра по московскому
  времени, а не дата публикации (A-EVT-5). Сезон, начавшийся 31 декабря в 22:00
  UTC, относится к следующему году.

Курсоры (A-EVT-10): `GET /reports/{id}/versions`, `/report-history`,
`/assessments`, `/assignments/unresolved` и `/seasons/{id}/master-bonuses`
отдают страницы по `api_contract.PAGE_SIZE` (100) записей. Следующая страница —
`?cursor=<next_cursor>` с теми же фильтрами; последняя — `next_cursor: null`.
Курсор непрозрачен, испорченный — 422. Версии идут по возрастанию номера,
история — от новых публикаций, оценки — от новых записей, нерешённые
назначения — по сроку, бонусы — по блоку.

Выбор серии (FIX_PLAN 2.21): формы создания мероприятия и подмероприятия
предлагают «Новая серия» или одну из доступных серий с названием, последним
экземпляром и сезоном. Для подмероприятия — только дочерние серии серии
мероприятия, ещё не занятые другими его подмероприятиями. Сервер по-прежнему
отвечает 422 на чужую серию мероприятия и 409 на недочернюю серию
подмероприятия.

Главная страница (АВ-26, АВ-35): председатель, его замы и мастер HR видят в
`/dashboard` все блоки и мероприятия текущих сезонов. Признак —
`view_all_areas` в глобальных возможностях сессии (правило `dashboard.all`).
Остальные видят только свои команды.

## Задачи и формы (выпуск 1)

Своя версия исходных полей оценивания (решение 32, EDITORS-05 а):

- Часы, оценка и дата выполнения назначения имеют свой счётчик
  `inputs_revision`. Его отдаёт `revision` в `AssessmentInputs`
  (`GET/PATCH /assignments/{id}/assessment-inputs`, `/assessments`), его ждут
  `expected_revision` в `PATCH /assignments/{id}/assessment-inputs`, в элементах
  `POST /assessment-inputs/bulk-hours` и в коррекциях вида `assessment_inputs`
  закрытой сводной.
- Счётчик растёт при любом изменении этих полей, кто бы их ни менял: сдача
  выставляет дату выполнения, поэтому правка, прочитанная до сдачи, получает 409.
- Версия назначения (`revision` в `Assignment`) растёт только вместе с видимым
  исполнителю: статусом, сдачей, замечанием. Правка часов и оценка без смены
  статуса её не меняют, и команда исполнителя с прочитанной ранее версией
  проходит. Оценка, меняющая статус, меняет обе версии.
- Поля задачи (дата выдачи, дедлайн, признаки) по-прежнему идут по версии
  задачи: дедлайн виден исполнителю, а команды исполнителя версию задачи не
  ждут.

Даты задачи (УВ-5): дату выдачи, дедлайн и дату выполнения, когда она уже
есть, переносят председатель, его замы и мастер HR (правило `task.dates.edit`;
в закрытом сезоне — председатель и замы). Руководители направлений заполняют
часы, оценку и признаки (`task.inputs.edit`). Чужой перенос — 403; то же время
в другой записи переносом не считается и проходит. Право видно возможностью
`edit_assessment_dates` в `TaskInputs` и `AssessmentInputs`; формы без неё
показывают даты только для чтения. Каждое изменение пишется в журнал аудита
со старыми и новыми значениями.

`access_revision` сессии считает членства в блоках по `block_id`:
переименование блока не меняет версию его участников (A-FE-1).

Формы (FIX_PLAN 2.12):

- Изменение прав без смены аккаунта не пересоздаёт рабочее место: открытые
  страницы перечитывают данные и сохраняют ввод, а данные, на которые пришёл
  ответ 403 или 404, убираются с экрана. Всё сбрасывается только при смене
  `user_id`, `account_state` или `registration_status`.
- Формы одной записи (например, организаторы и описание подмероприятия,
  строки одной сводной, сведения и повторная отправка регистрации) учитывают
  собственные сохранения друг друга. Базовая версия продвигается только по
  точной цепочке своих сохранений from→to; чужая версия по-прежнему
  останавливает форму с баннером сравнения.
- Конфликт 409 в форме помощи и в форме сдачи предлагает «Обновить данные».
  У сдачи сохранённые значения — пустой текст без файлов рядом с видимым
  исполнителю состоянием.
- Формы создания комментария и подмероприятия после успеха пустые.
- Множественный выбор людей — поиск, флажки и список выбранных. Снятие
  сохранённых людей требует подтверждения «Будут сняты: …».

## Заявки, регистрация, вход и кабинет (выпуск 1)

Заявки в блоки (решение 16, A-ROL-3):

- `BlockRequest` закрытой заявки дополнен полями `decided_at` (время
  последнего решения) и `decision_reason` (причина, только у `rejected`).
  У открытой заявки оба поля `null`.
- Заявку и причину отказа видят все, кто видит заявку: заявитель, председатель
  и замы, мастер HR, вся команда HR-блока (правило `block_request.view_as_hr`)
  и руководители блока заявки.
- `PATCH /participants/{id}/category` с той же категорией ничего не меняет:
  версия не растёт, запись аудита не пишется (A-ROL-12).

Регистрация (FIX_PLAN 2.10):

- `POST /auth/register` требует все поля, кроме отчества (решение 29):
  `surname`, `name`, `group_number`, `tg`, `phone`, `vk`, `residence`, `funding`
  (`budget` или `contract`, без значения по умолчанию). Пробелы по краям
  срезаются; пустое после этого поле — 422.
- Номер группы — число от 100 до 700 в регистрации, заявке
  (`PATCH /registrations/me`) и профиле (`PATCH /profile/{id}`); иное — 422.
  `UserOut.group_number` — число или `null`, если сохранённая группа не число.
- `RegistrationFields.funding` — `budget`, `contract` или `null`. Заявка нового
  VK-аккаунта начинается с пустой группы и `funding: null`; одобрить её нельзя
  (422), пока заявитель сам не заполнит поля. Уведомление
  `registration_submitted` приходит, когда ожидающая заявка впервые стала
  полной.
- Почта сравнивается без учёта регистра при регистрации, правке заявки,
  одобрении и правке профиля (409). Если в базе несколько вариантов одной почты
  в разном регистре, вход берёт точное совпадение, иначе отказывает и пишет
  предупреждение в журнал.
- `GET /registrations?status=pending|rejected|approved` — фильтр; без него
  порядок: ожидающие, отклонённые, одобренные, внутри — по `user_id`.
- `Dashboard.pending_registration_count` — число ожидающих регистраций для
  тех, кто их рассматривает (иначе 0).

Вход и токены (FIX_PLAN 2.11):

- `POST /auth/refresh` с уже использованным токеном отвечает 401 и не удаляет
  cookie `refresh_token`: его могла заменить вкладка, обновившая пару первой
  (A-ROL-14). Истёкший токен и отказ по аккаунту cookie по-прежнему удаляют.
  Клиент обновляет пару по очереди между вкладками (`navigator.locks`) и после
  неудачи повторяет запрос с парой, которую успела записать другая вкладка.
- `POST /auth/vk`, `POST /auth/vk/link` и `POST /auth/login` не держат общую
  блокировку записи: ответ VK и проверка пароля ждутся вне транзакции, затем
  одна короткая транзакция (A-ROL-15).
- Передача поста не удаляет refresh-токены нового председателя (решение 25).
- 401 при чтении сессии после неудачного refresh удаляет закрытые данные из
  кэша клиента (A-FE-4).

Кабинет «Администрирование» (`/admin`, АВ-34): вкладки видны по
возможностям сессии — `review_registrations` (заявки на регистрацию,
открываются первыми), `view_leadership` (председатель и замы; менять может
только председатель), `restore_account` (архив аккаунтов),
`manage_material_editors` (общие материалы), `grant_pgas_admin`
(администраторы ПГАС), `reset_password` (сброс пароля). Старые адреса
`/registrations`, `/leadership`, `/accounts/archive`, `/admin/users` ведут на
вкладки.

Администраторы ПГАС (решение 14):

- `GET /pgas-admins` — список `UserReference`; `PUT /users/{id}/pgas-admin`
  с `{"pgas_admin": true|false}` выдаёт или снимает право. Обе команды — для
  председателя и замов (`pgas.grant`), изменение пишется в аудит.
- Правку ПГАС клиент показывает по возможности `manage_pgas`.

Временный пароль (АВ-52 (а)):

- `POST /accounts/{id}/temporary-password` (председатель и замы,
  `account.reset_password`) отвечает `{user_id, email, temporary_password}`.
  Пароль показывается один раз и нигде не хранится в открытом виде; аудит
  пишет только факт сброса. Прежний пароль и сессии аккаунта перестают
  действовать. Пароль председателя и замов так не сбрасывается (403).
- Пока временный пароль не сменён, `Session.password_change_required` равно
  `true`, возможностей нет, а рабочие маршруты отвечают 403
  «Password change required». Доступны сессия, выход и
  `POST /auth/change-password`; смена снимает признак и, как раньше,
  завершает все сессии.
- Аккаунт только с VK (`MeOut.has_password: false`) видит баннер «Задайте
  пароль».

## Файлы (выпуск 1)

Выдача с проверкой на каждый запрос (решение 23, АВ-9):

- `GET /files/{id}/content` отдаёт байты файла. Права проверяются на каждый
  запрос, поэтому отзыв доступа (архив, снятая ссылка из материала, смена
  аватара) действует сразу. Нет доступа или файла — 404, хранилище недоступно —
  503.
- Маршрут принимает и `Authorization: Bearer`, и cookie `access_token`: `<img>`
  и обычная ссылка заголовок не отправляют. Только этот маршрут и только GET.
- Ответ: `Content-Type` из записи файла, `Content-Disposition` с исходным именем
  (A-MAT-15): `attachment; filename="<ASCII-замена>"; filename*=UTF-8''<имя>`,
  без CR, LF, кавычек и обратной косой черты. Картинки PNG, JPEG и WebP — `inline`.
  Кроме того: `Cache-Control: private, no-cache`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: sandbox`.
- Подписанная ссылка на хранилище клиенту не отдаётся. За nginx
  (`frontend/nginx.conf`, заголовок `X-File-Delivery: accel`) backend отвечает
  пустым телом с `X-Accel-Redirect: /_storage` и `X-Storage-Url` — подписью на
  60 с. Внутренний location берёт объект по ней. Cookie и `Authorization` в
  хранилище не уходят, заголовки хранилища скрыты, его отказ даёт 502. Без nginx
  (локальный запуск, тесты) backend передаёт байты сам.
- `GET /files/{id}/download` проверяет доступ и отвечает
  `{download_url: "/api/files/<id>/content", expires_at: null}`.
- Аватары (`photo_url`, `avatar_url`), `PgasEntry.file_url` и `file:<id>` в
  текстах приходят как `/api/files/<id>/content`. Списки людей, ПГАС, материалы и
  гайды хранилище не вызывают, поэтому его сбой их не ломает (A-MAT-9). Старая
  публичная загрузка без переноса отдаётся по своему адресу без подписи.
- `file_records.sealed_at` — время, когда записана проверенная копия
  `sealed/<id>`. Его ставят `complete` и `scripts/seal_completed_files.py`.
  Записи с отметкой читаются без HEAD. `file_records.storage_key` — ключ старой
  загрузки, перенесённой без копирования. Обе колонки добавляются при старте.
- Снимки сводной и бонусов показывают аватары на момент чтения, а не
  сохранённые ссылки. У обезличенного участника `null` (A-MAT-16). Сохранённые
  данные не меняются.

Старые гайды (FIX_PLAN 2.14, АВ-11/37):

- Старые URL разрешаются через `/materials/legacy-guides/{id}` и открывают
  текущий экран материала. Опубликованный текст — Markdown, исходный HTML
  мигрируется без перезаписи строки `guides`.
- `to_markdown` конвертирует только документы, которые действительно HTML.
  Если в тексте есть разметка Markdown или код, меняется только `<br>`, ничего не
  экранируется. Теги внутри кода не учитываются. `source_content` текущего редактора
  не конвертируется заново при сохранении (A-MAT-4).
- `POST /materials` с `file:<id>` в тексте — 422: новый материал ещё не владеет
  файлами (A-MAT-8). Файл, недоступный читателю, ломает только свою ссылку, а
  не весь список.
- Сохранение принимает показанный адрес `/api/files/<id>/content` вложения
  этого материала и хранит его как `file:<id>`.

Перенос старых загрузок (АВ-10): `scripts/adopt_legacy_files.py --database
<путь> [--apply]`. Запускается после миграции v13 и `repair_storage_links.py`.
Каждой старой публичной загрузке — `users.photo_url`, `pgas_entries.file_url`,
ссылкам в текстах материалов и их гайдов — достаётся завершённая запись файла
со своим ключом (`storage_key`, без копирования). Ссылка становится
`file:<id>`, аватар — `profile_metadata.avatar_file_id`. Ссылки на `sealed/`,
`private/` и неизвестные ключи не переносятся, только считаются: перенос
открыл бы их (A-SEC-2). Хранилище скрипт не вызывает: размер такой записи 0,
тип определяется по расширению. Без `--apply` база открывается только на
чтение. Скрипт печатает только числа, повторный `--apply` меняет 0 строк.
После переноса и выкладки бакет можно сделать приватным.

## Ошибки (выпуск 1)

Контракт ошибок (FIX_PLAN 2.13, решение 42):

- Тело ошибки — `{detail: {code, message, fields}}`. `code` устойчив, клиент
  выбирает по нему русский текст (`frontend/src/utils/api/messages.ts`).
  `message` — техническая деталь на английском, на экран не выводится.
  `fields` — данные к коду: `limit` у `deputy_limit`, `user_id` у
  `unknown_user` и `inactive_user`, `blockers` у `season_not_ready`, `errors` у
  `validation_error`.
- Старую форму со строкой или списком в `detail` сохраняют только маршруты
  старого сайта: `/auth/*`, `/profile/me`, `/profile/{id}`, `/pgas`, `/pgas/{id}`, `/contacts`, `/contacts/filter`.
  Новые маршруты с теми же началами (`/profile/me/avatar`, `/contacts/archive`,
  `/contacts/emails`, `/materials/legacy-guides/{id}`, `/pgas-admins`) отвечают в новой
  форме. Неизвестный путь — 404 `not_found`.
- Статус задаёт класс ошибки (`backend/errors.py`), а не текст сообщения:
  `NotFound` 404, `Forbidden` 403, `Conflict` 409, `InvalidInput` 422. Маршруты
  не переводят `ValueError` в статус по подстроке (A-SEC-7). Простой
  `ValueError` из разбора значения — 422 `invalid_input`, простой `LookupError` —
  404. Тест `test_error_contract.py` запрещает доменному коду бросать простые
  `ValueError` и `LookupError`.
- 404 — нет объекта или он недоступен для чтения. Ответ совпадает с ответом на
  несуществующий ID (A-SEC-6): подмероприятие, его созвон и созвон мероприятия
  (`Meeting not found`), задача, её комментарии и исходные поля оценивания,
  отчёт и его версии, история серии, заслуга, отметка уведомления. 403 —
  команда над объектом, который читается. Список задач с чужим фильтром области
  остаётся 403.
- Кандидат в составы, заместители и председатели (решение 42): несуществующий —
  422 `unknown_user`, с неодобренной заявкой, в архиве или заблокированный —
  409 `inactive_user`. Предел заместителей — 422 `deputy_limit`, повтор — 422
  `duplicate_users`, руководитель своим замом — 422 `self_deputy`, передача поста
  самому себе — 409 `already_chair`. Получатели заслуг, исполнители задач и
  редакторы материалов при неактивном участнике отвечают, как прежде, 422 с
  `inactive_user`. Повтор в `leaders` и `organizers` пока сохраняется, это
  A-ROL-10 (3.1).
- Переходы и состояния — 409: недопустимый переход исполнителя `conflict`,
  устаревшая версия `revision_conflict`, закрытый сезон `season_closed`,
  неготовый к закрытию сезон `season_not_ready`, второй запланированный сезон
  `planned_exists`, второй итоговый отчёт `final_report_exists`. Команда закрытого
  сезона от того, кому она не положена, — 403 `forbidden`.
- `POST /seasons` требует `type`. `object_kind` в `POST /season-corrections` — только
  `event`, `block_task` или `merit`. Иначе 422 `validation_error`.
- Upload-intent к несуществующему владельцу — 404. Серия отчётов не дочерняя
  для мероприятия — 422 `invalid_input` (раньше 409).
- Препятствие закрытию сезона, кроме `kind`, `owner_kind`, `owner_id` и
  технического `title`, содержит `subject` (название задачи, мероприятия или
  сезона) и `assignee` (имя исполнителя назначения).
- `POST /auth/vk` (маршрут старого сайта, `detail` строкой) — 409
  `vk_link_required`, если VK ID назван в сохранённой ссылке действующего аккаунта,
  а привязки VK у него нет: так выглядят аккаунты старого входа через VK до карты
  миграции. Второй аккаунт не создаётся (FIX_PLAN 2.18, MIGRATION_V13.md).

`invalid_input`, `validation_error`, `registration_attempt_limit`,

## Полная история и скрытие текста версии

`GET /history?target_kind=…&target_id=…` возвращает только разрешённую projection
с before/after, автором и временем. История task/assignment/merit/season/block/
event/subevent/leadership имеет общий контракт. Публичная история задачи не
выдаёт private исходные поля, результаты оценивания и основания ККР.

`POST /history/{activity|audit}/{source_id}/hide` с `expected_revision: 1`
скрывает собственный текст версии и после закрытия сезона при текущем доступе.
Чужие версии можно скрывать только при доказанном руководстве на дату изменения.
Это относится и к председателю/замам: нынешняя должность не заменяет
подтверждённый глобальный исторический интервал. Неизвестные даты и label-only
идентичность блока не используются как доказательство. Остаются автор/скрывший/
дата; текст источника и связанный predecessor следующей версии удаляются.
Текущие объекты, числовые поля ККР и утверждённые снимки сезона не меняются.

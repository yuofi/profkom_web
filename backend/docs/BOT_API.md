# Связь с ботом HereBot: контракт `/api/bot/v1`

[Каталог контрактов](README.md) · [Решения 4 ноября](../../docs/decisions/2026-11-04-bot-integration.md)

Сайт — сервер, бот ВК [HereBot_VK](https://github.com/profkomvmk/HeroBot_VK) — его клиент. Бот
сам забирает у сайта работу (уведомления, пачки рассылок, команды консоли), выполняет её в VK
и отчитывается. Сайт не обращается к VK и к боту внутри запросов пользователей. Базы не
общие: сайт хранит очередь и состояние бота у себя, бот — свои данные в PostgreSQL.

Разделы помечены этапом. Этапы 1–4 реализованы. У этапа 5 реализована сторона сайта
(`/api/bot/v1` и маршруты консоли), интерфейс и бот — в работе: при реализации этап уточняют
здесь же, совместимо с правилами версии ниже.

## Транспорт и доступ

- Адрес — обычный адрес сайта: бот обращается к `<SITE_API_URL>/api/bot/v1/...` через nginx.
  По сети, кроме loopback, только HTTPS.
- Заголовок `Authorization: Bearer <токен>`. Токен — не меньше 32 случайных байт
  (`secrets.token_urlsafe(32)`).
  - У бота он в `.env`: `SITE_BOT_TOKEN`, вместе с `SITE_API_URL`. Без обоих интеграция в боте
    выключена; одно без другого — ошибка настроек (код выхода 2).
  - Сайт хранит только SHA-256 токена в hex: `BOT_API_TOKEN_SHA256` в `backend/.env`. Можно
    перечислить через запятую два значения, чтобы сменить токен без простоя: сначала сайт
    принимает старый и новый, потом бот получает новый, потом старый убирают.
  - Без `BOT_API_TOKEN_SHA256` интеграция на сайте выключена: все маршруты `/api/bot/v1`
    отвечают 404 с кодом `bot_api_disabled`.
  - Сайт сравнивает SHA-256 присланного токена с каждым значением через
    `hmac.compare_digest`. Значения — 64 строчные hex-цифры; другое значение настройки
    останавливает запуск backend.
- Маршруты `/api/bot/v1` не входят в пользовательский роутер `/api`: у них нет JWT, проверки
  аккаунта и `guard_working_access`. Зависимости — проверка служебного токена (без обращения к
  БД) и обычная единица работы: GET — читающая, без блокировки записи; POST — пишущая.
- Ответы на ошибки — обычный конверт сайта `{detail: {code, message, fields}}`:

  | Статус | Код | Когда |
  | --- | --- | --- |
  | 401 | `bot_token_invalid` | Нет заголовка или токен не подходит |
  | 404 | `bot_api_disabled` | Интеграция на сайте выключена |
  | 413 | `payload_too_large` | Тело больше 256 КиБ |
  | 422 | обычный код проверки | Тело не по схеме |

  Порядок проверок: размер тела, затем настройка и токен, затем схема. Тело больше 256 КиБ
  отклоняется по `Content-Length` до чтения, а без длины — по мере чтения. Тело читается до
  единицы работы, поэтому медленная отправка не держит блокировку записи. В OpenAPI у этих
  маршрутов своя схема безопасности `BotServiceToken`.
- Время — ISO 8601 в UTC с `Z`: `2026-11-04T09:00:00Z`.

**Правила версии.** Внутри `v1` изменения только добавляют поля, виды команд и состояния. Обе
стороны пропускают незнакомые поля. Незнакомую команду бот возвращает с состоянием
`unsupported`. Незнакомый результат сайт пропускает. Несовместимое изменение — новый префикс
`/api/bot/v2`, старый работает, пока бот не обновлён.

## Цикл бота (этап 1)

Поток `site-sync` бота, независимо от потоков Long Poll и планировщика:

1. Отметка здоровья `site` в начале каждого прохода и после каждого запроса: она значит «цикл
   жив», а не «сайт доступен» (решение 0003 бота). Если сайт недоступен, бот остаётся здоровым.
2. `GET /work`. Если в ответе есть работа — выполнить её, собрать результаты и сразу начать
   следующий проход. Если работы нет — подождать `poll_after_ms`, но не меньше 1 и не больше
   60 секунд. Заявка привязки (этап 2) прерывает ожидание: бот подтверждает её в начале
   прохода, до `GET /work`.
3. `POST /report` — только если есть результаты, пора отправить heartbeat (60 секунд с
   последнего удачного отчёта), в буфере есть запись уровня CRITICAL или набралось 50 групп
   ошибок. Холостой проход пишущих запросов не делает.
4. Таймауты: подключение 3 с, чтение 15 с. При недоступности сайта (сеть, 5xx) — паузы
   1, 2, 4 … 60 секунд. Первая неудача — WARNING, дальше — INFO не чаще раза в 10 минут,
   восстановление — INFO. При 401 и 404 — ERROR не чаще раза в 10 минут и пауза 60 секунд.
5. При остановке бот последним отчётом передаёт heartbeat с `stopping: true`, с таймаутом
   3 секунды и без повторов.

Результаты и ошибки, которые не удалось отправить, бот держит в памяти (ограниченно) до
следующего удачного отчёта. Неподтверждённый отчёт он повторяет без изменений, с тем же
`report_id`. Отчёт с ответом 400, 413 или 422 бот выбрасывает: сайт не примет его никогда, а
повторы задержали бы heartbeat. Ошибки журнала из такого отчёта теряются, а результаты команд
вернутся, потому что сайт выдаёт команды, пока их не подтвердят. Перенаправления (3xx) бот не
выполняет и считает отказом: `SITE_API_URL` должен вести прямо на сайт по HTTPS. Доставка — «хотя бы один раз». Повтор отправки в VK не создаёт
дубля, потому что `random_id` у каждой отправки постоянный (этапы 3–4). Повтор отчёта сайт
узнаёт по `report_id`.

## `GET /api/bot/v1/work` (этап 1)

Параметр `limit` — 1…100, по умолчанию 50: сколько доставок отдать. Пачек рассылок — не больше
5 за ответ, отдельно от `limit`. Бот `limit` не передаёт.

```json
{
  "api": 1,
  "server_time": "2026-11-04T09:00:00Z",
  "poll_after_ms": 3000,
  "paused": false,
  "deliveries": [],
  "broadcasts": [],
  "commands": []
}
```

До этапа 5 `paused` всегда `false`, а `commands` пуст; `deliveries` заполняется с этапа 3,
`broadcasts` — с этапа 4. Сайт ничего не отмечает при выдаче: одна и та же работа выдаётся, пока
бот не подтвердит её в `/report`.

- `paused` (этап 5): отправка приостановлена из консоли. Доставки и рассылки не выдаются,
  команды выдаются. Подробно — в разделе «Консоль бота».
- `deliveries[]` (этап 3): `{delivery_id, peer_id, text, random_id, created_at}`. `text` — не
  длиннее 4000 символов. `random_id` — целое от 1 до 2³¹−1, постоянное для `delivery_id`. Что
  попадает в список — в разделе «Уведомления через бота».
- `broadcasts[]` (этап 4): пачки рассылок `{broadcast_id, batch_id, text, peer_ids, random_id,
  created_at}`. В `peer_ids` от 1 до 100 VK получателей по порядку их `user_id`, `text` —
  1…4000 символов, `random_id` — целое от 1 до 2³¹−1, постоянное для `batch_id`. `batch_id` —
  строка до 64 символов (сейчас `<broadcast_id>-0000`), бот её не разбирает. Что попадает в
  список — в разделе «Рассылки».
- `commands[]` (этап 5): `{command_id, kind, args, requested_by, created_at}`.
  - `kind`: `restart`, `logs`, `updates_check`, `update`, `rollback`.
  - `args` для `logs`: `{lines: 1…2000, level, contains}`. Для `update` и `rollback`:
    `{version}` — версия, которую видел человек.
  - `requested_by`: `{user_id, vk_user_id, name}`.
  - Что выдаётся и как бот их выполняет — в разделе «Консоль бота».

## `POST /api/bot/v1/report` (этап 1)

Тело — не больше 256 КиБ.

```json
{
  "api": 1,
  "report_id": "9f1c…32 hex",
  "boot_id": "4be0…32 hex",
  "heartbeat": {
    "version": "2.3.0",
    "commit": "abc1234",
    "started_at": "2026-11-04T08:59:00Z",
    "interval_s": 60,
    "stopping": false,
    "components": {"longpoll": 4, "scheduler": 12, "site": 0},
    "longpoll_connected": true,
    "database": "postgresql",
    "counters": {"chats": 3, "delayed_pending": 0, "delayed_failed": 0, "tokens": 5}
  },
  "errors": [
    {
      "fingerprint": "0f3a9c2d4e5b6a70",
      "level": "ERROR",
      "logger": "root",
      "where": "_scheduler_loop",
      "message": "Critical error in the scheduler loop: …",
      "traceback": "Traceback (most recent call last): …",
      "count": 3,
      "first_at": "2026-11-04T08:59:10Z",
      "last_at": "2026-11-04T08:59:40Z"
    }
  ],
  "deliveries": [],
  "broadcasts": [],
  "commands": [],
  "vk_events": [],
  "tokens": []
}
```

Ответ: `{"api": 1, "accepted": true, "duplicate": false, "server_time": "…"}`. Ответ 2xx
значит, что отчёт принят: `accepted` всегда `true`.

Сайт проверяет: `report_id` и `boot_id` — 32 строчные hex-цифры, `fingerprint` — 16, `count` —
1…10⁹, `interval_s` — 1…86400, в `components` и `counters` — до 32 ключей, `api` — `1`. Время без
пояса считается UTC; сайт хранит и отдаёт его с точностью до секунды.

**Поля:**

- `report_id` — новый для каждого отчёта, повтор того же отчёта — с тем же `report_id`. Сайт
  помнит последний: повтор возвращает `duplicate: true` и ничего не меняет.
- `boot_id` — новый при каждом запуске процесса бота. По его смене консоль видит перезапуск.
- `heartbeat` может быть `null`, если отчёт только с результатами.
  - `version` — версия сборки, как в `!версия` бота: `2.3.0` — релиз, `2.3.0-3-gabc1234` —
    коммит после релиза, суффикс `-dirty` — незакоммиченные правки, `-local` — запуск без
    `deploy.sh`. `commit` — короткий хэш сборки или пустая строка.
  - `components` — сколько секунд назад была отметка здоровья компонента; `null`, если отметки
    нет.
  - `database` — `postgresql` или `sqlite`.
  - `counters` — счётчики из БД бота, считаются раз в heartbeat. Счётчик, который не удалось
    посчитать, в отчёт не попадает. С этапа 3 там же `deliveries_sent`, `deliveries_denied`,
    `deliveries_failed` — итоги доставок в памяти процесса бота с его запуска, не из БД.
  - `updates` (этап 5): состояние канала обновлений из `state/`, раздел «Консоль бота».
- `errors` — до 50 групп записей журнала бота уровня WARNING и выше.
  - Группа — одинаковые `level`, `logger`, `where` и `message` после замены цифр на `#`.
    `fingerprint` — 16 строчных hex-цифр; бот берёт первые 16 hex SHA-256 этих полей, сайт
    считает отпечаток просто ключом группы.
  - `count` — сколько раз запись повторилась с прошлого удачного отчёта.
  - `message` — до 1000 символов, `traceback` — до 8000 символов, пустая строка или `null`,
    если его нет; сайт обрезает и сам.
    `logger` и `where` сайт обрезает до 200 символов.
  - Сайт складывает группы с одним `fingerprint`, в том числе внутри одного отчёта: `count`
    суммируется, `first_at` — меньший, `last_at` — больший, остальные поля — из последнего
    отчёта.
  - Секреты (ключ Long Poll, токены) бот вычищает до отправки.
- `deliveries` (этап 3): до 100 записей `{delivery_id, status, vk_message_id, error_code,
  retryable}`. `status`: `sent`, `failed`, `denied` — `denied` значит, что VK ответил 901
  (пользователь не разрешил сообщения сообщества). `vk_message_id` — целое не меньше 0 или
  `null` (у `sent` тоже, если VK не вернул номер). `error_code` — целое (код ошибки VK, у
  `denied` — 901), строка без кода VK (`network`, `http_<статус>`, `invalid`, `unexpected`)
  или `null` (у `sent`); строку длиннее 64 символов сайт обрезает. `retryable` бот передаёт
  всегда (у `sent` и `denied` — `false`), без поля сайт считает `false`. Как сайт их применяет
  — в разделе «Уведомления через бота».
- `broadcasts` (этап 4): до 10 записей `{batch_id, results}`, в `results` до 100 записей
  `{peer_id, status, vk_message_id, error_code, retryable}`. Поля и значения — как у
  `deliveries`; `batch_id` — 1…64 символа, `peer_id` — целое больше 0, иначе 422. Как сайт их
  применяет — в разделе «Рассылки».
- `commands` (этап 5): до 20 записей `{command_id, status, code, message, output}`. `status`:
  `running`, `done`, `failed`, `unsupported`. `command_id` — 1…64 символа, иначе 422. `output` —
  строки журнала у `logs`, до 128 КиБ. Итог с большим `output` бот отправляет отдельным
  отчётом, если вместе с ошибками журнала отчёт превысил бы 256 КиБ. Как сайт их применяет — в
  разделе «Консоль бота».
- `vk_events` (этап 2): до 500 записей `{vk_user_id, event, at}`, `event`: `message_allow` или
  `message_deny`. Как сайт их применяет — в разделе «Привязка VK».
- `tokens` (этап 2): до 500 записей `{vk_user_id, status, at}`, `status`: `ok`, `missing`,
  `invalid`, `unknown` — как `user_api.check_user_token` бота.

## Привязка VK (этап 2)

Аккаунт сайта связывается с VK пользователя через бота: сайт выдаёт одноразовый код, человек
отправляет его боту, бот подтверждает код на сайте. Пока интеграция на сайте выключена (нет
`BOT_API_TOKEN_SHA256`), привязки нет нигде и всё работает как до этапа 2.

### Состояние привязки

| `state` | Значит |
| --- | --- |
| `none` | Привязки нет |
| `ok` | VK привязан, сообщения сообщества разрешены, токен у бота `ok` или `unknown` |
| `messages_denied` | VK привязан, сообщения сообщества запрещены |
| `token_missing` | VK привязан, у бота нет токена пользователя |
| `token_invalid` | VK привязан, VK не принимает токен |

Если не выполнено несколько условий, `state` — первое из них по таблице. Требование выполнено
только при `ok`. Токен `unknown` (VK не ответил на проверку) требованию не мешает: сбой VK не
закрывает сайт.

Сайт хранит привязку в `bot_links` и копию `state` в `users.bot_link_state` (`NULL` значит
`none`). Копия меняется в той же транзакции, что и `bot_links`: проверке доступа и
`/api/session` не нужен лишний SQL.

### Когда привязка обязательна

- **Новая регистрация** (аккаунт `pending`). Заявка **готова**, когда все поля заполнены и
  `state = ok`.
  - Рецензенты получают `registration_submitted`, когда ожидающая заявка становится готовой:
    после правки полей, подтверждения привязки, события из отчёта бота или входа через VK ID.
    Регистрация по email больше не уведомляет сразу. Уведомление одно на подачу заявки: если
    заявка той же подачи снова стала готовой (например, человек запретил и снова разрешил
    сообщения), повторного нет.
  - `approve` и `resubmit` неготовой заявки — 409 `bot_link_required`. Capability
    `approve_registration` есть только у готовой заявки.
  - В `ApplicationOut` — поле `bot_link: {state, vk_user_id}`, при выключенной интеграции `null`.
- **Действующий аккаунт** (`active`). До `BOT_LINK_DEADLINE` — только баннер со сроком. С этого
  момента `guard_working_access` отвечает 403 `bot_link_required`, если `state` не `ok`.
  - Ограничение не действует на маршруты, свободные и сейчас (`/auth/*`, `/session`,
    `/registrations/me`, `/registrations/me/resubmit`, `POST /feedback`), на маршруты привязки
    `/bot-link/*` и на консоль бота `/bot/console/*` (у неё свои права).
  - Временный пароль меняют раньше привязки: его проверка идёт первой.
  - Та же проверка — в коротких транзакциях маршрутов с собственной транзакцией
    (`recheck_current_user`).
  - Старые маршруты сайта (`api_contract.LEGACY_ROUTES`: `/auth/*`, `/profile/*`, `/guides`,
    `/pgas`, `/contacts`) отвечают, как на любую свою ошибку, строкой в `detail`:
    `VK link through the bot required`.
  - Без `BOT_LINK_DEADLINE` действующие аккаунты не ограничиваются.

### Настройки сайта

В `backend/.env`. Значение не по формату останавливает запуск backend.

- `BOT_VK_URL` — диалог с ботом: `https://vk.me/<короткое имя>` или `https://vk.me/club<id>`,
  без параметров. Без настройки сайт показывает только команду для бота.
- `BOT_LINK_DEADLINE` — срок для действующих аккаунтов, ISO 8601 с поясом:
  `2026-12-01T00:00:00+03:00`.

### Код привязки

- 10 символов Crockford base32 (50 бит) из `secrets`, показывается как `ABCDE-FGHJK`.
- Сайт и бот нормализуют код одинаково: убирают пробелы и дефисы, переводят в верхний регистр,
  `O` читают как `0`, `I` и `L` — как `1`.
- Живёт 15 минут. Сайт хранит SHA-256 нормализованного кода.
- У аккаунта один действующий код: новый заменяет прежние.

### Как человек привязывает VK

1. На сайте — «Получить код» (`POST /api/bot-link/code`).
2. «Открыть бота» ведёт на `<BOT_VK_URL>?ref=<код>`: VK передаёт `ref` в сообщении,
   которое человек отправит первым, например кнопкой «Начать». Если `ref` не дошёл, человек
   отправляет боту команду `привязать ABCDE-FGHJK`: сайт показывает её с кнопкой
   «Скопировать».
3. Бот проверяет `messages.isMessagesFromGroupAllowed` и токен пользователя, затем вызывает
   `POST /api/bot/v1/links/confirm`.
4. Бот отвечает в ЛС. Если токена нет или VK его не принимает, бот сразу начинает обычный
   диалог выдачи токена; если сообщения запрещены — просит их разрешить.
5. Пока шаг открыт и вкладка видна, сайт раз в 3 секунды читает `GET /api/bot-link/me`.

### `POST /api/bot/v1/links/confirm`

Пишущая единица.

```json
{
  "api": 1,
  "code": "ABCDE-FGHJK",
  "vk_user_id": 123456,
  "messages_allowed": true,
  "token_status": "missing",
  "at": "2026-11-04T09:00:00Z"
}
```

- `vk_user_id` — целое больше 0. `token_status` — как в `tokens`: `ok`, `missing`, `invalid`,
  `unknown`; другое значение — 422.
- `messages_allowed` — `null` (или нет поля), если VK не ответил на проверку. Тогда сайт
  оставляет прежнее значение привязки, а у новой привязки считает `true`: человек сам написал
  сообществу.
- `at` — когда бот проверил сообщения и токен. Это время отсчёта для следующих событий.
  Новая привязка или другой VK берут все поля из подтверждения. Повторное подтверждение того
  же VK меняет поля по правилу событий: значение со временем раньше сохранённого не
  применяется.

Ответ 200:

```json
{"api": 1, "linked": true, "user_id": 42, "display_name": "Иван Петров", "state": "token_missing"}
```

Повтор с тем же кодом и тем же `vk_user_id`, пока код не истёк, — тот же ответ 200 и никаких
изменений: ответ мог потеряться по дороге к боту.

| Статус | Код | Когда |
| --- | --- | --- |
| 404 | `link_code_invalid` | Кода нет; он истёк; его использовал другой VK; аккаунт в архиве или заблокирован |
| 409 | `vk_mismatch` | Аккаунт создан входом через VK ID (`external_identities`, `vk:<id>`), а `vk_user_id` — другой |
| 409 | `vk_taken` | Этот VK привязан к другому аккаунту не в архиве или это VK ID-вход другого аккаунта |
| 429 | `link_rate_limited` | Больше 10 неудачных попыток с этого VK за 15 минут или больше 200 у всех |

Порядок проверок: лимит попыток, код и аккаунт, VK ID-вход аккаунта, занятость VK. Неудачная
попытка — ответ 404 или 409; после 10 неудачных с одного VK (200 у всех) за 15 минут следующие
отвечают 429, даже с верным кодом. Ответ 429 попыткой не считается.

Подтверждение:

- заменяет прежний VK аккаунта, если он был;
- снимает привязку этого VK у аккаунта в архиве;
- записывает в аудит старый и новый VK (`target_kind = user`, причина `bot_link`, автор —
  сам аккаунт); повтор с тем же кодом аудит не пишет;
- отмечает код использованным.

Если ожидающая заявка аккаунта стала готовой, рецензенты получают `registration_submitted`.
Счётчики попыток — в памяти процесса: uvicorn сайта работает одним процессом.

### События из отчёта

- Бот передаёт в `vk_events` каждое `message_allow` и `message_deny` из Long Poll. В `tokens`
  он передаёт каждое состояние своего токена пользователя, которое узнал: сохранённый в диалоге
  токен — `ok`, итог проверки или работы токена перед командой — этот итог, удалённый токен —
  `missing`. Передаются события всех пользователей бота.
  - `unknown` бот не передаёт: VK не ответил, и сайту нечего менять. Сайт `unknown` всё равно
    принимает.
  - Токен, который VK не принял в диалоге токена, — не событие: он не сохранён, а прежний
    токен не изменился.
- Сайт применяет событие только к привязанному VK; остальные пропускает и не хранит.
  Незнакомые `event` и `status` он тоже пропускает (правила версии), отчёт принимается.
- Событие применяется, если его `at` не раньше времени, сохранённого для этого поля
  (`messages_at`, `token_at`). Из нескольких событий с одним `at` действует последнее в списке.
- Сайт пересчитывает `state`. Если ожидающая заявка стала готовой — `registration_submitted`.
- Неотправленные события бот держит в памяти (до 1000 на оба вида, лишние — старые —
  выбрасывает с WARNING). При аварийной остановке они теряются, как и события отчёта, который
  сайт отклонил (400, 413, 422). Тогда человек привязывает VK заново: в подтверждении бот
  передаёт текущее состояние.

### Бот

- Поток Long Poll сайт не ждёт. Код из `ref` или команды бот ставит в очередь потока
  `site-sync` и будит его. Очередь — до 100 заявок; если она полна, бот отвечает «Бот занят,
  попробуйте через минуту».
- Команда — `привязать <код>`, также с `!` или `/` в начале, без учёта регистра. Вне диалога
  на неверный код бот отвечает подсказкой. В диалоге, в том числе когда бот ждёт токен, команда
  срабатывает только с кодом правильного вида: иначе это текст ответа диалогу (например,
  отложенного сообщения).
- `ref` бот берёт после обычной обработки сообщения: «Начать» из ссылки закрывает диалог, как
  текст меню, и иначе закрыл бы диалог токена, который начнёт ответ сайта. `ref` неверного
  вида бот молча пропускает. Если в сообщении и `ref`, и команда, действует команда.
- Код бот отправляет нормализованным, в виде `ABCDE-FGHJK`. `at` — время перед проверками VK.
- Не больше 5 попыток с одного VK за 10 минут; бот считает их до запроса к сайту, отдельно от
  `link_rate_limited` сайта и со своим текстом. Заявка, на которую бот ответил «Бот занят», не
  считается.
- Если сайт недоступен или связь выключена, бот не повторяет заявку сам: человек отправляет код
  ещё раз. Остальные заявки этого прохода получают тот же ответ без запроса к сайту. Ответ 200
  без `linked: true` бот считает ошибкой (ERROR в журнале). 401, 403, 404 (в том числе 404 без
  кода от сайта без этапа 2) и перенаправления — «Привязка к сайту сейчас не работает» и ERROR
  не чаще раза в 10 минут.
- Если `state` — `messages_denied`, а токена нет или он не работает, ответ один: просьба
  разрешить сообщения и сразу диалог токена. `display_name` бот очищает от управляющих символов
  и обрезает до 100 символов.
- На каждый исход — ответ в ЛС: привязано («Аккаунт сайта привязан: Иван Петров»), код не
  подошёл, VK другого аккаунта, VK уже привязан, слишком много попыток, сайт недоступен,
  привязка не настроена. Без интеграции (`SITE_*` не заданы) команда отвечает, что привязка к
  сайту не настроена.

## Уведомления через бота (этап 3)

Сайт отправляет через бота те же уведомления, что показывает в колокольчике, — только
категорий из настроек «Уведомления вне сайта»: «трекер» (виды `task_*`), «заявки»
(`registration_*`, `block_application*`, `block_request*`) и «ПГАС» (`pgas_*`), как решает
`profile_features.delivery_category`. Другие виды в VK не уходят.

### Что уходит в VK

Решение владельца: вид события, название объекта и ссылка — без комментариев, оценок и
причин отказа. Текст — тот же, что в колокольчике сайта (`workspace.notification_text`), и
ссылка на ту же страницу:

```
Изменён статус задачи: Подготовить зал
https://profkom.example/tasks/3f2a…
```

- Ссылка — `PUBLIC_SITE_URL` и путь, который открывает уведомление на сайте:
  `bot_api.ROUTES` повторяет `targetRoute` из `frontend/src/utils/routes.ts`, а тест
  сравнивает их списки целей. Идентификатор кодируется как `encodeURIComponent`. Без цели
  уведомления или с незнакомой целью — главная страница (`/`).
- `PUBLIC_SITE_URL` — настройка `backend/.env`, адрес сайта для людей: `http(s)://хост[/путь]`
  без параметров, `/` в конце сайт убирает; по умолчанию — `FRONTEND_URL`. При
  `APP_ENV=production` и включённой интеграции адрес (свой или `FRONTEND_URL`) — только
  `https://`, иначе запуск backend останавливается. Значение не по формату останавливает запуск
  всегда.
- Текст длиннее 4000 символов сайт обрезает с «…», ссылку не трогает.

### Когда сайт ставит уведомление в очередь

Очередь — существующая таблица `notification_delivery_events`, канал `vk`. Строку ставит
`profile_features.collect_delivery_event` в той же транзакции, что и уведомление на сайте: его
вызывает `emit`, а решения по своей регистрации и заявке в блок заявитель получает прямым
вызовом. Строка `pending` ставится, если одновременно:

- интеграция включена;
- у получателя в настройках включён VK для категории уведомления;
- VK привязан и сообщения сообщества разрешены: `users.bot_link_state` — `ok`,
  `token_missing` или `token_invalid` (токен для сообщений не нужен).

Иначе при включённой интеграции строки канала `vk` нет. Каналы почты и Telegram ведут себя как
раньше (`not_connected`). При выключенной интеграции всё как до этапа 3: включённый в
настройках VK даёт строку `not_connected`, бот её не получает.

**VK по умолчанию.** При первой привязке аккаунта (у него ещё не было строки `bot_links`)
подтверждение включает VK для «трекера» и «заявок» в настройках аккаунта в той же
транзакции; остальные значения не меняются, строка настроек создаётся при необходимости. Если
настройки изменились, их `revision` растёт: открытая форма со старой версией получит 409.
Повторная привязка (другой VK или тот же) и повтор подтверждения настройки не трогают:
выключенное человеком остаётся выключенным.

### Состояния строки канала `vk`

| `state` | Значит |
| --- | --- |
| `pending` | Ждёт отправки; `next_attempt_at` — не раньше какого времени |
| `sent` | VK принял сообщение (`vk_message_id`, `sent_at`) |
| `denied` | VK ответил 901: сообщения сообщества запрещены |
| `failed` | Отправка не удалась окончательно (`error_code`) |
| `cancelled` | При выдаче оказалось, что отправлять нельзя: нет доступа к объекту, аккаунт не действует |
| `expired` | Не отправлено за 24 часа |

### Выдача в `GET /work`

- До `limit` строк `pending` канала `vk`, у которых `next_attempt_at` прошло, созданных не
  раньше чем 24 часа назад, по `created_at` (при равенстве — по `delivery_id`). Частичный
  индекс `ix_delivery_vk_pending` по `pending`-строкам: холостой опрос — один индексный запрос.
- `peer_id` — текущий `vk_user_id` привязки: если человек перепривязал VK, сообщение уйдёт на
  новый. `created_at` — время уведомления, ISO 8601 UTC с `Z`.
- Строки, где сейчас нельзя отправить по дешёвым причинам — привязки нет, сообщения
  запрещены, VK в настройках выключен (или строка настроек не читается), — отсеивает тот же
  запрос: они не занимают места в выдаче и ждут. Если человек исправит это в течение 24 часов,
  уведомление уйдёт.
- Текст и доступ к объекту сайт проверяет при выдаче тем же кодом, что и ленту колокольчика
  (`workspace.notification_views`, по одному разу на получателя в выдаче; уведомление
  находится по `(user_id, event_key)`). Строка не выдаётся, а ближайший отчёт помечает её
  `cancelled`, если:
  - аккаунт не действует: в архиве, удалён или заблокирован. Заявитель, ожидающий
    регистрации, действует: решение по заявке ему уходит;
  - колокольчик показал бы `access_revoked` — доступа к объекту больше нет;
  - самого уведомления на сайте уже нет.
- Такие строки сайт держит в памяти процесса до ближайшего отчёта: `GET /work` — читающая
  единица и ничего не пишет. Пока строка ждёт отчёта, выдача её пропускает в том же запросе.
  В памяти не больше 1000 строк; остальные выдача найдёт снова. Как и счётчики попыток
  привязки, это рассчитано на один процесс uvicorn.
- `random_id` — первые 31 бит SHA-256 от `delivery_id`, но не 0 (тогда 1).

### Результаты в `POST /report`

Каждый результат засчитывает попытку (`attempts`), сохраняет `error_code` текстом и время
(`updated_at`).

- `sent` — строка становится `sent`, сохраняются `vk_message_id` (может быть `null`) и время
  `sent_at`.
- `denied` — строка становится `denied`, а у привязки сайт ставит `messages_allowed = false`
  (время — время отчёта), как при событии `message_deny`: если у привязки сохранено более
  позднее время, значение не меняется. `users.bot_link_state` пересчитывается в той же
  транзакции (`save_link`).
- `failed` с `retryable: true` — строка остаётся `pending`, `next_attempt_at` — через 1, 5, 30,
  120 минут после 1–4-й неудачи; пятая неудача — `failed`. С `retryable: false` — сразу
  `failed`. Доставку с неверными полями бот возвращает как `failed`, `error_code: "invalid"`,
  `retryable: false`.
- Результат для строки, которая уже не `pending`, или для неизвестного `delivery_id` сайт
  пропускает: повтор отчёта ничего не меняет. Из двух результатов одной строки в одном
  отчёте действует первый. Незнакомый `status` сайт пропускает.
- Бот отчитывается только о доставках, которые пытался отправить. Строка без результата
  остаётся как была, без засчитанной попытки, и выдаётся снова.
- Результаты применяются до отметки `cancelled`: результат строки, которую выдача уже держит,
  важнее отмены.
- Чистка раз в час (вместе с чисткой ошибок): `pending` старше 24 часов становятся `expired`.

### Бот

- Доставки отправляет поток `site-sync` через отдельную сессию VK с токеном сообщества: свой
  лимит частоты (не больше 4 запросов в секунду), не общий с ответами в ЛС и Long Poll. Один
  `messages.send` на доставку, с `random_id` с сайта и `dont_parse_links=1`.
- Ошибки VK: 901 — `denied`; 18, 113, 900, 902 (отказы по конкретному пользователю) —
  `failed`, `retryable: false`; 1, 6, 9, 10, 14, 29, сеть и ответ не 2xx — `failed`,
  `retryable: true`. Без кода VK `error_code` — `network`, `http_<статус>`, `invalid` (доставка
  с неверными `peer_id`, `random_id` или `text`, не повторяется) или `unexpected`.
- Результаты считаются результатами прохода: отчёт уходит сразу. Неподтверждённые результаты
  бот держит до принятого отчёта и не отправляет доставку повторно, пока её результат ждёт
  отчёта. О доставках, до которых проход не дошёл, бот не отчитывается.
- Итоги доставок с запуска процесса бот передаёт в `counters` heartbeat: `deliveries_sent`,
  `deliveries_denied`, `deliveries_failed`.

## Рассылки (этап 4)

Решения владельца: рассылку отправляют председатель, замы и назначенные ими отправители
(`broadcast.send`). Она уходит в ЛС бота всем одобренным аккаунтам с подключённым ботом и
дублируется уведомлением на сайте.

### Что уходит в VK

Текст рассылки, как его написал автор: 1–4000 символов после обрезки пробелов по краям,
переводы строк сохраняются. Без вложений, клавиатуры, подписи и ссылки на сайт. Бот отправляет
его с `dont_parse_links=1`, как уведомления.

### Получатели и пачки

- Список получателей фиксируется при отправке одним запросом: аккаунты с `account_state =
  active`, без блокировки, с `users.bot_link_state` — `ok`, `token_missing` или
  `token_invalid`. Для каждого сайт запоминает `vk_user_id` его привязки. Автор входит в
  список, если подходит.
- Дальше список не меняется. Кто привяжет VK позже, рассылку не получит. Кто после отправки
  перепривязал VK или ушёл в архив, получит её на запомненный VK: текст у всех одинаковый,
  лишнего такая отправка не раскрывает.
- Получатели делятся на пачки по 100 в порядке `user_id`. `batch_id` — строка, уникальная на
  сайте. `random_id` пачки — первые 31 бит SHA-256 от `batch_id`, но не 0 (тогда 1), как у
  доставок.

### Уведомление на сайте

В той же транзакции сайт ставит уведомление вида `broadcast` всем действующим аккаунтам (как
`emit`: не в архиве, без блокировки), кроме автора. Его получают и те, у кого VK не привязан.

- Текст в колокольчике — «Рассылка: » и первая непустая строка текста без пробелов по краям,
  не длиннее 100 символов (длиннее — первые 99 и «…»). Её хранит `payload` уведомления:
  `{broadcast_id, title}`; `event_key` — `broadcast:<broadcast_id>`.
- Уведомления пишет `notifications.emit_everyone`: один запрос аккаунтов и одна пакетная
  вставка, правила `emit` те же (не в архиве, без блокировки, не автор, без повтора по
  `event_key`).
- Цель — `{kind: "broadcast", id: <broadcast_id>}`, страница `/broadcasts/{id}` с полным
  текстом. `bot_api.ROUTES` и `targetRoute` получают эту цель вместе.
- В VK это уведомление не уходит: у вида `broadcast` нет категории доставки.

### Состояния

| Получатель | Значит |
| --- | --- |
| `pending` | Ждёт отправки |
| `sent` | VK принял сообщение |
| `denied` | VK ответил 901: сообщения сообщества запрещены |
| `failed` | Отправка не удалась окончательно (`error_code`) |
| `cancelled` | Рассылку отменили до отправки |
| `expired` | Не отправлено за 24 часа |

Пачка — `pending` (ждёт выдачи или повтора), `done`, `cancelled`, `expired`. Рассылка —
`sending` (есть получатели `pending`), `done` (таких нет), `cancelled` (отменена, когда они
ещё были).

### Выдача в `GET /work`

- До 5 пачек `pending` с наступившим `next_attempt_at`, созданных не раньше чем 24 часа назад, по
  `created_at` (при равенстве — по `batch_id`). Частичный индекс по `pending`-пачкам: холостой
  опрос — ещё один индексный запрос, всего два.
- `peer_ids` — запомненные VK получателей пачки в состоянии `pending`. Пачку без таких
  получателей выдача не отдаёт и держит в памяти процесса до ближайшего отчёта, как доставки,
  которые нельзя отправить: следующие опросы её пропускают, отчёт закрывает её как `done`.
- `created_at` — время отправки рассылки, ISO 8601 UTC с `Z`. Состав пачки и её `random_id` не
  меняются, пока она не подтверждена; повтор после отчёта уходит только получателям, которые
  остались `pending`, с тем же `random_id`.

### Результаты в `POST /report`

- Результат применяется к получателю пачки с этим `peer_id`, если он `pending` или
  `cancelled`: отправленное важнее отмены. Остальные результаты, неизвестные `batch_id` и
  `peer_id` сайт пропускает. Из двух результатов одного получателя в одном отчёте действует
  первый.
- Каждый применённый результат сохраняет `error_code` текстом (до 64 символов) и время.
  `sent` сохраняет `vk_message_id` (может быть `null`). `denied` также ставит
  `messages_allowed = false` у привязки этого VK, если она есть, как результат `denied`
  доставки (`save_link`). `failed` с `retryable: false` — сразу `failed`. С `retryable: true`
  получатель `pending` остаётся `pending`, а отменённый — `cancelled`: повтора не будет.
- После результатов пачка `pending`, названная в отчёте, без получателей `pending` становится
  `done`. Иначе её `attempts` растёт, `next_attempt_at` — через 1, 5, 30, 120 минут после 1–4-й
  попытки. После пятой оставшиеся `pending` становятся `failed` с последним `error_code` (из
  этого отчёта, а у получателя без результата в нём — сохранённым), а пачка — `done`. Пачка не
  `pending` (`cancelled`, `done`, `expired`) не меняется, её получатели `cancelled` — меняются.
- Пачку `pending`, которую выдача нашла без получателей `pending` (их строки удалило удаление
  аккаунта по retention), ближайший отчёт закрывает как `done` и без результатов. Отчёт без
  пачек и без таких отметок пачки не читает: отчёт только с heartbeat — по-прежнему три запроса.
- Рассылка становится `done`, когда у неё не осталось получателей `pending`, если её не
  отменили.
- Чистка раз в час: пачки `pending` старше 24 часов и их получатели `pending` — `expired`;
  рассылка без получателей `pending` — `done`.

### Отмена

`POST /api/broadcasts/{id}/cancel` переводит получателей и пачки `pending` в `cancelled`, а
рассылку — в `cancelled`. Пачку, которую бот уже взял, отмена не останавливает: её результаты
придут и будут записаны. Уведомления на сайте остаются.

### Бот

- Каждая пачка — один вызов `messages.send` с `peer_ids` через запятую, `random_id`, `message` и
  `dont_parse_links=1` через сессию доставок этапа 3. Лимит частоты общий: вместе не больше 4
  запросов в секунду. Порядок в проходе: заявки привязки, доставки, затем пачки.
- Проверка пачки: `peer_ids` — от 1 до 100 VK пользователей (целые от 1 до 2·10⁹, беседы не
  подходят), повторы убираются; `random_id` — от 1 до 2³¹−1; `text` — 1…4000 символов, не
  пустой. `batch_id` — непустая строка до 128 символов или целое; `broadcast_id` и `created_at`
  бот не проверяет. Пачку с неверными полями бот не отправляет. Получателям с верным `peer_id`
  он возвращает `failed`, `error_code: "invalid"`, `retryable: false`. Если верных `peer_id`
  нет, бот пачку пропускает без отчёта; сайт таких пачек не выдаёт.
- Ответ VK с `peer_ids` — список по получателям: `{peer_id, message_id,
  conversation_message_id}` или `{peer_id, message_id: 0, error: {code, description}}`. Бот
  принимает и `error_code`, и код числом.
  - С `message_id` больше 0 получатель — `sent`. Без ошибки и без `message_id` — тоже `sent`, с
    `vk_message_id: null`.
  - С ошибкой результат определяет та же таблица кодов, что у доставок. Код не числом —
    `unexpected` с повтором.
  - Из нескольких записей одного получателя действует первая. Записи о чужих получателях бот
    пропускает.
  - Получатель, которого нет в ответе, — `failed`, `error_code: "missing"`, `retryable: false`:
    неизвестно, ушло ли сообщение.
- Ошибка всего вызова даёт каждому получателю пачки один и тот же результат. Это код VK, сеть
  или ответ не 2xx, и результат определяет та же таблица кодов. Два исключения:
  - Код 901 на весь вызов — `failed`, `error_code: 901`, `retryable: false`, а не `denied`: по
    одному ответу сайт не снимает разрешение сообщений с сотни привязок.
  - Ответ 2xx без ошибки VK, который не прочитать (не JSON, нет `response`, не список), —
    `failed`, `error_code: "unexpected"`, `retryable: false`: VK вызов обработал, сообщение могло
    уйти. У доставок этапа 3 такой ответ пока считается сетевой ошибкой с повтором: у одиночной
    отправки повтор с тем же `random_id` VK не дублирует.
- Пауза после ошибки всего вызова, которую стоит переждать (1, 6, 9, 10, 14, 29, сеть, не 2xx),
  общая для доставок и пачек. Ошибки отдельных получателей паузы не дают.
- Время прохода: доставки — первые 20 секунд, новая пачка начинается, только пока с начала
  прохода прошло меньше 40 секунд. Ждущая заявка привязки прерывает пачки после первой пачки
  прохода. Отметка здоровья `site` — после каждой пачки.
- Пачку, чьи результаты ждут принятого отчёта, бот повторно не отправляет, как доставки. В
  одном отчёте — не больше 10 пачек. Неотправленных в отчёт пачек бот держит не больше 10, ещё
  10 — в неподтверждённом отчёте; сверх этого он ждёт сайт. При остановке бот заканчивает
  текущую пачку, следующую не начинает и передаёт результаты последним отчётом.
- Итоги по получателям с запуска процесса — в `counters` heartbeat: `broadcasts_sent`,
  `broadcasts_denied`, `broadcasts_failed`. Тексты рассылок и получатели в журнал бота не
  попадают: одна строка INFO на проход со счётчиками.

## Консоль бота (этап 5)

Решения владельца: консоль видят и ей управляют мастер блока `IT` и назначенные им
сопровождающие (`bot.console.view`, `bot.console.operate`), председатель её не видит.
Обновление и откат идут через канал `deploy.sh request` бота с его ограничениями (решение 0008
бота).

### Команды

| `kind` | `args` | Что делает бот |
| --- | --- | --- |
| `restart` | `{}` | Передаёт `done` и, когда сайт принял отчёт, останавливается штатно (как по SIGTERM, с последним heartbeat `stopping: true`) с кодом 0. Контейнер поднимает Docker (`restart: unless-stopped`). Без надзора (локальный запуск) бот просто останавливается |
| `logs` | `{lines, level, contains}` | Последние записи `Logs/herebot.log` (с ротированными файлами) |
| `updates_check` | `{}` | Запрос `check` в `deploy.sh request` |
| `update` | `{version}` | Запрос `update` до `version` |
| `rollback` | `{version}` | Запрос `rollback` на `version` |

- `logs`: `lines` — 1…2000, по умолчанию 200: сколько записей (запись с traceback — одна).
  `level` — `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` или `null`: записи не ниже этого
  уровня. `contains` — 1…100 символов или `null`: подстрока без учёта регистра в любом месте
  записи.
- `update`, `rollback`: `version` — `X.Y.Z`, версия, которую человек видел в консоли
  (`updates.check.target` для обновления и `updates.check.previous` для отката).
- `command_id` — 32 строчные hex-цифры. Для `updates_check`, `update` и `rollback` это и `id`
  запроса в `update-requests/`: один и тот же `command_id` не даёт второго запроса серверу.
- `requested_by` — `{user_id, vk_user_id, name}`: аккаунт сайта, VK его привязки (или `null`)
  и его имя на сайте. Для запросов серверу `requested_by` в файле запроса — этот `vk_user_id`.

Состояния команды на сайте:

| Состояние | Значит |
| --- | --- |
| `pending` | Создана, бот её ещё не взял |
| `running` | Бот взял её и сообщит итог позже (ждёт ответа сервера) |
| `done` | Выполнена |
| `failed` | Не выполнена (`code`, `message`) |
| `unsupported` | Бот этой версии такой команды не знает |
| `expired` | `pending` дольше 10 минут или `running` дольше 30 минут без итога |

Срок 10 минут — как у запросов `deploy.sh request`: перезапуск, заказанный при упавшем боте,
не должен сработать через час.

### Пауза отправки

`paused` в `GET /work` — консоль приостановила отправку. Пока пауза, выдача не отдаёт доставки
и пачки рассылок; очередь копится и истекает по своим правилам (24 часа). Команды выдаются. Пауза
хранится в `bot_status` и переживает перезапуск сайта и бота; снимает её только консоль.

### Обновления в heartbeat

С этапа 5 heartbeat несёт `updates` — то, что бот видит в `state/` (все поля `null`, если файла
нет или его не прочитать):

```json
{
  "remote": "on",
  "check": {"status": "available", "checked_at": "…Z", "running": "2.4.0", "target": "2.5.0",
            "newer_major": "", "blocked": "", "previous": "2.3.0", "rollback": "bot",
            "error_kind": ""},
  "changelog": {"version": "2.5.0", "from": "2.4.0", "truncated": false, "text": "…"},
  "job": {"id": "…", "source": "bot", "action": "update", "state": "ok", "phase": "done",
          "reason": "", "from": "2.4.0", "to": "2.5.0", "running": "2.5.0", "rolled_back": false,
          "started_at": "…Z", "updated_at": "…Z"}
}
```

- `remote` — `on`, `off` или `null` (`state/host`; `on` значит ещё и понятный серверу формат
  запросов). `check`, `changelog`, `job` — файлы `state/check`, `state/changelog`, `state/job`.
  Время — ISO 8601 UTC с `Z`. `changelog.text` — до 8000 символов.
- Сайт хранит `updates` в `heartbeat_json` как есть, проверяя только, что это объект и что его
  JSON в UTF-8 не длиннее 16 КиБ. Иначе сайт отбрасывает один `updates`, а остальной heartbeat
  сохраняет и отчёт принимает. Heartbeat без `updates` (бот до этапа 5) хранится как раньше, без
  этого ключа. Консоль предлагает обновление, только когда
  `check.status = available` и `target` не равен работающей версии, и откат, только когда
  `check.rollback = bot` и `previous` не равен работающей версии, — как ЛС бота.

### Выдача в `GET /work`

- `paused` — из `bot_status`; строки нет — `false`.
- `commands[]` — до 10 команд `pending` моложе 10 минут и `running` моложе 30 минут (оба срока —
  от `created_at`), старые первыми: `{command_id, kind, args, requested_by, created_at}`. Команда
  выдаётся, пока бот не сообщит итог, в том числе после `running`: так бот после перезапуска
  (например, обновлением) её не теряет. `args` — с подставленными значениями по умолчанию,
  `created_at` — ISO 8601 UTC с `Z` до секунды.
- Холостой опрос без паузы — не больше трёх SQL: состояние паузы и наличие команд одним
  запросом (строка `bot_status` по ключу и `EXISTS` по частичному индексу команд), доставки и
  пачки — как раньше. На паузе — один. Сами команды читаются, только когда они есть, ещё одним
  запросом по тому же индексу.

### Результаты в `POST /report`

- `commands` — до 20 записей `{command_id, status, code, message, output}`. `status` —
  `running`, `done`, `failed`, `unsupported`. `code` — машинная причина (`rate_limited`,
  `busy`, `disabled`, `stale`, `no_reply`, `no_log` …) до 64 символов или `null`. `message` —
  для человека, до 500 символов. Длиннее сайт обрезает. `output` — только у `logs`: у команды
  другого вида сайт его не хранит. До 128 КиБ в UTF-8; длиннее сайт обрезает с начала,
  оставляя последние записи, как бот.
- `running` применяется к `pending`. `done`, `failed`, `unsupported` — к `pending`, `running` и
  `expired`: поздний итог важнее истечения. Итог уже завершённой команды, незнакомый
  `command_id` и незнакомый `status` сайт пропускает.
- Состояние для этих правил — то, что видит консоль: `pending` старше 10 минут уже `expired`,
  даже если чистка его ещё не отметила, и `running` к нему не применяется.
- Записи одного отчёта применяются по порядку, каждая — к состоянию после предыдущих: `running`
  и итог одной команды в одном отчёте дают итог. Из двух итогов действует первый.
- Отчёт с итогами читает названные команды одним запросом и пишет изменившиеся одним `UPDATE`.
- Отчёт с итогами команд бот отправляет сразу, вместе с heartbeat: консоль видит новое
  состояние обновлений без минуты ожидания.
- Ежечасная чистка: `pending` старше 10 минут и `running` старше 30 минут — `expired`; `output`
  стирается через 24 часа после итога (`finished_at`); команды старше 30 дней удаляются,
  хранятся не больше 500 последних. Это три запроса.

### Бот

- Команды выполняются в потоке `site-sync`, по одной, после доставок и пачек. Команду, которую
  бот уже выполняет или чей итог ждёт принятого отчёта, он не начинает снова.
- `restart`: не раньше, чем сайт принял отчёт с `done`. Если штатная остановка не закончилась
  за 25 секунд, процесс выходит с кодом 1 (Docker даёт 30 секунд до SIGKILL).
- `logs`: файлы читаются с конца, не больше 4 МБ (ротация — 1 МБ и 3 старых файла). Секреты
  вычищаются так же, как в ошибках журнала. Если вывод длиннее 128 КиБ, отбрасываются самые
  старые записи и `message` об этом говорит. Нет файла журнала — `failed`, `code: "no_log"`.
- `updates_check`, `update`, `rollback` — как кнопки в ЛС бота, с теми же проверками:
  - не тот `version`, что сервер предлагает сейчас (`_offered`), — `failed`, `code: "stale"`;
  - прошлый запрос ещё без ответа, идёт задача или запрос был меньше минуты назад — `failed`,
    `code: "busy"` или `rate_limited`;
  - `requested_by.vk_user_id` нет — `failed`, `code: "no_vk"`;
  - иначе бот кладёт запрос с `id = command_id`, сообщает `running` и ждёт ответ сервера.
    `accepted` у обновления и отката и `done` у проверки — `done`, `rejected` — `failed` с кодом
    причины из `state/replies`. Сервер не взял запрос за 5 минут — `failed`,
    `code: "no_reply"`.
  - Отправленные `command_id` бот хранит в своей БД (`BotState`), чтобы после перезапуска не
    положить второй запрос, а дождаться ответа на первый.
  - Остальным владельцам бота — то же уведомление, что при запросе из ЛС, с пометкой «из
    консоли сайта» и именем с сайта. Итог задачи автору приходит в ЛС, как при запросе из ЛС.
- Пауза: при смене `paused` бот пишет одну строку INFO. Других действий пауза от бота не
  требует: работы на отправку сайт не выдаёт.
- Бот версии до этапа 5 отвечает на все команды `unsupported`.

**Этап 3:** `GET /api/profile/me/notification-preferences` и ответ `PUT` того же маршрута

запрос уже прочитал: SQL не добавляется.

**Этап 4:** рассылки (`backend/broadcasts.py`). Право проверяется первым: без
`broadcast.send` — 403 `forbidden`, в том числе при выключенной интеграции. При выключенной
интеграции `audience` и создание отвечают 404 `bot_api_disabled`, список, страницы и отмена
работают.

| Маршрут | Право | Что делает |
| --- | --- | --- |
| `GET /api/broadcasts/audience` | `broadcast.send` | `{total, reachable}`: `total` — все действующие аккаунты (не в архиве, без блокировки), автор тоже; `reachable` — сколько из них получат рассылку в VK (список получателей, как при отправке; автор — если подходит), поэтому `reachable ≤ total`. Колокольчик получают `total` − 1: все, кроме автора. Читающая единица, один запрос |
| `POST /api/broadcasts` | `broadcast.send` | `{text, idempotency_key}` → `BroadcastOut`. `text` — 1…4000 символов после обрезки пробелов по краям, иначе 422 `validation_error` с `loc: ["body", "text"]` в `fields.errors`; лишнее поле — тоже 422. `idempotency_key` — UUID или нет поля. Повтор тем же автором с тем же ключом и тем же текстом (после обрезки) возвращает ту же рассылку в её нынешнем состоянии; тот же ключ с другим текстом или от другого аккаунта — 409 `duplicate_request_key`, как у задач (GL-07). Нет ни одного получателя в VK — 409 `broadcast_no_recipients`, ничего не сохраняется. Запись в аудит |
| `GET /api/broadcasts` | `broadcast.send` | `{items: BroadcastOut[], next_cursor}`, свежие первыми, по 20 (в наборе интеграционных тестов — по 3, `api_contract.PAGE_SIZE`). Следующая страница — `?cursor=<next_cursor>`; неверный курсор — 422 `invalid_input` |
| `GET /api/broadcasts/{id}` | действующий аккаунт | `BroadcastOut`. Без `broadcast.send` поле `counts` — `null`. Нет рассылки — 404 `not_found` |
| `POST /api/broadcasts/{id}/cancel` | `broadcast.send` | → `BroadcastOut`, отменяет любой обладатель права. Нет рассылки — 404 `not_found`; рассылка не `sending` — 409 `broadcast_not_sending`. Запись в аудит |

`BroadcastOut`: `{broadcast_id, text, author, created_at, state, cancelled_at, counts}`.
`author` — `{user_id, display_name, avatar_url}` или `null` после удаления аккаунта автора.
`created_at`, `cancelled_at` — ISO 8601 UTC с `Z` до секунды. `state` — `sending`, `done`,
`cancelled`. `counts` — `{total, pending, sent, denied, failed, cancelled, expired}` по
получателям в VK.

Аудит: `target_kind = "broadcast"`, `target_id` — `broadcast_id`, автор записи — отправитель.
Причина `broadcast_send` — `{state: "sending", recipients, notified}` (получателей в VK и
уведомлений на сайте), `broadcast_cancel` — `{state: "cancelled", cancelled}` (сколько
получателей отменено).

Отправителей назначают председатель и замы на той же странице через маршруты этапа 1
`/api/broadcasts/senders`.

**Этап 5:** консоль бота (`backend/bot_console.py`; там же теперь `status` этапа 1). Право
проверяется первым (403 `forbidden`). При выключенной интеграции пауза и создание команды
отвечают 404 `bot_api_disabled`, чтение работает.

| Маршрут | Право | Что делает |
| --- | --- | --- |
| `GET /api/bot/console/status` | `bot.console.view` | Как на этапе 1, плюс `paused`, `paused_at`, `paused_by` (`{user_id, display_name, avatar_url}` или `null`; без паузы оба `null`) и `queue: {deliveries, batches}` — все строки канала `vk` и пачки рассылок в `pending`, в том числе ждущие повтора. `heartbeat.updates` — как прислал бот; без него ключа нет |
| `PUT /api/bot/console/pause` | `bot.console.operate` | `{paused: bool}` → ответ `status`. Пауза создаёт строку `bot_status`, если её ещё нет. Повтор ничего не меняет и в аудит не пишется. Аудит `bot_pause` и `bot_resume` |
| `POST /api/bot/console/commands` | `bot.console.operate` | `{kind, args, idempotency_key}` → `CommandOut`, см. ниже |
| `GET /api/bot/console/commands` | `bot.console.view` | `{items: CommandOut[], next_cursor}`, свежие первыми, по 20; `output` в списке — `null`. Неверный курсор — 422 `invalid_input` |
| `GET /api/bot/console/commands/{id}` | `bot.console.view` | `CommandOut` с `output`. Нет команды — 404 `not_found` |

Создание команды:

- `kind` и `args` — как в «Консоль бота», лишнее поле или неверное значение — 422
  `validation_error`, `loc` — путь к полю (`["body", "args", "lines"]`). `args` у `logs` можно не
  передавать целиком или частично — значения по умолчанию: 200 записей, любой уровень, без
  подстроки. У `restart` и `updates_check` `args` — `{}` или нет поля. Сохраняются и уходят боту
  `args` со значениями по умолчанию.
- Бот не `online` — 409 `bot_offline`: команда до него не дойдёт.
- Уже есть `pending` или `running` команда того же вида — 409 `bot_command_pending`; `update` и
  `rollback` считаются одним видом.
- `updates_check`, `update`, `rollback` без привязанного VK у автора — 409
  `bot_console_vk_required`: серверу нужен VK ID автора запроса.
- `restart` раньше чем через 2 минуты после прошлого `restart` (по его `created_at`, в любом
  состоянии) — 429 `bot_command_rate_limited`.
- `idempotency_key` — UUID или нет поля. Повтор тем же автором с тем же ключом и теми же
  `kind` и `args` (после значений по умолчанию) возвращает ту же команду в её нынешнем
  состоянии; иначе — 409 `duplicate_request_key`.
- Порядок проверок: право, интеграция, повтор по ключу (он отвечает, даже если бот уже не на
  связи), затем `bot_offline`, `bot_command_pending`, `bot_console_vk_required`,
  `bot_command_rate_limited`. Отказ ничего не сохраняет.
- Боту в `requested_by` уходят `user_id` автора, VK его привязки в момент создания (или `null`)
  и `display_name` автора на сайте — тот же, что в `requested_by` ответа.
- Запись в аудит `bot_command`: `{kind, args}`.

`CommandOut`: `{command_id, kind, args, state, code, message, requested_by, created_at,
updated_at, finished_at, has_output, output}`. `requested_by` — `{user_id, display_name,
avatar_url}` или `null` после удаления аккаунта. `state` при чтении учитывает сроки: `pending`
старше 10 минут и `running` старше 30 минут показываются как `expired`, даже если чистка их ещё
не отметила. `has_output` — есть ли сохранённый `output` и прошло ли меньше 24 часов с итога:
позже `output` — `null`, даже если чистка его ещё не стёрла. Времена — ISO 8601 UTC с `Z` до
секунды. Ответ на создание — тоже `CommandOut`.

Аудит этапа 5: `target_kind = "bot"`, `target_id` — `command_id` или `pause`, автор записи —
автор команды или паузы. У паузы — `{paused: false}` → `{paused: true}` и наоборот.

## Хранение на сайте

**Этап 1:** новые таблицы, только добавления.

- `bot_status` — одна строка: `boot_id`, `report_id`, `started_at`, `last_seen_at` (время
  последнего отчёта), `heartbeat_json`, `updated_at` (когда сохранён heartbeat), `cleaned_at`
  (последняя чистка `bot_errors`).
- `bot_errors` — группа на `fingerprint`: `level`, `logger`, `location`, `message`,
  `traceback`, `count`, `first_at`, `last_at`; индекс по `last_at`.
  - Сайт хранит не больше 500 групп и не старше 30 дней; остаются группы с самым поздним
    `last_at`.
  - Чистка — внутри отчёта: не чаще раза в час, а также сразу, если отчёт добавил новые
    группы. Так лимит в 500 групп соблюдается и между чистками.
- Аккаунтов сайта эти таблицы не называют.

**Этап 2:**

- `bot_links` — привязка аккаунта: `user_id` (ключ), `vk_user_id` (уникальный),
  `messages_allowed`, `messages_at`, `token_status`, `token_at`, `linked_at`, `updated_at`.
- `bot_link_codes` — коды: `code_hash` (ключ), `user_id`, `created_at`, `expires_at`,
  `used_at`, `used_vk_user_id`; индексы по `user_id` и `expires_at`. Новый код удаляет прочие
  коды аккаунта и все истёкшие.
- `users.bot_link_state` — копия `state`, добавленный столбец, `NULL` значит `none`. Пишет
  обе таблицы одна функция `bot_api.save_link`.
- Архив аккаунта привязку не снимает. Удаление по retention (`bot_api.anonymize`) снимает
  привязку и коды и стирает VK (`vk_user_id`) в записях аудита аккаунта.

**Этап 3:** добавленные столбцы `notification_delivery_events` (на старой базе их добавляет
`database._ensure_sqlite_delivery_queue`, повторный запуск ничего не меняет):

- `attempts` — сколько результатов бот прислал по строке, по умолчанию 0;
- `next_attempt_at` — с какого времени строку `pending` можно выдать. Новая строка любого
  канала получает время создания: так все строки одной вставки называют одни столбцы и
  уходят одним запросом;
- `sent_at`, `vk_message_id`, `error_code` (текст), `updated_at` — последнее изменение.

Времена в этой таблице — ISO 8601 UTC с микросекундами и `+00:00`, как прежний `created_at`
(`registration.now`): сравниваются как текст. В ответах бота — с `Z` до секунды. Частичный
индекс `ix_delivery_vk_pending` по `(next_attempt_at, created_at)` для строк `channel = 'vk'
AND state = 'pending'`; уникальный индекс `(user_id, event_key, channel)` остаётся.

Строки доставок входят в retention аккаунта, как и сами уведомления: при удалении по
retention `profile_features.anonymize` удаляет строки аккаунта всех каналов. Архив их не
трогает, но строки `pending` архивного аккаунта выдача отменяет (`cancelled`).

**Этап 4:** новые таблицы (`bot_models.py`). На старой базе их создаёт `create_all` при
запуске backend, повторный запуск ничего не меняет.

- `broadcasts` — `broadcast_id` (UUID), `author_user_id` (`NULL` после удаления аккаунта автора
  по retention), `text`, `state`, `idempotency_key` (уникальный индекс
  `ux_broadcasts_idempotency_key`, может быть `NULL`), `request_hash` — SHA-256 запроса с ключом,
  как у задач (`request_keys`), `created_at`, `updated_at`, `cancelled_at`,
  `cancelled_by_user_id`. Индекс `ix_broadcasts_list` по `(created_at, broadcast_id)` — для
  списка.
- `broadcast_batches` — `batch_id` (ключ; `<broadcast_id>-0000`, `-0001` … по порядку
  получателей), `broadcast_id` (индекс), `state`, `attempts` (сколько отчётов назвали пачку,
  пока она была `pending`), `next_attempt_at`, `created_at` (время рассылки), `updated_at`.
  Частичный индекс `ix_broadcast_batches_pending` по `(next_attempt_at, created_at)` для строк
  `state = 'pending'`.
- `broadcast_recipients` — ключ `(broadcast_id, user_id)`; `batch_id` (индекс), `vk_user_id`,
  `state`, `vk_message_id`, `error_code` (текст), `updated_at`.
- Времена в этих таблицах — ISO 8601 UTC с микросекундами и `+00:00`, как в очереди этапа 3, но
  всегда с дробной частью: сравниваются как текст. В ответах — с `Z` до секунды.
- Удаление аккаунта по retention (`bot_api.anonymize`) удаляет его строки получателя и стирает
  `author_user_id` и `cancelled_by_user_id` в его рассылках; текст остаётся. Архив их не
  трогает.

**Этап 5:**

- `bot_commands` (`bot_models.py`, на старой базе её создаёт `create_all`) — `command_id` (ключ,
  32 hex), `kind`, `args_json`, `state`, `code`, `message`, `output` (стирается через 24 часа),
  `requested_by_user_id`, `requested_vk_user_id`, `requested_name`, `idempotency_key`
  (уникальный индекс `ux_bot_commands_idempotency_key`, может быть `NULL`), `request_hash`,
  `created_at`, `updated_at`, `finished_at` (когда пришёл итог). Хранятся 30 дней и не больше 500
  последних.
  - Частичный индекс `ix_bot_commands_open` по `(created_at, command_id)` для строк `state IN
    ('pending', 'running')`: по нему и проверка в холостом опросе, и чтение команд по порядку.
    С одним `created_at` план для чтения по порядку выбирал индекс списка.
  - Индекс `ix_bot_commands_list` по `(created_at, command_id)` — для списка.
  - Времена — как у рассылок этапа 4: ISO 8601 UTC с микросекундами и `+00:00`, сравниваются как
    текст.
- `bot_status` получает столбцы `paused` (по умолчанию `false`), `paused_at` (с `Z` до секунды,
  как прочие времена этой строки), `paused_by_user_id`. Снятие паузы стирает `paused_at` и
  `paused_by_user_id`: они называют действующую паузу. На старой базе столбцы добавляет
  `database._ensure_sqlite_bot_console` по образцу этапа 3, повторный запуск ничего не меняет.
- Удаление аккаунта по retention стирает в его командах `requested_by_user_id`,
  `requested_vk_user_id` и `requested_name`, а в `bot_status` — `paused_by_user_id`, если пауза
  его. Архив их не трогает.

## Бюджет производительности

| Что | Предел |
| --- | --- |
| Холостой `GET /work` | Читающая единица; на этапе 1 без SQL, на этапе 3 — один запрос по частичному индексу `ix_delivery_vk_pending`, с этапа 4 — два (ещё индекс пачек рассылок; на стенде 2 SQL, 2–3 мс); p95 < 5 мс локально |
| `POST /report` только с heartbeat | Не больше 3 SQL (`BEGIN IMMEDIATE`, чтение и запись `bot_status`, проверено тестом); блокировка записи p95 < 5 мс локально. Повтор отчёта — 2 SQL. Ежечасная чистка добавляет 4: две чистки ошибок, отметку `expired` доставок (этап 3) и пачек рассылок (этап 4, `UPDATE … RETURNING`; если пачки истекли, ещё по запросу на их получателей и рассылки) |
| Частота записей | Heartbeat раз в 60 секунд плюс отчёты с результатами: порядка 1,5–3 тысяч коротких транзакций в сутки |
| Права на страницах | Новые отношения берутся из снимков `role_assignments` и блоков, которые уже читаются на каждый запрос: 0 дополнительных SQL на страницу |
| Проверка привязки (этап 2) | Обычный маршрут и `/api/session` — 0 дополнительных SQL: состояние — в уже прочитанной строке `users` (проверено тестом и замером). `ApplicationOut` добавляет одно чтение `bot_links`, очередь рецензента — одно на страницу |
| `GET /api/bot-link/me` | Читающая единица, не больше 2 SQL (аккаунт и одно чтение привязки с кодом); её опрашивают раз в 3 секунды |
| `POST /api/bot-link/code`, `links/confirm` | Пишущая единица из нескольких коротких запросов по ключу и индексу, без обращений к VK: код — 4 SQL с `BEGIN`, подтверждение — около 10, повтор — 4; уведомление рецензентов добавляет запросы `registration_submitted` |
| События в отчёте | Привязки читаются одним запросом на отчёт (`vk_user_id IN (...)`), пишутся только изменившиеся: отчёт с теми же фактами — на 1 SQL больше пустого |
| Очередь уведомлений (этап 3) | `emit` не добавляет чтений: состояние привязки — в строках `users`, которые он уже читает; строка очереди — та же вставка, что и раньше. Тест сравнивает число SQL `emit` и смены статуса задачи с интеграцией и без; на стенде смена статуса задачи с 48 получателями — 613 SQL до этапа 3 и после |
| `GET /work` с доставками | Читающая единица, без блокировки записи. Холостой — один запрос по `ix_delivery_vk_pending` (проверено тестом и `EXPLAIN QUERY PLAN`; на стенде 1 SQL, 2–3 мс). С доставками — тот же запрос строк вместе с привязками, аккаунтами и настройками, одно чтение уведомлений и проверка доступа колокольчика по одному разу на получателя: для задач — около 7 SQL на получателя. На стенде 50 доставок 10 получателям — 77 SQL, 16–30 мс |
| Отправка рассылки (этап 4) | Пишущая единица: список получателей с номерами пачек — один `INSERT … SELECT`, пачки — одна пакетная вставка, уведомления на сайте — один запрос аккаунтов и одна пакетная вставка, без запросов на получателя: число SQL не зависит от числа получателей (тест: 3 и 300). На стенде с 1000 добавленными аккаунтами с ботом (1019 действующих) — 17 SQL на запрос, блокировка записи 21–28 мс, запрос 22–31 мс. Отмена рассылки с 1000 получателями `pending` — 16 SQL, блокировка 14 мс |
| `GET /work` с пачками | Холостой — два запроса по частичным индексам доставок и пачек (проверено тестом и `EXPLAIN QUERY PLAN`, в том числе с пачками, которые держит память). Пачки читаются вторым из них вместе с текстом рассылки (по ключу); с пачками добавляется один запрос — их получатели `pending` по индексу `batch_id`: всего три (тест: 5 пачек по 100; на стенде 3 SQL, 4–9 мс) |
| Результаты пачек в отчёте | Пачки и их получатели `pending` и `cancelled` читаются двумя запросами на отчёт; получатели и пачки пишутся одним `UPDATE` (executemany) каждые, рассылки — одним `UPDATE`. Отчёт с 5 × 100 результатами — 8 SQL вместе с `BEGIN` и `bot_status` (тест); `denied` добавляет 3: чтение привязок с аккаунтами, запись привязок и `users.bot_link_state`. На стенде 5 × 100 `sent` — 8 SQL, блокировка записи 14 мс; 5 × 100 вперемешку с повторами и 5 `denied` — 10 SQL (пачки остаются `pending`, рассылки не пересчитываются), 14 мс |
| Страницы рассылок | Список — постоянное число запросов на страницу: авторы с аватарами одним чтением, `counts` одним `GROUP BY` по рассылкам страницы (тест: 1 и 20 рассылок разных авторов — одинаково). `audience` — один запрос по аккаунтам с привязками. На стенде список из 3 рассылок по 1000 получателей — 8 SQL на запрос, 5–13 мс; рассылка для обычного аккаунта — 7 SQL; `audience` — 5 SQL, 3–10 мс. Колокольчик и страницы сайта не дорожают: `/api/session`, главная, счётчик и лента колокольчика — 17/19, 24/46, 2 и 2/17 SQL (участник/председатель) и до, и после рассылок (тест сравнивает `/api/session` и счётчик) |
| Консоль (этап 5) | Холостой `GET /work` без паузы — не больше трёх SQL: пауза и наличие команд одним запросом по `bot_status` и частичному индексу команд, затем доставки и пачки; на паузе — один (и ещё один, если есть команды). Отчёт с итогами команд — на два SQL больше (чтение и запись команд). `GET /api/bot/console/status` — постоянное число запросов, счётчики очереди — по частичным индексам. Создание команды — пишущая единица из нескольких коротких запросов, без обращений к боту |
| Результаты доставок в отчёте | Строки читаются одним запросом на отчёт и пишутся одним `UPDATE` (executemany); `denied` добавляет одно чтение привязок с аккаунтами и их запись. Отчёт с 50 результатами — 8 SQL (тест; на стенде 11 вместе с ежечасной чисткой, 18 мс). Отметка `cancelled` для строк, которые держит выдача, — один `UPDATE` |

## Безопасность

  открывает. Доставка этапа 3 несёт только VK получателя и текст колокольчика со ссылкой: вид
  события и название объекта, без комментариев, оценок и причин отказа.
- Пачка рассылки (этап 4) несёт только VK получателей и текст, одинаковый для всех. Кто
  получил рассылку, видят только обладатели `broadcast.send`, и только в виде счётчиков.
- Журнал переписки бота на сайт не передаётся. Журнал по запросу консоли — только
  `herebot.log`.
- Обновление и откат из консоли (этап 5) идут через тот же канал `deploy.sh request`, что из
  ЛС бота, с теми же ограничениями. Автор запроса — VK ID привязанного аккаунта сайта.
  Владельцы бота получают такое же уведомление о запросе, как при запросе из ЛС.

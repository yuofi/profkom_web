## A01 · P2 · Старые административные экраны используют несовместимые команды

Уверенность: высокая. Требования: FE-01, FE-02, FE-04; AUTH-02, ROLE-06; контракт PATCH профиля (строки 2260–2261), исключение создания блоков (BLOCK-01).

Путь `admin/:tab` остаётся в [App.tsx](../src/App.tsx):250–252 под `ExtendedRoute`, который допускает `review_registrations` ([wrappers.tsx](../src/pages/Wrappers/wrappers.tsx):22–24). [AdminPage.tsx](../src/pages/Admin/AdminPage.tsx):18–27 открывает старые панели:

- [UsersManagement.tsx](../src/pages/Admin/panels/UsersManagement.tsx):64–75 отправляет «Одобрить» через PATCH профиля с `in_profcom: true`, вместо версии и команды одобрения регистрации.
- [BlocksManagement.tsx](../src/pages/Admin/panels/BlocksManagement.tsx):141–144 напрямую добавляет ID в `arr_of_human`. Это не двухэтапная заявка HR → мастер. Панель также предполагает старые `master: string` и `arr_of_human`; при нормализованном Block падает при рендере (в частности, строки 305–307). Сохранены создание/удаление блока.
- [EventsManagement.tsx](../src/pages/Admin/panels/EventsManagement.tsx):8–9,49–70 использует фиксированный список мероприятий/ролей и PATCH `events_roles`, вместо независимых назначений с ID и capabilities.

Подтверждение: A01a нажимает одобрение и фиксирует неправильный PATCH; A01b открывает панель блоков с согласованным DTO и фиксирует ошибку рендера. Прямое изменение состава и JSON ролей подтверждены кодом, отдельные команды не исполнялись.

Исправление: заменить старые входы регистраций/блоков/мероприятий переходами в современные экраны или перевести их на те же компоненты и команды; сохранить необходимое управление гайдами. Убрать несовместимые действия и создание блоков из доступного интерфейса.

Критерий закрытия: прямые старые URL работают с новыми DTO; одобрение идёт только через регистрацию с revision; вступление — через согласованный процесс; роли — через назначения по ID. Из этих экранов нет PATCH привилегий профиля, `events_roles` или `arr_of_human`.

## A02 · P2 · Старые формы неправильно разбирают структурированные ошибки API

Уверенность: высокая. Требования: FE-01 (понятные отказы/конфликты), общий формат ошибок.

[Form.tsx](../src/components/Form/Form.tsx):53–62 присваивает `data.detail` в текст ошибки. При `detail: {code, message, fields}` настоящий `AxiosError` приводит к передаче объекта в React и падению формы. Если ошибка адаптера не проходит `instanceof AxiosError`, теряется серверное сообщение и показывается общий `Request failed with status code 422`. Это касается сохранённых форм `useForm`, включая вход и ПГАС; новый `ActionForm` уже использует нормализацию.

Подтверждение: A02a — потеря сообщения на ошибке адаптера; A02b — падение на настоящем `AxiosError` со структурированным `detail`.

Исправление: применить общий `normalizeApiError` и обработку ошибок полей в старом `useForm`; не использовать объект как текст и не полагаться только на идентичность конструктора ошибки.

Критерий закрытия: достижимые старые формы при 403/409/422 показывают строковое сообщение и ошибки полей, сохраняют ввод и не падают.

## A03 · P2 · Вход обходит проверку состояния сессии, возврат ко входу не завершает сессию

Уверенность: высокая для порядка запросов и очистки; сбой входа воспроизведён при 403 профиля. Требования: FE-01, AUTH-01; сохранение login/refresh/logout/VK, до одобрения только состояние регистрации.

[Greeting.tsx](../src/pages/Greeting/Greeting.tsx):81–87 после получения токена сначала обязательно читает `/profile/me`, затем обновляет `/session` и переходит дальше. Аналогичный порядок у VK (107–115). При 403 собственного профиля pending-аккаунта успешная аутентификация заканчивается ошибкой формы: чтение состояния регистрации не начинается. Ошибки VK остаются только в console.

В [SessionPages.tsx](../src/pages/Workspace/SessionPages.tsx):62–67 действие «Ко входу» удаляет лишь access-cookie; не вызывает существующий logout и не очищает частный кеш. Серверная refresh-сессия этим не завершается.

Подтверждение: A03a фиксирует отсутствие `/session` после отказа профиля; A03b — отсутствие logout и сохранение кеша после клика.

Исправление: общий переход после обычного входа/регистрации/VK с очисткой частного кеша и чтением `/session` первым; профиль читать только для активного аккаунта. Для pending/rejected использовать общий полноценный выход, выводить пользователю ошибки VK.

Критерий закрытия: pending/rejected после входа попадает на состояние регистрации без запросов рабочих данных; активный — на рабочий экран. Возврат ко входу завершает серверную сессию и очищает кеш; refresh не возвращает прежний аккаунт.

## A04 · P2 · У руководителей нет обычного входа в формы заслуг; неверная проверка доступа

Уверенность: высокая. Требования: FE-02 (строки 94–96), формы особых заслуг главорга и волонтёрства мастера/ответственного, объектные capabilities без доступа к расчёту.

[WorkspaceLayout.tsx](../src/components/Workspace/WorkspaceLayout.tsx):46–48 показывает сезоны только при `view_summary`. Из карточки блока/мероприятия/подмероприятия нет ссылки на форму учёта выполненной работы. Вход в неё есть со страницы сезона, до которой мастер без доступа к сводной не доходит из обычной навигации.

В [MeritPages.tsx](../src/pages/Workspace/MeritPages.tsx):389–399 чтение и сама страница требуют глобальный `create_volunteer_merit` либо `view_summary`; форма создания (425–428) — только глобальный volunteer-флаг. Объектный `create_head_merit` мероприятия сам по себе не открывает форму.

Подтверждение: A04a проверяет отсутствие перехода из блока и основной навигации для уполномоченного руководителя без сводной; A04b — отказ страницы при `create_head_merit` события без постороннего volunteer-флага.

Исправление: добавить входы из соответствующих областей с выбором допустимого сезона; допускать фактически разрешённый тип заслуги и контекст по capabilities. Не выдавать ради формы чтение рассчитанного ККР.

Критерий закрытия: мастер без `view_summary` находит и отправляет волонтёрскую запись своего блока; главорг с `create_head_merit` — свою форму без volunteer-флага. Читателю/редактору без права создание не показывается; сезон и источник верны.

## A05 · P2 · Обновление конфликтующей версии всё ещё стирает ввод в части форм

Уверенность: высокая для воспроизведения мероприятия; остальные перечисленные места требуют отдельных регрессионных сценариев. Требования: FE-01 и общий контракт revisions/409; сохранность ввода при конфликте.

В [EventPages.tsx](../src/pages/Workspace/EventPages.tsx):311–326 форма описания имеет `key={event.revision}`. После правки пользователем, конкурентного изменения, ответа 409 и нажатия «Обновить данные» форма пересоздаётся и заменяет введённый текст серверным значением. Предыдущее исправление ключей охватило задачу/отчёт/материал, но не все формы.

Сходные ключи по версии остаются в формах назначения/подмероприятия EventPages, блока MembershipPages, RegistrationForm, созвона ReportPages и управления сезоном SeasonPages, а также LeadershipPage. У части форм нет действия обновления после конфликта — его тоже надо проверить.

Подтверждение: A05 воспроизводит потерю описания мероприятия через отправку формы, 409 и явное обновление данных.

Исправление: хранить черновик независимо от revision и применять новую серверную версию явно, с возможностью сравнить/повторить отправку. Проверить все формы с таким же ключом и отсутствие действий восстановления.

Критерий закрытия: для мероприятия, блока, регистрации, созвона и сезонных форм сценарий «ввод → 409 → обновление» сохраняет введённые значения; новый expected_revision используется после явного обновления. Смена самого объекта корректно меняет форму.

## A06 · P2 · Обновление справочника скрывает поля выбранного получателя новой заслуги

Уверенность: высокая. Требования: FE-02, F05; сохранность ввода и исторических получателей.

[MeritPages.tsx](../src/pages/Workspace/MeritPages.tsx):75–88 дополняет варианты отсутствующими получателями только из уже сохранённой записи (`existing`). Для новой несохранённой заслуги выбранный человек, исчезнувший из свежего справочника, пропадает из списка полей: счётчик выбранных остаётся 1, но его часы/оценка/дата не видны. Значения внутри формы не доказаны потерянными; дефект — скрытый и недоступный для правки выбранный получатель.

Подтверждение: A06 выбирает человека, меняет справочник в QueryClient и фиксирует исчезновение индивидуальных полей при сохранённом выборе.

Исправление: удерживать снимки выбранных получателей и их черновые значения независимо от текущего справочника, помечать недоступного/архивного, удалять только по явному снятию выбора. Допустимость сохранения решает сервер.

Критерий закрытия: после выбора и ввода обновление контактов не скрывает человека и его значения; показана причина недоступности. Payload содержит ровно явно выбранные ID.

## A07 · P2 · Фото ограничено 5 MiB вместо согласованных 10 MiB

Уверенность: высокая. Требование: общий контракт файлов [CODEX_FRONTEND.md](../../CODEX_FRONTEND.md):2306.

[AvatarPicker.tsx](../src/components/Workspace/AvatarPicker.tsx):55–72 содержит текст и локальную проверку 5 MiB. Объект `File` размером 6 MiB с разрешённым JPEG MIME отклоняется до обращения к upload. Это расходится с выбранным контрактом 10 MiB; проверка реального изображения здесь не проводилась.

Подтверждение: A07 фиксирует локальную ошибку и отсутствие вызова `filesApi.upload`.

Исправление: согласовать локальную границу и подсказку с 10 MiB, сохранив ограничения MIME.

Критерий закрытия: разрешённый тип чуть меньше и ровно 10 MiB проходит к upload intent; больше 10 MiB отклоняется локально. Реальная загрузка/декодирование проверяется отдельно с API.

## A08 · P3 · Селекторы руководства не исключают неодобренного кандидата

Уверенность: высокая для обработки указанного ответа; требование одинаковой фильтрации руководства — вывод из модели действующих участников, ROLE-06 прямо проверяет pending для мастера/зама. Само назначение на сервере не проверялось.

[SessionPages.tsx](../src/pages/Workspace/SessionPages.tsx):122–128 исключает из кандидатов только действующего председателя. Контакт с `in_profcom: false`, если он присутствует в ответе/кеше, предлагается в передаче поста и назначении замов. Другие новые селекторы уже используют отбор действующих участников.

Подтверждение: A08 подаёт такой контакт в кеш и фиксирует его option в форме. Это не утверждение, что согласованный live API обязательно вернёт pending или разрешит назначение.

Исправление: применять отбор одобренных действующих участников и обрабатывать устаревший выбор. Сохранить возможность назначения действующего участника вне текущего состава области; окончательный запрет — на сервере.

Критерий закрытия: pending не предлагается при таком ответе, действующий участник вне области доступен, серверный 422 отображается без потери ввода.

## A09 · P3 · Пустой результат поиска материалов оставляет пустую область

Уверенность: высокая. Требования: понятные состояния списков, приёмка фильтров и пустых состояний.

[MaterialPages.tsx](../src/pages/Workspace/MaterialPages.tsx):72–103 фильтрует карточки, но проверяет пустоту по исходному `items.length`. При существующих материалах и несовпадающем поиске нет ни карточек, ни сообщения, ни действия сброса.

Подтверждение: A09 вводит несовпадающий запрос при непустом исходном списке и фиксирует пустую выдачу без объяснения.

Исправление: вычислять отфильтрованный список отдельно, показывать «Ничего не найдено» и сброс условий; отличать это от глобального отсутствия материалов и ошибки загрузки.

Критерий закрытия: отдельно проверены пустой исходный список, пустая фильтрованная выдача, совпадения, загрузка и ошибка; сброс возвращает доступные карточки.

## Группировка дальнейшей работы

Новые задачи — продолжение существующего плана, без ветки на каждый дефект. Обе группы начинать от актуальной локальной `dev`, интегрировать после проверки. Сейчас исправления не начаты.

После каждого A-пункта — краткий отчёт и запись подтверждения в чеклисте. Общую готовность не отмечать до закрытия обеих групп.

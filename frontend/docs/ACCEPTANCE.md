# Frontend: результаты приёмки

Срез: 2026-10-18. Реализуется контракт API 1.3 из `CODEX_FRONTEND.md`. Проверки ниже используют синтетический transport и не подтверждают готовность backend/деплоя.

## Автоматические проверки

- ESLint, TypeScript project build, production Vite build.
- Vitest: Zod, refresh/retry, контракт и переходы, роли, разделение публичных/исходных/расчётных DTO, календарь МСК, Markdown, рендер страниц с намеренно оставленными закрытыми данными в кеше.
- Курсорные списки дочитываются полностью; зацикленный cursor возвращает ошибку вместо потери записей.
- Разделы загружаются отдельно. Моки исключены из production; source maps не включены.

## Основные сценарии и доказательства

## Что нужно от backend для интеграции

1. Безопасная сессия, object capabilities и запрет рабочей области pending/archived; отсутствие скрытых полей в public DTO.
2. Совпадающие имена полей, cursor wrappers, revisions и структурированные 403/409/422.
3. Настоящий upload-intent → PUT → complete с проверкой файла, объектно защищённые временные download URLs; аватар через file_id/preset_id.
4. Реальные регистрации/заявки/категории/материалы/аватары/архивы. После каждой записи — повторный GET и конкурентный сценарий.
5. Согласованный API чтения предыдущих версий закрытой сводной и аудита исправлений. До этого единственный связанный подпункт чеклиста остаётся открытым.
6. Настоящий XLSX с двумя листами и серверными значениями. Моковая выгрузка — только заглушка транспорта, её нельзя выдавать за готовый файл расчёта.

Критерий закрытия каждого интеграционного пункта — успешные настоящие запросы, повторное чтение, проверка второй ролью и отрицательная проверка доступа. Производственный деплой не выполнялся.

## Браузерная проверка

- Организатор: свои задачи → результат с текстом/ссылкой → «На проверке», после повторного GET видны первая сдача и серверная дата. Часов/оценки/критериев в интерфейсе нет.
- Профиль: выбран локальный аватар «Лист», получено подтверждение сохранения; крупное изображение открывается, Escape закрывает и возвращает фокус.
- Мобильный iframe 390×844: длинный заголовок задачи переносится, меню открывается/закрывается при переходе; календарь отображается списком с московским временем и сезоном.
- Настольный iframe 1280×1200: сводная показывает все столбцы, несколько текущих/прошлых отметок, нулевую строку и «Уже исключён»; широкая таблица не ломает навигацию.
- Мероприятия: через форму создано подмероприятие и прочитано после инвалидации (пункт 4).
- Pending: проверено отсутствие рабочего меню (пункт 3); отдельный DOM-тест подтверждает, что запускается только GET /session.

Скриншоты локальной проверки сохранены вне репозитория в `/private/tmp/profkom-frontend-*-proof.png`. Временные HTML-harness файлы удаляются перед фиксацией изменений.

## Итоговые проверки

79 тестов в восьми файлах успешно. ESLint и TypeScript/Vite build успешно. Production JS проверен на отсутствие mock transport, DEV role storage и synthetic score markers; source maps отсутствуют. Изменения backend и производственный деплой не выполнялись. Ещё не подтверждены real API, S3/VK, реальные XLSX и серверный аудит; открытые пункты сохранены в CHECKLIST.md.

Отказ сервиса дополнительно проверен браузером через DEV scenario: видны «Сервис временно недоступен» и «Обновить данные», успешные записи не подставляются. После проверки возвращён normal-сценарий. Даты мероприятий доступны для ввода МСК и передачи UTC; принадлежность к сезону меняется только отдельной командой.

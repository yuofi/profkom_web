## Вывод

Основные процессы работают с настоящим локальным API и сохранением в SQLite. Полностью согласованной связку пока считать нельзя: обнаружены **шесть групп расхождений**, из них пять влияют на доступность или поведение интерфейса, одна — на точность TypeScript-контракта. Это уточняет прежнюю backend-приёмку: наличие реализованного обработчика и успешные отдельные тесты не доказывают доступность сценария в реальном интерфейсе.

Блокеров backend для исправления этих пунктов нет. В двух случаях требуется дополнить проекцию capabilities; API истории сводных уже реализован. Внешние VK/S3 и развёртывание остаются отдельным уровнем приёмки.

## Найденные расхождения

### INT-01 · P1 · Очередь оставшейся работы закрыта интерфейсом для руководителей

**Основание:** FE-02, TASK-09/10, просмотр нерешённой работы перед закрытием сезона.

**Доказательство:** мастер и председатель получают `200` на `tasksApi.unresolved()`; в ответе есть реальное назначение с `assignee_unavailable_reason=left_scope`. В `/session.capabilities` нет `view_unresolved_assignments`. `TaskPages.tsx:788` отключает запрос очереди и показывает «Нет доступа к очереди». На рабочем экране председателя при этом есть счётчик и ссылка «Разобрать назначения», ведущая на запрещённую самим фронтом страницу. Воспроизведено также браузером.

**Причина:** `backend/access.py:9` не включает эту возможность в глобальную проекцию, хотя объектные карточки блоков/подмероприятий её возвращают. Frontend проверяет именно session capability.

**Исправить:** согласовать семантику глобальной возможности открыть свою управленческую очередь. Вычислять её по действующим полномочиям, сохранив серверную фильтрацию областей; проверить входы из задач, dashboard и сезона. Не расширять доступ к чужой работе ради отображения кнопки.

**Критерий закрытия:** мастер/соответствующие замы и руководители открывают только разрешённую очередь, находят ушедшего исполнителя и выполняют явное атомарное переназначение. После снятия последней управленческой роли действие исчезает. Обычный участник не получает чужую очередь.

### INT-02 · P2 · История опубликованных версий отчёта никогда не открывается

**Основание:** FE-03, REPORT-05/06.

**Доказательство:** опубликованы две версии одного отчёта; `reportsApi.versions()` возвращает `[1, 2]`. У редактора в `Report.capabilities` только `edit_report` и `publish_report`, у читателя список пуст. Frontend требует `view_report_versions` для запроса и секции (`ReportPages.tsx:216`, `:259`). Backend не выдаёт это имя ни в одном месте; проекция находится в `database.py:1355`. Браузер показывает текущую версию 2 без истории версии 1.

**Исправить:** выдавать capability чтения версий по тому же основанию, что используется для защищённого API версий; согласовать её с клиентом. Проверить и текущих читателей, и сохранённых редакторов закрытых экземпляров.

**Критерий закрытия:** разрешённый пользователь открывает обе публикации, видит автора/дату/текст и может запросить разрешённые файлы старой версии. Снятый руководитель без независимого основания и читатель чужой серии получают отказ; черновик не раскрывается.

### INT-03 · P2 · История исправлений закрытой сводной не подключена к UI

**Основание:** FE-02 — исправления закрытых итогов с историей; SEASON-03, SUMMARY-01.

**Доказательство:** действующие `GET /seasons/{id}/summary/versions` и `GET /seasons/{id}/summary/versions/{version}` возвращают несколько неизменяемых версий, причину, автора/дату и снимок. Реальное изменение отметки создало новую версию; чтение предыдущего перечисленного снимка прошло. Обработчики: `backend/season_summaries.py:387`, `:400`. В `frontend/src/utils/api/seasons.api.ts` нет клиентов этих методов; `SummaryPage` (`SeasonPages.tsx:349`) показывает только текущую сводную и номер. Предыдущая блокировка отсутствующим backend read API уже снята, но интерфейс не доведён.

**Исправить:** добавить DTO/клиенты списка версий и снимка, защищённый просмотр истории на странице сводной, причину/автора/дату и выбор прошлой версии. Добавить инвалидацию списка после исправлений/решений. Исторический снимок показывать отдельно от действующих итогов, без локального пересчёта.

**Критерий закрытия:** председатель исправляет закрытый итог с причиной, затем в UI видны прежний и новый снимки и их происхождение; прежние значения не меняются. Разрешённый HR читает историю, но не получает полномочия исправления; обычному участнику закрыт расчёт.

### INT-04 · P2 · Форма собственных контактов отвергает допустимые данные аккаунта

**Основание:** FE-05, CONTACT-01; согласованный регистрационный DTO.

**Доказательство:** действующий аккаунт зарегистрирован и одобрен с `tg=@profkom_test` и пустым отчеством. Backend отдаёт эти значения; собственная форма заявки допускает отсутствие отчества. `ProfileValidationSchema` (`utils/zod.ts:38`, `:48`) требует непустое отчество и только Telegram-ссылку `t.me/...`. Изменение одной фамилии в браузере не отправляется: показаны обе ошибки на уже сохранённых полях. Контрактный тест на реальном профиле воспроизводит отказ схемы.

**Исправить:** унифицировать нормализацию/валидацию Telegram и необязательных полей в регистрации, заявке и профиле. Сохранить понятное отображение ссылок. Уточнить единое правило коротких VK-адресов, не добавляя валидацию, которая отвергает собственные действующие данные сервера.

**Критерий закрытия:** пользователь с допустимым `@username` и без отчества изменяет одно своё поле, успешно сохраняет и перечитывает профиль; некорректные контакты получают понятную ошибку. Чужие контакты по-прежнему нельзя изменить.

### INT-05 · P2 · Клиент предлагает формат файла, который API отвергает

**Основание:** FE-02/03/05 — рабочие загрузки и понятная проверка допустимых форматов.

**Доказательство:** `Attachments.tsx:6` и file-input разрешают `.gif`. Настоящий `filesApi.intent()` для `test.gif`, `image/gif`, допустимого размера и доступного отчёта получает `422 invalid_input: File type is not allowed`. В `backend/file_access.py:TYPES` GIF отсутствует. Это отказ до обращения к S3, поэтому реальный bucket не нужен для воспроизведения. Отдельно следует согласовать MIME-алиасы, объявленные старым интерфейсом ПГАС.

**Исправить:** сделать согласованный список расширений/MIME и правил размера для всех клиентских загрузок. Убрать неподдерживаемый GIF из выбора либо явно реализовать и проверить его на сервере; первый вариант не требует расширения текущего контракта. Пустой/альтернативный MIME обрабатывать по согласованному правилу с серверной проверкой фактического содержимого.

**Критерий закрытия:** каждый предлагаемый интерфейсом формат проходит intent → PUT → complete на тестовом хранилище с подходящими байтами; неподдерживаемые типы отклоняются до загрузки с понятным сообщением. Границы 10/20 MiB и ACL после утраты роли остаются закрытыми тестами.

### INT-06 · P3 · Несколько nullable-полей не совпадают с TypeScript DTO

**Основание:** общий API 1.3, FE-01 — корректные безопасные клиентские модели.

**Доказательство:** 77 фактических ответов проверены против 28 семейств интерфейсов. Сервер возвращает `null` для `RoleAssignment.principal_assignment_id`, `Contribution.merit_id`, `Contribution.bonus_id`, `FormerContact.patronymic`; клиент объявляет их как необязательный `string` без `null` (`contract.ts:37`, `:216`, `:217`, `:401`). Заметного падения UI в этих случаях не обнаружено: используемые компоненты преимущественно защищены `??`/условиями. Но успешный `tsc` не подтверждает корректность фактического ответа Axios.

**Исправить:** выровнять nullable/optional по согласованному wire-контракту; проверить legacy-адаптеры и добавить независимые проверки реальных ответов. Не маскировать расхождение утверждениями типов или подменой ответа.

**Критерий закрытия:** репрезентативные ответы всех проверенных DTO проходят контрактную проверку; компилятор и компоненты корректно обрабатывают и пустое значение, и реальный ID.

# План оставшихся работ frontend

Срез: 2026-10-18. База до сохранения плана — локальная `dev`, коммит `7acb922`. Повторная проверка выявила незакрытые требования: 79 проходящих тестов не подтверждают готовность перечисленных ниже сценариев. Прежние результаты остаются в [ACCEPTANCE.md](ACCEPTANCE.md), актуальный статус — в [CHECKLIST.md](CHECKLIST.md).

## Процесс

Связанные пункты группируются в ветки от актуальной локальной `dev`: `feature/frontend-workflow-fixes` (F01–F03 и F07), `feature/frontend-summary-forms` (F04–F06), `feature/frontend-compatibility-acceptance` (F08–F09). Внутри группы — проверяемые коммиты и краткий отчёт после каждого пункта. После проверки группы — интеграция в локальную `dev`; следующая ветка создаётся от неё. Публикация веток и деплой в этот план не входят.

Область изменений — frontend и его документация. Права и рассчитанные значения приходят с сервера; таймеры и фильтры не создают полномочия. Тестовый transport остаётся только в DEV/test. Неизвестные API и связи ID фиксируются как вопросы контракта, а не выдумываются в клиенте.

## F01. Сверка требований и проверок

Ветка: `feature/frontend-workflow-fixes`.

- Составить таблицу: требование из `CODEX_FRONTEND.md` → экран/действие → API → проверка → пробел → критерий закрытия.
- Включить пять подтверждённых недоделок F02–F06, фильтры справочника/рабочего экрана, старые входы в редактор гайдов и связанные сценарии нескольких ролей.
- Разделить дефект frontend, неподтверждённый сценарий и конкретный пробел API. Дополнительные исправления оформить задачами в соответствующей группе до их реализации.
- Пересмотреть галочки, если проверен только вызов API-клиента или ручная смена фикстуры, а не действие пользователя.

Готовность: у каждого незакрытого требования есть задача с наблюдаемым результатом либо назван отсутствующий элемент контракта. Нет статуса «готово» без подходящего подтверждения.

## F02. Обновление заявок у границы 72 часов

Ветка: `feature/frontend-workflow-fixes`.

Проблема: открытая очередь сама не перечитывает capabilities при наступлении `substitute_available_at`.

- Запланировать повторный GET по серверному сроку текущего этапа; после перехода HR → мастер использовать новый срок.
- Обновлять данные после возвращения во вкладку; сохранить ручное обновление и понятную ошибку сети.
- Убирать таймеры при уходе, ограничить повторные запросы. Уже прошедший срок не должен создавать бесконечный цикл.
- Разрешать подмену только после ответа с нужным capability.

Проверка: экран открыт до границы; время проходит без перезагрузки. Проверить запрос на границе, новый этап, одноэтапный HR, отказ сервера, возвращение во вкладку и ошибку сети.

Готовность: подмена становится доступна после подтверждения сервером без перезагрузки страницы; часы браузера сами не открывают действие.

## F03. Переход от препятствия закрытию к назначению

Ветка: `feature/frontend-workflow-fixes`.

Проблема: препятствие с `assignment_id` ведёт в общую очередь, где может не быть уже принятого назначения без оценки.

- Разрешить связь назначения с задачей через доступные данные существующего контракта.
- Открывать конкретную задачу и нужное назначение/форму оценивания, с выделением и правильным фокусом.
- Обработать недоступный объект и изменение прав без перехода в посторонний пустой список.
- Проверить остальные типы препятствий: предыдущий сезон, задача, final главного мероприятия и подмероприятия.

Готовность: незавершённое и принятое без оценки назначения приводят к своим действиям; недоступное даёт понятное сообщение. Прямой переход и возврат к закрытию сохраняют контекст. Если API не позволяет разрешить связь, указан точный недостающий идентификатор/метод; фиктивной ссылки нет.

## F04. Полные формы исправления закрытых итогов

Ветка: `feature/frontend-summary-forms`.

Проблема: команда поддерживает `task_inputs`, `assessment_inputs` и `merit`, но форма отправляет только `assessment_inputs`.

- Добавить выбор типа и объекта: даты/критерии задачи, оценивание назначения, исходные данные особой заслуги/волонтёрства в пределах согласованного DTO.
- Загружать исходные значения, revision объекта и версию закрытой сводной; показывать, что меняется.
- Требовать причину и серверное право председателя. Не добавлять ввод рассчитанного ККР.
- При 409/422 сохранять ввод, объяснять конфликт/ошибки полей, не показывать частичный успех. После успеха перечитывать сводную, источники и затронутые бонусы.

Готовность: все три типа изменений проходят через формы с правильными payload, причиной и версиями, подтверждаются повторным чтением транспорта. Проверены запрет другой роли, конкурентное изменение и повторная отправка. Просмотр старых версий/аудита остаётся отдельной зависимостью API.

## F05. Выбор получателей заслуги

Ветка: `feature/frontend-summary-forms`.

Проблема: индивидуальные поля создаются для всего справочника, а не выбранных людей; прежний получатель может исчезнуть из вариантов после архивирования.

- Добавить поиск и выбор получателей, поля часов/оценки/даты показывать только выбранным.
- Сохранять ввод при временном снятии/возврате выбора; отправлять только выбранных получателей.
- При редактировании сохранять исторических получателей и значения, даже если их нет в текущем справочнике.
- Историческую допустимость участия определять ответом сервера, а не текущим `in_profcom`.

Готовность: из 100 контактов выбраны двое — видны только их шесть индивидуальных полей. Разные значения сохраняются; снятие/возврат выбора не теряет ввод; редактируется запись с архивированным получателем; состав payload точный. На телефоне форма доступна без горизонтального прокручивания всей страницы.

## F06. Цветные отметки решений

Ветка: `feature/frontend-summary-forms`.

Проблема: несколько решений показаны общей текстовой строкой без требуемого цветового выделения.

- Добавить единые метки «Золотой Red Bull», «Предупреждение о кике», «Кик», «Найс» с читаемыми цветами и контрастом.
- Показывать все выбранные решения; прошлые оставлять в отдельной исторической колонке.
- Сохранить явные подписи и пустое состояние, чтобы значение читалось без определения цвета.

Готовность: несколько текущих/прошлых меток, отсутствие меток и длинные подписи проверены на телефоне и компьютере. Ничего не скрыто; прошлое решение не присваивается текущему сезону. Изменение вызывает только команду решений, без архивирования аккаунта и рассылок.

Готовность: проверены два незакрытых сезона, глобальные сущности, совмещение фильтров, пустой поиск и ошибка категории. Результат и пустое состояние соответствуют выбранным условиям; смена текущего сезона не скрывает прежнюю работу.

## F08. Совместимость старых гайдов с материалами

Ветка: `feature/frontend-compatibility-acceptance`.

Проблема: новый редактор имеет черновик/публикацию, а доступный старый редактор гайдов сохраняет текст напрямую.

- Проверить `/guides`, `/docs/:id`, старые административные действия и ссылки из материалов/блоков. Сопоставить чтение, создание, правку и удаление с требованием сохранения функций.
- Установить, определена ли связь guide ID с material ID. При подтверждённой связи направить редактирование в единый сценарий черновика и явной публикации, сохранив ссылки/содержимое.
- Если связи нет, выполнить независимую работу с интерфейсом/маршрутами и записать точное требование к mapping. Не сопоставлять документы по заголовку или случайному равенству ID.
- Проверить Markdown, галереи, контактные вставки и отдельные права ПГАС.

Готовность: каждый старый путь имеет проверенное поведение. Читатель видит прежнюю публикацию при правке, редактор — черновик, публикация явная; старый URL открывает правильный документ. Если это требует миграции API/данных, соответствующий подпункт остаётся открытым с конкретным условием снятия блокера.

Готовность: все подтверждённые независимые недоделки закрыты наблюдаемыми сценариями; у оставшихся названа конкретная внешняя зависимость и условие её снятия. Количество зелёных тестов само по себе не закрывает весь frontend.

## Отдельные зависимости backend

- Read API старых версий закрытой сводной/аудита коррекций. Условие снятия: версии и изменения получаются по ID, с автором/временем/причиной и проверкой прав.
- Реальные сессия, capabilities, revisions, сохранение. Условие снятия: реальные ролевые сценарии, повторный GET, запрет доступа и конкурентный 409.
- Настоящие upload/complete/download, аватары и VK. Условие снятия: успешный поток, повторное чтение и отрицательная проверка доступа.
- Настоящая XLSX-выгрузка. Условие снятия: открывается файл с двумя согласованными листами и значениями серверного расчёта.
- Связь старых гайдов с материалами — потенциальная зависимость F08; подтвердить в аудите, а не заранее считать решённой или непреодолимой.

# HTML-вставки в гайды: проект решения

Статус: **первый выпуск реализован и функционально проверен локально** по отдельному
разрешению владельца после просмотра макета 10 ноября 2026 года. Исходный
проект ниже сохранён как обоснование. Действующие контракты описаны в
[backend/docs/GUIDE_EMBEDS.md](../../backend/docs/GUIDE_EMBEDS.md) и
[frontend/docs/GUIDE_EMBEDS.md](../../frontend/docs/GUIDE_EMBEDS.md).
Включение на сервере остаётся отдельной операцией. Числа в разделе 8 —
критерии приёмки, а не утверждение о достигнутой скорости production.

12 ноября чтение дополнительно оптимизировано: ограниченный кэш хранит готовый
JSON неизменяемого содержания, а текущие права и динамический DTO проверяются
на каждом запросе. Локальные 8 серий по 100 одновременных запросов на формат с
gzip (level 5 / minimum 512) дали p95 HTML/Markdown 0,970 для типового исходника 10,5 КБ,
0,977 для 500 элементов и 1,029 для 1495 элементов: критерий +10% выполнен в этих
сценариях. Это синтетический ASGI gzip на localhost HTTP/1.1, не nginx/production;
смешанная нагрузка других API не измерялась. Без gzip 500 элементов всё ещё дают
+15,24% при 100 запросах. Последовательный путь больших документов с gzip даёт
+13%/+17% (+0,566/+0,794 мс), у типового документа превышения нет. Общий бюджет
production поэтому не объявляется доказанным. Исторические browser-замеры 30 пар
не показали дополнительного CLS от вставок после исправления содержания.
Подробные условия и raw samples: `.local/logs/guide-html-ready-20261112/REPORT.md`.

Уточнения первого выпуска: кнопки — ссылки с выбором назначения; доступны
таблицы, приватные изображения и статичные градиенты. Новые гайды сначала
сохраняются, затем получают вставки и файлы. Старый Markdown сохраняет свою
политику файлов без дополнительного парсинга на GET. Для расширенного формата
введён отдельный предел исходника 2 MiB; старые документы не ограничиваются
этим изменением. Переходы на заголовки проверяются компилятором, а номерные
якоря обычного Markdown следует перепроверить после перестановки разделов.

## 1. Предлагаемый результат

Оставить Markdown основой гайда, добавить явные блоки HTML с ограниченным
набором элементов и готовыми классами оформления. Автор сможет вставить
красивую карточку, сетку шагов, предупреждение, таблицу, раскрывающийся ответ
или иллюстрацию. Для обычных случаев код писать не потребуется: редактор
предложит шаблоны и поля настройки. Для сложной композиции останется вкладка
«HTML» с подсказками и проверкой.

Сервер проверяет вставку при сохранении и публикации и сохраняет небольшое
дерево разрешённых элементов. Читатель получает готовое дерево и обычные
React-компоненты: без выполнения пользовательского JavaScript, парсинга HTML
при каждом открытии и отдельного iframe на каждую карточку.

Первый выпуск предназначен для гайдов блоков (`kind=guide`). Возможность
применить тот же формат к КМБ и общим документам — отдельное расширение после
проверки редакторского UX. HTML в комментариях, задачах, отчётах и уведомлениях
от этого не появляется.

### Что получит автор

- «Вставить → Оформленный блок»: заметка, шаги, две колонки, карточки, FAQ,
  таблица сравнения, изображение с подписью.
- Цветовые темы сайта, сетки, интервалы и типографика без ручной настройки CSS.
- Предпросмотр всего гайда и отдельной вставки на ширине телефона и компьютера.
- Сообщение о неподдерживаемом элементе рядом с исходным кодом, до публикации.
- Сохранение исходника, отмена/повтор, отдельные сохранение черновика и публикация.

Произвольные сторонние страницы, скрипты, формы и CSS не входят в первый выпуск.
Это ограничение нужно явно показывать в справке редактора, чтобы вставка HTML
из внешнего конструктора не выглядела как обещание точного переноса его дизайна.

## 3. Выбор подхода

| Подход | Оформление и UX | Быстродействие и сопровождение | Решение |
| --- | --- | --- | --- |
| Разрешить HTML во всём Markdown | Просто вставить разметку; трудно объяснить разные права и ограничения | Парсинг и очистка во всех местах, увеличенная поверхность ошибок, риск затронуть комментарии | Не выбирать |
| Только визуальные блоки без HTML | Удобно новичку, но нет нужного владельцу режима вставки кода | Быстро и предсказуемо, но ограничивает перенос готовых композиций | Использовать как основной интерфейс поверх HTML-вставки |
| Ограниченный HTML → проверенное дерево → React | Шаблоны плюс редактор кода; единый стиль, поиск, печать и содержание | Компиляция на записи, компактный читатель; не нужен новый серверный сервис | **Рекомендуемый первый выпуск** |
| HTML/CSS в sandbox iframe | Больше свободы CSS и сильнее изоляция стилей | Отдельные документы, высота, фокус, печать, поиск и приватные изображения усложняются | Отложить до подтверждённой потребности в произвольном CSS |

`rehype-sanitize` показывает подход с явной схемой разрешённых элементов и
атрибутов; его документация отдельно разбирает DOM clobbering и совместимость
с математикой. Если в прототипе рассматривается клиентская HTML-цепочка, её
нужно проверять как целое, включая плагины после очистки. Однако в предлагаемом
первом выпуске браузер читателя вообще не принимает произвольный HTML.
[Документация rehype-sanitize](https://github.com/rehypejs/rehype-sanitize).

## 4. Формат и границы вставки

Добавить отдельный тип `MaterialContent` с форматами `markdown` и
`markdown-embeds-v1`. Расширенный формат включается явным действием редактора
«Добавить HTML-вставку». Исходником остаётся текст; обычный кодовый блок
`html` по-прежнему отображает код. Вставка обозначается отдельным fenced-блоком
`profkom-html`, например:

````markdown
## Как вступить в блок

Обычный Markdown остаётся без изменений.

```profkom-html
<section class="guide-card guide-tone-info">
  <h3>Что подготовить</h3>
  <p>Коротко расскажите о себе и выберите удобное время.</p>
  <a href="/blocks">Открыть список блоков</a>
</section>
```
````

Не распознавать fenced-блоки регулярным выражением по всему документу. Нужен
Markdown-парсер с корректной обработкой вложенности, длинных ограждений,
отступов и экранирования. В прототипе проверить согласованность извлечения
на сервере и существующего remark-парсинга по общему набору примеров.

У старого материала с форматом `markdown` даже случайное совпадение имени
ограждения остаётся кодом. Преобразование формата — явная запись с ревизией,
не миграция по эвристике. Идентичность вставки задаётся стабильным ID,
генерируемым редактором и проверяемым сервером; позиция в документе сама по
себе не является идентификатором. Вставленный вручную блок получает ID при
первом сохранении с показом изменения исходника.

### Разрешённые элементы первого выпуска

| Группа | Элементы и ограничения |
| --- | --- |
| Структура | `section`, `div`, `p`, `span`, `h2`–`h6`, `br`, `hr`; уровень заголовка проверяется, основной `h1` принадлежит странице |
| Текст | `strong`, `em`, `s`, `mark`, `small`, `sub`, `sup`, `blockquote`, `pre`, `code` |
| Списки | `ul`, `ol`, `li`, `dl`, `dt`, `dd`; ограниченные числовые `start`/`value` |
| Таблицы | `table`, `caption`, `thead`, `tbody`, `tfoot`, `tr`, `th`, `td`; `scope`, ограниченные `colspan`/`rowspan`; таблица помещается в доступную прокручиваемую область |
| Раскрытие | `details`, `summary`; без скриптов; редактор требует понятный заголовок |
| Ссылки | `a`: нормализованные относительные маршруты сайта, якоря и `https`-ссылки; внешние ссылки маркируются; `rel`/`target` задаёт приложение |
| Изображения | `figure`, `figcaption`, `img`: только `file:<id>` своего материала, проверенный MIME, `alt`, размер; выбор через существующий загрузчик |

Не принимать `script`, обработчики `on*`, `style`, `link`, `meta`, `base`,
`iframe`, `object`, `embed`, `form`, ввод/кнопки, SVG/MathML и пользовательские
custom elements. Формулы остаются в существующем Markdown-режиме с его
ограничениями. Не разрешать произвольные `id`, `name`, `data-*`, ARIA-роли или
атрибуты `tabindex` из кода; нужные семантические атрибуты генерируют компоненты.
Якоря создаются в пространстве имён материала/вставки, а ссылки на них
переписываются компилятором. Это также исключает совпадение с ID формы входа
или элементов оболочки сайта.

Отдельная схема описывает атрибуты каждого узла; общего переноса props через
`{...attributes}` нет. URL проверяются после декодирования сущностей и
нормализации: запрещены управляющие символы, `javascript:`, `data:`, `blob:`,
протокол-относительные адреса и ссылки на служебные API в роли навигации.
Изображения с внешних хостов в первом выпуске не загружаются. Импорт внешнего
изображения, если понадобится, проектируется отдельно с SSRF-защитой, лимитами
и переупаковкой файла.

### Оформление

Разрешить конечный набор классов: карточка, сетка 2/3 колонок, шаги, заметка,
цитата, компактная таблица; оттенки `neutral`, `info`, `success`, `warning`.
Компилятор переводит их в enum-параметры внутренних компонентов. CSS Modules
и токены сайта задают реальный CSS; пользовательский класс не становится
классом на произвольном узле страницы.

Сетка автоматически становится одноколоночной на узком экране. Ширина не
выходит за контейнер, текст переносится, изображения сохраняют пропорции.
Палитра, контраст и отступы проверяются для тёмной и поддерживаемых тем сайта.
Нет фиксированного позиционирования, бесконечной анимации, сторонних шрифтов,
фильтров или теней с произвольными значениями. Расширение набора классов —
обычный выпуск приложения с визуальными тестами, а не изменение автором CSS.

## 5. Серверная обработка и хранение

### Компилятор

1. Проверить действующую авторизацию и право редактировать этот материал.
   Применить лимит байтов до запуска парсера, затем проверить структуру Markdown.
2. Разобрать HTML как HTML5 fragment. Кандидат для локального прототипа —
   `html5lib`: Python, без дополнительного Node-сервиса; библиотека заявляет
   соответствие HTML-разбору браузеров. Точную закреплённую версию выбрать
   после проверки поддержки, зависимостей и замера прототипа.
   [Документация html5lib](https://html5lib.readthedocs.io/en/latest/).
3. Из результата собрать **новое** дерево фиксированной схемы: текст, известный
   тег, разрешённые типизированные свойства, дети. Ничего из исходного дерева
   автоматически не переносить. Ограничить глубину/узлы/строки/URL; отклонить
   недопустимые конструкции с указанием вставки и причины.
4. Получить из дерева набор `file_id`, заголовки, текстовое представление и
   диагностические сообщения. Заголовки и текст — производные данные, не
   разрешения на чтение и не публичный поисковый индекс.
5. Сохранить исходник и производное дерево согласованно. Повторно проверить
   ревизию и права непосредственно в транзакции записи. Публикация дополнительно
   подтверждает завершённость и принадлежность всех файлов.

Парсер сам по себе не является санитайзером. Граница безопасности — схема
нового дерева, повторная проверка его формы клиентом и фиксированный React
renderer. Не использовать `dangerouslySetInnerHTML` ни для предпросмотра,
ни для читателя, ни как аварийный fallback. Документация React предупреждает
о риске XSS при передаче недоверенного HTML в этот API.
[Документация React](https://react.dev/reference/react-dom/components/common#dangerously-setting-the-inner-html).

Компиляция не делает сетевых запросов и не проверяет S3 на каждый просмотр.
CPU-разбор выполняется вне event loop и вне удержания SQLite writer lock;
число одновременно работающих компиляторов ограничено. Перед реализацией
нужно проверить границу существующего `Database.async_atomic`: не вынести
проверку ревизии из транзакции ради скорости. Практический вариант — прочитать
ACL, скомпилировать вне write unit, затем внутри неё заново проверить ACL,
`expected_revision`, набор файлов и атомарно записать результат. Для черновика
с ошибкой допускается сохранить исходник как непубликуемый draft; читатель
продолжает видеть прежнюю публикацию.

### Предлагаемая модель

Добавить к материалу независимые `draft_format` и `published_format` с
безопасным значением по умолчанию `markdown`. Производные данные хранить в
таблице `material_render_artifacts` с уникальным ключом `(material_id, slot)`,
где `slot` — `draft` или `published`:

- версия схемы дерева и политики разрешений;
- хеш исходника вместе с форматом, ревизия/идентификатор сохранения;
- ограниченный JSON дерева вставок, карта заголовков и набор ссылок на файлы;
- результат проверки и безопасные диагностические коды для редактора.

Номер ревизии всего материала может меняться при настройке редакторов или
аудитории, поэтому соответствие артефакта определяет прежде всего хеш исходника
и версия политики; ACL всегда проверяется заново. При публикации черновик и
его проверенный артефакт становятся опубликованными атомарно. Не использовать
«последний артефакт» без проверки соответствия тексту.

Читательский DTO содержит только опубликованный результат, редакторский —
исходник и диагностику черновика. Каталог материалов получает краткие сведения,
без деревьев и HTML всех гайдов. Строгий `wireContract` обновляется вместе с
Python/TypeScript схемами. Источники файлов в артефакте — стабильные `file_id`,
а не подписанные URL с истекающим сроком действия.

## 6. ACL, файлы и кэш

- Сохраняются текущие `material.edit`, `material.read_block_guide`, публикация,
  аудитория и управление редакторами. Наличие HTML не добавляет полномочий.
- Preview доступен только редактору материала; он не публикует текст и не
  открывает файлы другим пользователям. Если делается endpoint preview, он
  ограничен по размеру, частоте и числу параллельных вычислений.
- Проверку опубликованных файлов нужно перевести с поиска строки
  `file:<id>` на общий извлекатель реальных ссылок для обоих форматов.
  Один и тот же извлекатель используют публикация, выдача файла и retention.
  Иначе файл, упомянутый в удалённом/запрещённом HTML или в кодовом примере,
  может ошибочно стать доступен. Эта совместимая замена требует отдельного
  теста старых Markdown-материалов и не делается GET-запросом.
- Приватные изображения идут через существующий API и проверяются при каждом
  запросе. В HTML нет публичного HTML-файла в бакете и нет обхода контекста
  материала. Удаление вставки из публикации прекращает доступ к её файлам
  читателям, если файл больше нигде разрешённо не используется.
- Кэш компиляции не хранит разрешения, сессию или подписанные ссылки.
  Запрещены общий CDN-кэш приватного материала и ответ `304` до проверки ACL.
  При потере прав интерфейс удаляет опубликованный текст, черновик и
  предпросмотр из активного UI по существующему механизму смены доступа.
- HTML-исходник не попадает в общие журналы ошибок. Метрики содержат размер,
  длительность, число узлов и код отказа; доступ к диагностике — у редактора.

## 7. UX редактора и читателя

### Автор

1. Нажимает «Оформленный блок» и выбирает шаблон по небольшому превью.
2. Заполняет текст, ссылки и изображения в обычных полях. Рядом переключатель
   «HTML»; возврат к полям возможен только для распознаваемого шаблона,
   произвольную композицию редактор не переписывает молча.
3. Видит рядом итоговую вставку. Полный предпросмотр открывается явно;
   переключатели ширины 390/768/1280 px не изменяют исходник.
4. Неподдерживаемые элементы показаны как ошибки с объяснением и доступным
   вариантом замены. Не удалять код тихо и не показывать «успешный» результат,
   отличающийся от будущей публикации. Исходник можно скопировать целиком.
5. Сохраняет черновик. При ошибках сохраняется работа и список проблем;
   кнопка публикации объясняет, что исправить. Изменение исходника сразу
   делает предыдущий предпросмотр неактуальным; старый ответ preview не
   заменяет результат более нового ввода.
6. Перед публикацией проверяет сравнение текущей публикации и нового результата.
   `expected_revision`, конфликт «перечитать/сохранить свою копию» и guard
   несохранённых изменений действуют для всех настроек и HTML-исходника.

Не вводить фоновую автопубликацию. Автосохранение, если его добавят позднее,
отдельно согласовать; исходная версия сохраняет действующее явное сохранение.

### Читатель

Гайд остаётся одной страницей: общее содержание, поиск браузером, выделение
текста, ссылки на разделы и печать работают внутри вставок. Внешние ссылки
отмечены. `details` управляется клавиатурой, таблица имеет подпись и область
горизонтальной прокрутки, изображения — `alt` и размеры. Для печати раскрываются
секции и убираются декоративные фоны, мешающие чтению.

Ошибка одной вставки показывает локальную карточку с доступным текстовым
представлением; остальные разделы остаются видны. Не превращать ошибку
валидации в бесконечный spinner. Клиент никогда не показывает исходный HTML
как исполняемую запасную версию. При несовместимой версии дерева читатель
получает безопасный fallback, редактор — понятное предложение перепроверить.

## 8. Быстродействие: устройство и критерии

Все бюджеты сначала проверяются на синтетическом стенде, затем на согласованном
окружении. Зафиксировать CPU/RAM сервера, браузер, устройство/профиль замедления,
размер материала, холодный/тёплый кэш и число повторов. Не переносить цифры
быстрого ноутбука в обещания для телефона или production.

### Пределы первого прототипа

| Параметр | Начальный предел |
| --- | --- |
| HTML одной вставки | 32 KiB UTF-8 |
| Вставок в гайде | 20 |
| HTML всех вставок | 128 KiB UTF-8 |
| Элементов | 300 на вставку, 1500 на документ |
| Глубина | 12 вложенных элементов |
| Изображений | 4 на вставку, 20 на документ; действующие лимиты файла сохраняются |
| Скомпилированный JSON | 512 KiB до сжатия; превышение — ошибка проверки |

Это согласованный между backend и UI контракт, с понятной ошибкой до публикации.
Более тяжёлые материалы делятся на разделы/страницы; пределы повышаются только
после нового замера. Лимит общего тела существующего Markdown определяется
отдельно: нельзя внезапно запретить сохранение старого большого гайда только
из-за внедрения вставок.

### Чтение

- Ни одной новой зависимости HTML-парсера в начальном bundle сайта и в обычном
  Markdown-материале. Renderer вставок — отдельный lazy chunk; ориентир его
  дополнительного gzip-размера до 20 KiB, CSS до 5 KiB.
- Чтение не запускает компилятор и не пишет БД. Один дополнительный запрос к
  артефактам на детальный material GET; число SQL не растёт с количеством
  вставок. В списке материалов нет запроса артефактов.
- На странице нет iframe, сторонних шрифтов/скриптов и сетевых вызовов от
  декоративного блока. Изображения ниже первого экрана используют lazy loading
  и async decode; заданные размеры резервируют место. Видимое первое
  изображение не задерживается общим lazy-правилом.
- Для типового гайда до 10 вставок/500 элементов: дополнительный render p95
  до 50 мс на зафиксированном мобильном профиле, дополнительный CLS до 0,02.
  Если длинный документ превышает бюджет, сначала уменьшаем DOM и сложность
  шаблонов. Виртуализация текста не должна ломать поиск, оглавление и печать.
- Для 100 одновременных читателей на прогретом синтетическом наборе: material
  GET p95 не более чем на 10% хуже исходного; измерять вместе с обычными API,
  а не только изолированный быстрый endpoint. Дерево не перерасчитывается
  при проверке сессии, фоновой активности или смене чужого профиля.

### Редактирование и сервер

- Ввод текста не ждёт парсинга. Preview обновляется после паузы 300–500 мс,
  только когда он открыт; запросы отменяются/результаты маркируются номером
  исходника. Ограниченная очередь и отбрасывание устаревших работ обязательны.
- Прототип компиляции 128 KiB: p95 до 150 мс CPU на зафиксированном серверном
  профиле, жёсткий дедлайн задания 1 с. Проверить патологическую вложенность,
  исправление сломанного HTML и длинные сущности. Если предел не достигается,
  уменьшить лимиты или заменить парсер после общего корпуса тестов.
- Одновременно не более одного тяжёлого задания компиляции на небольшой
  инсталляции; ограниченная очередь возвращает понятный `429`, не копится
  бесконечно. Задание с дедлайном должно реально прерываться/изолироваться,
  а не только прекращать ожидание HTTP, оставляя CPU занятой работой.
- Во время preview/save обычные session/contacts/task GET не должны получать
  заметную очередь event loop. Зафиксировать отдельно время компиляции,
  ожидание SQLite lock, длительность транзакции и размер ответа.

Не нужен новый постоянно работающий Node-сервис, Redis или S3 для HTML. Данные
небольшие, производный JSON живёт рядом с материалом. Изображения остаются
отдельной задачей хранилища: HTML-вставки сами по себе не устраняют его задержки.

## 9. Почему произвольный CSS оставляем на отдельный этап

Если шаблонов не хватит, следующий кандидат — специальный HTML/CSS-документ
на отдельном origin без cookies сайта, внутри iframe с пустым `sandbox`,
без разрешения скриптов, форм, всплывающих окон и верхней навигации. Изоляция
имеет ограничения: без `allow-same-origin` документ получает особый origin;
сочетание `allow-scripts` и `allow-same-origin` для своего origin опасно.
[Документация iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

Нужны собственные CSP-заголовки, например запрет внешних соединений и
исполнения скриптов; CSP дополняет проверку входа, а не заменяет её.
[Документация CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP).

До выбора iframe отдельно решить:

- Как выдавать приватные изображения без публичных URL, cookie сайта и
  произвольного сетевого доступа вложенного документа.
- Как задавать высоту без недоверенного JS и не заставлять телефон прокручивать
  вложенные области; фиксированная/выбранная автором высота — компромисс.
- Как работают оглавление, поиск, печать, ссылки, загрузка файла и доступность.
- Как фильтруются CSS `url()`, `@import`, шрифты, тяжёлые фильтры/анимации и
  ресурсоёмкие селекторы; sandbox сам по себе не ограничивает затраты CPU.
- Как выглядит страница при нескольких фреймах и при отзыве доступа.

Автоподбор высоты через скрипт и `postMessage` означал бы дополнительную
доверенную инфраструктуру и проверку сообщений; не добавлять его незаметно
под обещание «HTML без JavaScript». Поэтому этот режим — новый проект,
а не флажок в первом выпуске.

## 10. План реализации и проверок

### Этап A. Локальный прототип и уточнение формата

Собрать 5–8 синтетических гайдов: простой текст, карточки, FAQ, большая таблица,
иллюстрации и предельно допустимый размер. Показать редакторские шаблоны на
390/768/1280 px. Реализовать экспериментальный компилятор вне приложения,
проверить HTML5/Markdown parsing, лимиты и измерить CPU/RAM. После результатов
утвердить список классов, формат ID, пределы и окончательный выбор парсера.

### Этап B. Данные и API за выключенным флагом

Добавить аддитивную идемпотентную миграцию; все существующие форматы —
`markdown`, исходники и публикации неизменны. Добавить компилятор, типы
`MaterialContent`, артефакты и preview. Покрыть свежую БД и старую схему двумя
startup-проходами, сохранность строк, FK и `integrity_check`. GET ничего
не чинит и не создаёт.

Проверить старые API-контракты и совместимость legacy GuideORM: публикация
по-прежнему сохраняет исходный текст; старый адаптер не начинает выполнять HTML.
Артефакты удаляются по существующему retention материала, не отдельной
безусловной очисткой. Сначала поставить backend, который понимает оба формата,
затем frontend; флаг записи включать только после готовности обоих.

### Этап C. Renderer и редактор

Реализовать фиксированные компоненты дерева, CSS-шаблоны, файловый picker и
предпросмотр тем же renderer, что читатель. Расширенный editor/parser грузится
при открытии соответствующего действия. Сохранить undo/redo, фокус, guard,
конфликты и ручную публикацию. Разрешить первоначально один тестовый материал,
потом остальные гайды после проверки.

### Этап D. Приёмка

| Проверка | Критерий |
| --- | --- |
| Безопасность | Корпус XSS/mutation-XSS, смешанные регистры/сущности/пространства имён, сломанная разметка, URL-обходы, DOM clobbering; в браузере нет выполнения кода/лишних сетевых обращений |
| ACL | Посторонний, участник своего/чужого блока, бывший редактор, pending/rejected и root; приватный draft/изображения не открываются через preview, публикацию, историю или прямой file URL |
| Конкуренция | Два редактора, stale revision, смена прав во время компиляции, удаление/публикация одновременно, старый preview после нового; частичной записи нет |
| Файлы | Чужой/незавершённый/удалённый файл, удаление вставки, повторная ссылка, старый Markdown, отзыв доступа, retention; список ресурсов соответствует реально разрешённому дереву |
| Совместимость | Старые гайды, галереи, формулы, code fences и legacy URL неизменны; HTML не включился в комментариях/задачах |
| UX | Клавиатура/фокус, экранный диктор, 390/768/1280 px, длинные слова, таблицы, печать, содержание, несохранённые изменения, отказ публикации с сохранением исходника |
| Производительность | Бюджеты раздела 8, N повторов и p50/p95, холодный/тёплый кэш, максимальный документ и конкурентное чтение; GET не содержит компиляции/записи/S3-проверки |

Использовать существующие изолированные backend/Vitest/HTTP/Playwright-проверки;
реальные учётные записи и провайдеры не нужны для проверки этой функции.
Нагрузку на production не запускать вместо локальной репетиции.

### Этап E. Выкладка и обратимость

Перед будущей выкладкой — SQLite backup API, репетиция миграции, сохранённые
образы и выключенный флаг новых вставок. При проблеме выключить создание и
публикацию новых вставок; существующие читаются текущим безопасным renderer
либо его текстовым fallback. Старый бинарник, не знающий новый формат,
**не является полноценным откатом** после первой расширенной публикации:
нужен совместимый предыдущий выпуск с fallback либо заранее проверенный
экспорт в Markdown. Не восстанавливать старую БД поверх новых пользовательских
изменений только ради отката UI.

При изменении политики безопасности пометить прежние артефакты для явной
перекомпиляции вне GET. Для критически запрещённой версии сразу применить
fallback/блокировку вставки до перепроверки; не продолжать её показывать
только потому, что хеш исходника совпал. Исходник остаётся доступен редактору
как текст для исправления.

## 11. Решения для согласования перед реализацией

1. Принять первый выпуск как ограниченный HTML плюс готовые классы,
   без произвольного CSS/JavaScript и внешних iframe.
2. Утвердить 6–8 исходных шаблонов после просмотра макетов на телефоне.
3. Утвердить пределы после замеров прототипа, не по предположению о скорости.
4. Подтвердить начало с гайдов блоков и сохранение нынешних редакторских прав.

Сам план можно включить в текущий Git-релиз. Реализация, миграция и включение
HTML требуют отдельной задачи; в поставку 10 ноября они не входят.

# Новая задача → сообщение в VK-чате команды

Статус: **локальная реализация по согласованному интерфейсу**. Запрос владельца от
10 ноября 2026 года: привязывать беседу к блоку или мероприятию и по явному
действию автора уведомлять о созданной задаче назначенных исполнителей либо
всех участников беседы. Названия бесед принадлежат БД HereBot. Первый выпуск
работает только с VK; опросы, автоматические напоминания и повторная рассылка
при каждом изменении задачи в него не входят.

После согласования первоначального проекта владелец выбрал переключатель в
**существующей** форме создания задачи, между исполнителями и наблюдателями.
Новая отдельная форма не создаётся. На страницах блока и мероприятия действие
«Настройки чата» открывает диалог привязки. По умолчанию рассылка выключена,
обычная кнопка остаётся «Создать задачу».

Актуальное описание реализации:
[backend и протокол](../../backend/docs/TASK_CHAT_ANNOUNCEMENTS.md),
[frontend](../../frontend/docs/TASK_CHAT.md).
Ниже сохранён исходный проект и его критерии приёмки; при расхождении названий
кнопок/полей приоритет имеют эти документы и текущий код. Локальные проверки
используют синтетические данные и подменённый VK; публикация на сервере и реальная
отправка в беседу в эту работу не входят.

## 1. Что уже есть

Проверено по локальному коду сайта и локальной копии HereBot. Это не проверка
состояния production и не подтверждение доступности методов в живом VK.

| Участок | Текущее поведение | Как использовать |
| --- | --- | --- |
| [TaskCreateForm](../../frontend/src/pages/Workspace/TaskCreateForm.tsx) | Выбор очереди, исполнителей, срока; защита несохранённых изменений; `idempotency_key` для повтора создания | Добавить намерение отправить сообщение в существующую форму и её ключ запроса |
| [POST /tasks](../../backend/main.py), `Database.create_task` | Единая единица записи HTTP; повтор команды возвращает прежнюю задачу | Сохранять задачу и задание рассылки атомарно, без вызова VK внутри запроса |
| [access.py](../../backend/access.py) | Отдельные отношения мастера, заместителя, ответственного мероприятия; capabilities из центральных правил | Добавить отдельные scoped-права настройки и отправки |
| [MembershipPages](../../frontend/src/pages/Workspace/MembershipPages.tsx), [EventPages](../../frontend/src/pages/Workspace/EventPages.tsx) | Страницы блока и мероприятия с действиями по capabilities | Разместить «Настройки → Уведомления в VK» рядом с действиями команды |
| [BOT_API](../../backend/docs/BOT_API.md), [bot_api.py](../../backend/bot_api.py) | Бот опрашивает `/work`, подтверждает результаты через `/report`; GET не изменяет состояние, есть пауза и повтор отчёта | Добавить отдельный тип работы с согласованием возможностей бота |
| HereBot `models.py:Chats` | `chat_id` — `peer_id` беседы, `title` — название; игровое состояние хранится отдельно в полях той же строки | Сохранить эту таблицу источником названий; не превращать `Users` игры в реестр состава беседы |
| HereBot `core/bot.py`, `handlers/utility_handlers.py` | Запоминает беседу при добавлении/команде, обновляет известные названия при старте | Расширить учёт доступности и свежести; переименование не разрывает привязку |
| HereBot `core/chat_members.py`, `core/permissions.py` | Постраничное чтение состава, ограниченные повторы, кэш; проверка администратора беседы отказывает при сомнении | Использовать для подтверждения привязки и подготовки упоминаний вне HTTP сайта |
| HereBot `handlers/mention_handlers.py` | `@channel` — **собственная команда бота**: он строит индивидуальные упоминания и отправляет их пачками | Вызывать выделенный helper напрямую, не посылать боту текст `@channel` в надежде на повторную обработку |
| HereBot `core/site_delivery.py`, `core/site_broadcast.py` | Принимают только положительные VK ID пользователей меньше `2_000_000_000` | Сохранить запрет бесед в этих каналах; создать отдельный `chat_announcements` |

Текущая реализация `@channel` исключает автора и удалённые страницы, использует
`@screen_name (_)` и `PACK_SIZE`. В новом канале понадобятся стабильные VK ID,
ограничение по длине сообщения и сохранённый состав каждой пачки. Нативное
поведение `@all`/`@channel` у VK не считаем подтверждённым контрактом. В HereBot
`@all` сейчас вообще вызывает отдельный шуточный обработчик.

Проверка официальной схемы VKCOM подтверждает, что
`messages.send` принимает `peer_id` беседы (`2_000_000_000 + chat_id`), а
`random_id` описан как идентификатор против повторной отправки. Методы
`messages.send` и `messages.getConversationMembers` допускают токен сообщества;
конкретные права в беседе всё равно проверяются отдельно.
Источники: [схема методов messages](https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/messages/methods.json),
[объекты messages: title, is_admin, is_owner](https://github.com/VKCOM/vk-api-schema/blob/master/messages/objects.json).
Просмотренный снимок схемы имеет версию 5.199; это не утверждение, что 5.199 —
последняя доступная версия API сегодня. Страницы dev.vk.ru/dev.vk.com инструментом
не открылись, и нативный массовый пинг по ним не подтверждён. Перед живым
включением проверить действующую документацию и поведение в web/mobile клиентах.

## 2. Как это выглядит для пользователя

### Настройки блока или мероприятия

На странице команды появляется действие «Настройки». В нём раздел
«Уведомления в VK»: название привязанной беседы, состояние связи, когда бот
последний раз подтвердил доступ, кнопки «Привязать чат», «Сменить чат»,
«Отвязать». На телефоне это отдельная полноширинная панель, без широкой таблицы.

Первичная привязка:

1. Мастер/ответственный открывает настройки. Сайт проверяет scoped-право и
   наличие подтверждённой VK-связи его аккаунта.
2. «Привязать чат» выдаёт короткую одноразовую команду, например
   `/site_bind ABCDE-FGHJK`, сроком на 10 минут. Код привязан к автору,
   конкретному объекту и его текущей ревизии привязки. В БД сайта — хеш кода.
3. Автор отправляет команду в нужную беседу, где уже есть HereBot. Бот проверяет,
   что отправитель — администратор беседы, его VK совпадает с владельцем кода,
   а бот может читать состав и отправлять сообщения.
4. Сервисный запрос бота подтверждает код, `peer_id`, идентификатор сообщества,
   название и состояние проверки. Сайт заново проверяет актуальные права и
   ревизию; расходует код и сохраняет привязку в одной транзакции.
5. Настройки показывают «Подключено: P2B · команда». Код исчезает. Повтор того
   же подтверждения идемпотентен; другая беседа или другой VK его не используют.

Выдача и проверка кодов ограничены по аккаунту/VK и scope: например, не более
5 новых кодов за 10 минут и 5 ошибочных попыток подтверждения за 10 минут;
отказ не раскрывает, существует ли код. Ограничения долговечные/общие для
процессов, а не только счётчик одной вкладки. Конкретные числа — начальная
настройка проекта, которую нужно проверить на UX; срок 10 минут обязателен.

Этот шаг не раскрывает на сайте весь список бесед бота и не позволяет мастеру
выбрать чужую беседу по угаданному `peer_id`. Одного членства автора в беседе
недостаточно. Если мастер не администратор VK-чата, интерфейс объясняет, что
нужно временно/постоянно получить это право либо попросить ответственного с
обоими правами выполнить привязку. Сайт не выдаёт роль администратора VK.

Повторная привязка уже подтверждённого чата может показывать известное название,
но изменение назначения всё равно требует нового кода. Название не является
ключом, а приглашение `vk.me/join/...` не является доверенным идентификатором.

### Создание задачи

Рядом с основным действием формы располагается «Сделать рассылку». Кнопка
включает намерение отправки и раскрывает компактный предпросмотр. Она **не
отправляет сообщение до создания задачи**. Основная кнопка меняется с
«Создать задачу» на «Создать и отправить»; выключение возвращает обычное создание.

| Ситуация | Что показывает форма |
| --- | --- |
| Чат подключён, исполнители выбраны | «Уведомим: Анна, Илья · 2 человека» и предпросмотр точечных упоминаний |
| Чат подключён, исполнителей нет | «Уведомим всех участников чата»; заметная подпись перед подтверждением |
| У одного из выбранных исполнителей нет подтверждённого VK или его нет в чате | Явное объяснение, кто не может быть упомянут; отправка недоступна до исправления. Можно создать задачу без рассылки |
| Чат не подключён | Неактивная кнопка с постоянно видимой причиной «К этой команде ещё не привязан чат» и ссылкой «Настроить» при наличии прав |
| Закрытая очередь или задача с ограниченной аудиторией | «Для закрытых задач рассылка в общий чат недоступна»; обычные личные уведомления работают по своим правилам |
| Бот отключён, привязка недействительна или нет права отправки | Отдельная конкретная причина; форма задачи остаётся доступной |
| Бот временно офлайн, но привязка подтверждена | «Сообщение будет ждать подключения бота»; намерение допускается, при подтверждении создаётся очередь отправки |
| Нет свежего состава для предпросмотра | «Проверим получателей перед отправкой»; не показывать выдуманный точный счётчик |

Выбранные исполнители всегда означают только этих людей: отсутствие их VK не
переключает рассылку на всех. Сервисный аккаунт не становится получателем.
Подпись «Упомянем в общем чате» отличает этот способ от рассылки личных сообщений:
даже при одном адресном упоминании само сообщение видит вся беседа.
Если пользователь меняет очередь/команду, выбор рассылки сбрасывается и
перепроверяется назначение; черновик текста задачи не теряется.

После создания открывается задача, а рядом со статусом рассылки отображается:
«Ожидает отправки», «Отправлено», «Не удалось отправить» или
«Отправлено частично». Неудача VK не откатывает сохранённую задачу. Повторная
попытка продолжает то же задание, не создаёт вторую задачу или вторую рассылку.

### Сообщение в беседе

Для обычной задачи в открытой очереди команды: короткий заголовок, название
команды, срок при его наличии, ссылка «Открыть задачу» и упоминания. В первом
выпуске ссылка в тексте достаточна; inline-кнопка может дублировать её.
Отключить автоматическое создание предпросмотра ссылки (`dont_parse_links=1`).
Заголовок передаётся только в подтверждённый чат этой команды после явного
включения намерения автором. Пользовательские заголовки/названия не должны
превращаться в команды или дополнительные упоминания: нейтрализовать
`@all`, `@channel`, конструкции `[id...|...]` и аналогичную VK-разметку,
а разрешённые упоминания собирать отдельно из проверенных числовых VK ID.
Не отправлять сырое Markdown/HTML-описание в качестве шаблона.

Не включать ККР, оценки, комментарии, вложения, содержание описания, список
наблюдателей или другие частные сведения. В первом выпуске **рассылка из
закрытых очередей и задач с ограниченной аудиторией полностью недоступна**,
включая нейтральный текст со ссылкой и точечными упоминаниями. Сообщение
видит вся беседа, поэтому проверка доступа исполнителей не ограничивает
фактическую аудиторию. Для таких задач остаются существующие личные уведомления.

Сам факт существования задачи и упоминания людей также раскрывают информацию.
Сайт не контролирует приглашение новых людей в VK-чат, пересылку сообщения
или доступ с другого VK. Даже для обычной задачи публикация кратких сведений
идёт только по явному намерению автора в подтверждённый чат команды; нельзя
обещать совпадение всего состава VK-чата с читателями сайта. Ссылка сохраняет
обычную авторизацию и ACL. Возможность публиковать специально выбранные
сведения закрытой задачи — отдельное будущее решение владельца с отдельным
правом и явным согласием на аудиторию всего чата.

## 3. Права и выбор назначения

Добавить центральные действия `scope.chat.manage` и `task.chat_announce`, а
также capabilities `manage_chat` и `announce_task`. Не использовать глобальное
`broadcast.send`: оно предназначено для массовых личных сообщений и имеет
другую аудиторию и круг отправителей.

Предлагаемая матрица первого выпуска:

| Роль | Привязка своего блока/мероприятия | Рассылка задачи своего объекта |
| --- | --- | --- |
| Председатель, его заместители | Да | Да при доступе к задаче |
| Мастер блока и действующий заместитель мастера | Да, только своего блока | Да |
| Ответственный мероприятия и его действующий заместитель | Да, только своего мероприятия | Да |
| Ответственный подмероприятия и его заместитель | Собственного чата в первом выпуске нет | Да в подтверждённый чат родительского мероприятия, если разрешено для подмероприятий |
| Ответственный очереди без роли руководителя команды | Нет | Нет по умолчанию; отдельное делегирование можно согласовать позже |
| Участник команды / исполнитель | Нет | Нет; обычное создание задачи не даёт права тегнуть весь чат |
| HR-мастер / IT-мастер только по глобальной роли | Нет чужих привязок | Нет чужих рассылок без обычных scoped-прав |
| Сервисный аккаунт | Может отзывать связь и просматривать техническое состояние | Может создавать очередь, но не подменяет VK-человека для подтверждения новой привязки |

Это предложение для реализации, а не уже добавленная политика. В исходном
запросе явно названы мастер блока и ответственный мероприятия. Расширение на
их заместителей в таблице предложено по существующим `BLOCK_LEADS`/`EVENT_LEADS`,
но ещё не утверждено для этого нового действия; перед реализацией его нужно
согласовать либо ограничить первую версию явно названными ролями.

Назначение вычисляет сервер из настоящей очереди задачи. Для блока — его
привязка; для мероприятия — его привязка. Для подмероприятия — только явно
разрешённое наследование чата родительского мероприятия с подписью об этом.
Для персональной, председательской и служебной очереди автоматического
назначения нет. Клиент не передаёт произвольный чат вместо этого правила.

## 4. Где хранятся данные

**Бот, PostgreSQL.** `Chats` остаётся источником названий. Дополнительно нужны
состояние присутствия бота, последняя успешная проверка, revision и время
обновления названия. Событие переименования и периодическое ограниченное
обновление исправляют заголовок без перезапуска. Выход бота/потеря прав
делают запись недоступной, но не уничтожают её историю.

**Сайт, собственная БД.** Новая `scope_chat_bindings` содержит `binding_id`,
`scope_kind`, стабильный `scope_id`, `provider=vk`, `bot_identity` (сообщество),
`peer_id`, revision, состояние, автора и дату подтверждения. Уникальность —
одна текущая привязка на объект. Не связывать по имени блока или заголовку чата.
Одна беседа может обслуживать несколько объектов только через отдельное
явное подтверждение каждого; по умолчанию предупредить о повторном использовании.

Название и техническое состояние на сайте — ограниченная проекция bot → site
для уже привязанных бесед, с `observed_at`/revision. Источник истины остаётся
`Chats` бота. Сайт не запрашивает VK при открытии страницы и не читает напрямую
PostgreSQL бота. Состав всех чужих бесед не синхронизируется и не показывается.

**Задания.** `task_chat_announcements` на сайте: UUID задания, task_id,
binding_id + binding_revision, автор, режим `assignees|all`, snapshot выбранных
site/VK ID, версия шаблона, idempotency_key, состояние, attempts,
next_attempt_at, created/sent/updated_at, короткий код ошибки.
Уникальность на `(task_id, purpose=created)` исключает повтор начального анонса.
Режим и выбранные получатели фиксируются при создании задания. Повтор
перепроверяет доступ этих людей, но не выводит режим заново из изменившейся
задачи: удаление всех назначений после создания не превращает `assignees` в
`all`. Изменившаяся связь VK выбранного человека требует отмены/нового
подтверждения, а не тихой отправки другому VK.

На стороне бота отдельная долговечная таблица исполнения хранит job_id,
community/peer, согласованный payload hash, подготовленные части, постоянный
`random_id` каждой части, результат VK и незавершённое подтверждение. В ней
нет пользовательских токенов. Состав `all` фиксируется перед первой отправкой,
дедуплицируется, затем не пересобирается при повторе: иначе границы пачек
изменятся и один `random_id` будет относиться к разным сообщениям.
Уникальные ограничения `(job_id, part_number)` и
`(bot_identity, random_id)` фиксируют это в БД; не предполагаем изоляцию
дедупликации VK по беседам. Обнаруженную коллизию
ID разрешить до первой отправки, сохранив выбранное значение, а не менять
его при retry.

## 5. Контракт и последовательность выполнения

Имена новых маршрутов ниже — проект контракта, подлежащий совместному
добавлению в DTO и тесты сайта/бота.

1. `GET /scopes/{kind}/{id}/chat` — текущая разрешённая проекция и capabilities.
   `POST .../chat/link-code` — код с expected_revision; `DELETE .../chat` —
   отзыв с expected_revision. GET никогда не создаёт код и не чинит данные.
2. `POST /api/bot/v1/chats/confirm` — bot-token + код + проверенный VK автора +
   идентичность бота + peer + метаданные. Повтор одного подтверждения возвращает
   тот же результат. Между внешней проверкой бота и применением сайт заново
   проверяет пользователя, роль, объект, revision и срок кода.
3. Проекция состояния привязанных бесед поступает через отдельную ограниченную
   секцию `/report`; heartbeat сообщает поддержку `chat_announcements_v1`.
   Старый бот без возможности не получает новую работу.
4. `GET /tasks/create-context?...` либо небольшое расширение подробной проекции
   выбранной очереди возвращает назначение/доступность. Предпросмотр не тянет
   все контакты и не делает синхронный запрос к VK.
5. `POST /tasks` получает `chat_announcement: {enabled, binding_revision}`.
   Режим и получателей сервер выводит из валидированных исполнителей задачи,
   а не принимает произвольный список VK ID. Намерение входит в request hash.
   Сохранение задачи, roster и outbox выполняется в одной HTTP-транзакции.
6. `/work` возвращает отдельный `chat_announcements[]` только совместимому боту,
   после проверки текущего доступа автора/получателей, существования задачи,
   неотозванной привязки и её revision. Обычные `deliveries`/`broadcasts`
   остаются каналами ЛС с прежними ограничениями.
7. Бот проверяет доступ к чату, заново проверяет выбранных участников и
   подготавливает сохранённые части. Для `all` исключает отрицательные ID,
   деактивированные страницы и самого бота; инициатора можно не пинговать,
   как в текущем `@channel`. Это нужно явно отражать в подписи количества.
8. Бот отправляет части с постоянными `random_id`, отдельным бюджетом и таймаутом.
   Результат отправки сохраняется до HTTP-отчёта. Повтор `/work` или перезапуск
   бота приводит к продолжению/повтору отчёта, а не к созданию нового анонса.
9. `/report` принимает результаты по заданию и части; повтор идемпотентен.
   Переходы статуса аудируются; в интерфейсе видны время и автор отправки,
   ошибка без токенов и содержание только в пределах текущего доступа к задаче.

Уточнение гонок: отзыв привязки отменяет ещё не выданную и подготовленную, но
не отправленную работу. Для этапа перед первой отправкой нужен короткий
повторный серверный authorize/claim, реализованный как POST, а не запись в GET
`/work`: compare-and-swap состояния с короткой lease и fencing token,
исключающим двух текущих исполнителей задания. Перед каждой ещё не отправленной
частью бот подтверждает действующую lease/token; сервер проверяет роли,
privacy и ревизию привязки, а отчёт проверяет идентификатор части и fencing
token. Lease должна покрывать ограниченный сетевой таймаут и обновляться
до его истечения. Просроченный исполнитель не начинает новые части; новый
исполнитель продолжает с теми же сохранёнными random_id. После последней
проверки остаётся неизбежное окно сети до принятия
сообщения VK; уже принятое сообщение нельзя объявлять автоматически отозванным.
Если отвязка/смена ролей произошла после начала части, показать реальный итог.
Строгой атомарности между двумя БД и VK здесь нет.

## 6. Ошибки, повторы и ограничения

- Ошибку перед созданием (нет чата, неверная revision, нет права, несовместимый
  бот, неподтверждённый выбранный VK) показать у настройки. Пользователь
  может выключить рассылку и сохранить задачу. Не молча терять намерение.
- Отсутствие участника, обнаруженное ботом после создания, — понятная ошибка
  задания без отправки остальным до исправления; никогда не fallback на всех.
- Сеть, временная ошибка VK и rate limit — ограниченный backoff с jitter.
  Пример бюджета: 1, 5, 15, 60 минут, затем `failed`; TTL задания 24 часа.
  Отправка позднее TTL требует нового явного действия, не неожиданного пинга.
- Потеря доступа к беседе/удаление бота/неверный peer — постоянная ошибка до
  исправления привязки. Не повторять каждый poll и не зацикливать проверку состава.
- Таймаут после `messages.send` — неопределённый результат; повтор использует
  тот же сохранённый payload и random_id. Не обещать абсолютную exactly-once
  доставку без учёта документированного окна дедупликации VK.
- Частичная отправка — учитывать каждую часть. «Повторить» отправляет только
  неподтверждённые части с прежними ID. Изменившийся после подготовки текст
  требует отдельного нового анонса, который не входит в автоматический MVP.
- Задание не должно переживать удаление задачи или перенос в другую команду
  с автоматической отправкой в прежний чат: отменить и показать причину.
- На каждую беседу — последовательная очередь, ограничение частоты и объёма;
  между беседами — ограниченная параллельность. Пауза консоли распространяется
  и на этот канал. Обычные команды бота/ЛС не ждут длинного `@channel`.
  Перед claim/dispatch повторно проверяются текущие роли и привязка; pause
  удерживает ещё не отправленную работу, unlink отменяет её. При выключении
  feature-флага новые задания не выдаются и не принимаются.
- Длина учитывает упоминания и ссылку, не только body. Большой состав делится
  на части; в предпросмотре «понадобится несколько сообщений». Список новых
  участников после начала рассылки не добавляется в уже выполняемую работу.
- Все логи — job/часть/status/error class/latency; без текстов задач, кодов
  привязки, токенов и полной выгрузки участников. Аудит фиксирует субъекта,
  объект, старую/новую привязку и результат с обычными правами доступа.
- «Отправлено» означает, что VK принял сообщение, а не что каждый участник
  прочитал его или получил push на телефон. Настройки клиента/чата и
  особенности упоминаний проверяются отдельно на web и мобильном VK.

## 7. Быстродействие и UX при недоступном VK

Ниже **целевые критерии будущей реализации**, не результаты замеров.

| Проверка | Цель |
| --- | --- |
| Обычное создание без рассылки | Нет новых внешних запросов; не более одной дешёвой проверки выключенного флага |
| Создание с рассылкой | Только локальная валидация + INSERT outbox; p95 не хуже базового больше чем на 10% или 20 мс, берём больший допуск |
| Чтение задач без открытого статуса рассылки | Нет реестра чатов/составов в ответе; число SQL не растёт с количеством задач |
| Настройки одного объекта | Локальная bounded-проекция; p95 API до 200 мс на целевом сервере при обычной нагрузке |
| Обновление состояния | Poll только открытой и видимой панели: 3 с на привязке/ожидании, остановка после конечного статуса; фоновые вкладки не опрашивают |
| Исправный бот без очереди | Начало обработки обычно за один `/work` poll, цель до 5 с; это не SLA доставки VK |
| Недоступный VK, 100 одновременных созданий | Нет зависших API-ответов из-за VK; фиксируется рост outbox, действуют лимиты и backoff |
| Большой чат | Явная пагинация состава; ограничение общего бюджета чтения; нет неограниченного списка в HTTP-ответе сайта |

Нагрузочный эксперимент сравнивает одну и ту же синтетическую БД и сценарий
с выключенным/включённым намерением. Отдельно измерить API p50/p95, число SQL,
длину очереди, время ожидания, время VK и ошибки. Не смешивать задержку сайта
со временем доставки внешнего провайдера.

## 8. Реализация по этапам

1. Зафиксировать DTO, ACL, объём сообщения, правило подмероприятий и политику
   закрытых очередей. Добавить общий контракт `chat_announcements_v1`.
2. Бот: additive migration для метаданных чатов и долговечного исполнения;
   подтверждение кода, события состояния, выделенный sender и limiter.
3. Сайт: таблицы привязки/одноразовых кодов/outbox, индексы и ревизии; маршруты
   и service-contract, транзакционное намерение в создании задачи.
4. UI: настройки, защищённая привязка, кнопка намерения и предпросмотр,
   состояния отправки с доступным клавиатурным управлением и мобильной вёрсткой.
5. Полный синтетический end-to-end: API сайта + бот + fake VK; обычные ЛС,
   уведомления об одобрении регистрации и текущие рассылки не регрессируют.
6. Отдельно разрешённый пробный запуск в одной беседе; только после него
   включение для остальных объектов. Не привязывать старые чаты автоматически.

Флаг `TASK_CHAT_ANNOUNCEMENTS_ENABLED=false` по умолчанию; включение требует
совместимой версии бота. Миграции добавочные и идемпотентные; откат приложения
не удаляет таблицы. При выключении флага новые намерения не принимаются,
неотправленная работа ставится на паузу/отменяется по явной выбранной политике,
а история остаётся читаемой. Первый rollout не меняет существующие настройки
личных уведомлений и не делает их opt-in равным рассылке в общий чат.

## 9. Приёмочные проверки

- ACL-матрица: мастер своего/чужого блока, заместители, ответственные,
  участник, owner очереди, HR, root, архивный/заблокированный аккаунт;
  одинаковые решения capability и серверной команды.
- Привязка: верный код, истёкший/повторный/чужой код, другая беседа,
  неадминистратор VK, смена роли между выдачей и подтверждением, две
  одновременные привязки, повторная доставка отчёта, смена сообщества бота.
- Названия: rename беседы/блока не меняет стабильную связь; сайт не выдаёт
  каталог чужих чатов; отсутствие свежих данных отображается честно.
- Создание: без intent нет отправки; с intent ровно одна задача и один outbox
  при потерянном ответе/двойном клике; ошибка транзакции не оставляет outbox.
- Исполнители: один, несколько, дубликаты, нет выбранных, нет VK,
  VK вне беседы, удалённая страница, смена ссылки аккаунта, сервисный аккаунт.
- Приватность: закрытая очередь/задача полностью отвергает намерение рассылки
  в чат, в том числе нейтральный текст и точечное упоминание; если она стала
  закрытой после создания, неотправленная работа отменяется. Обычная задача
  не раскрывает body/файлы/оценки; несанкционированный reader не видит delivery details.
- Гонки: отозвана привязка, удалена/перенесена задача, сняты права автора,
  исполнители изменены до claim, бот вышел из беседы, название изменилось
  во время retry, участники меняются между страницами и между частями.
- Доставка: 6/9/14/29 VK, 917/927, сеть, timeout после принятия, потерянный
  report, restart после каждой части, просроченная работа, частичный успех;
  подтверждённые части не отправляются повторно новым random_id.
- Длина: Unicode, спецсимволы упоминаний, длинный заголовок/URL, 0/1/200+
  участников, постраничный состав, ограничение общего времени и сообщений.
  Проверить mention injection в названии задачи/блока и подписи; только
  подтверждённый список получателей создаёт упоминания. Проверить, что
  удаление назначений после сохранения не переключает режим на всех.
- Совместимость: старый бот не получает работу нового типа; каналы ЛС
  по-прежнему отвергают `peer_id` бесед; пауза работает; migrations дважды
  сохраняют существующие строки и индексы.
- UI: desktop/mobile, клавиатура, сообщения причины у disabled-кнопки,
  смена очереди, уход с dirty-формы, retry без дублирования, offline/empty/error,
  отмена polling при закрытии и без случайной отправки из предпросмотра.
- Нагрузка: бюджет из раздела 7, ограниченная память, число SQL без N+1,
  backpressure бота и независимость обычных страниц от VK/S3.
- Отдельный разрешённый живой gate: принятие VK, рендер сообщения/ссылки и
  точечного/массового упоминания в web и приложении VK, в том числе с
  отключёнными уведомлениями. Не требовать push вопреки настройкам клиента.

## 10. Что не входит в первый выпуск

Автоматический VK-опрос, назначение из голосования, ответы в чате с записью
результата в задачу, Telegram, публикация в канале сообщества, изменение
сообщения при каждом редактировании задачи, массовые повторные напоминания и
произвольный выбор чата при создании задачи. Для опроса отдельно нужно решить
источник истины назначения и зависимость от пользовательского VK-токена;
кнопка открытия задачи уже позволяет взять задачу в существующем трекере.

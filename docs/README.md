## Приоритет документов

1. Прямые действующие решения владельца и [AGENTS.md](../AGENTS.md).
2. Текущий код и адресные тесты: при расхождении обнаруженную ошибку документации
   исправляют, а изменение продуктового контракта согласовывают.
3. Этот обзор, архитектура и тематические контракты backend/frontend.
4. Датированные решения — основание правил, но не инструкция к новой выкладке.
5. Архив — состояние на конкретную дату, включая старые ошибки и ограничения.

Исходные `CODEX_FRONTEND.md` и `CODEX_BACKEND.md` удалены по решению владельца
как устаревшие задания. Действующие требования находятся в архитектуре и
тематических контрактах. Исторические счётчики тестов, порты и номера веток
не описывают работающий стенд сегодня.

## Как поддерживать порядок

- Постоянные правила обновлять в тематическом документе, не заводить очередной
  файл `*_FINAL_v2.md`. Архитектура хранит обзор, контракт — детали, тесты — проверку.
- Решение с датой помещать в `docs/decisions/`; явно указывать, что оно заменяет.
- Завершённый отчёт включать в архив соответствующего этапа; актуальный план не
  должен смешиваться с журналом выполнения. Новый roadmap появляется после согласования.
- Тяжёлые журналы, снимки, измерения и приватные рабочие артефакты оставлять
  в `.local/`, со ссылкой из указателя. Не копировать в Git базы, пароли и диагностику.
- При перемещении документа обновлять ссылки. Markdown-тексты, загружаемые сайтом,
  считать данными приложения, а не рабочими записками.

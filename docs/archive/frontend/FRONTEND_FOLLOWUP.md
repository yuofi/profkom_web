## Процесс

Связанные пункты группируются в ветки от актуальной локальной `dev`: `feature/frontend-workflow-fixes` (F01–F03 и F07), `feature/frontend-summary-forms` (F04–F06), `feature/frontend-compatibility-acceptance` (F08–F09). Внутри группы — проверяемые коммиты и краткий отчёт после каждого пункта. После проверки группы — интеграция в локальную `dev`; следующая ветка создаётся от неё. Публикация веток и деплой в этот план не входят.

Область изменений — frontend и его документация. Права и рассчитанные значения приходят с сервера; таймеры и фильтры не создают полномочия. Тестовый transport остаётся только в DEV/test. Неизвестные API и связи ID фиксируются как вопросы контракта, а не выдумываются в клиенте.

## F01. Сверка требований и проверок

Ветка: `feature/frontend-workflow-fixes`.

- Составить таблицу: требование из `CODEX_FRONTEND.md` → экран/действие → API → проверка → пробел → критерий закрытия.
- Включить пять подтверждённых недоделок F02–F06, фильтры справочника/рабочего экрана, старые входы в редактор гайдов и связанные сценарии нескольких ролей.
- Разделить дефект frontend, неподтверждённый сценарий и конкретный пробел API. Дополнительные исправления оформить задачами в соответствующей группе до их реализации.
- Пересмотреть галочки, если проверен только вызов API-клиента или ручная смена фикстуры, а не действие пользователя.

Готовность: у каждого незакрытого требования есть задача с наблюдаемым результатом либо назван отсутствующий элемент контракта. Нет статуса «готово» без подходящего подтверждения.

## F02. Обновление заявок у границы 72 часов

Ветка: `feature/frontend-workflow-fixes`.

Проблема: открытая очередь сама не перечитывает capabilities при наступлении `substitute_available_at`.

- Запланировать повторный GET по серверному сроку текущего этапа; после перехода HR → мастер использовать новый срок.
- Обновлять данные после возвращения во вкладку; сохранить ручное обновление и понятную ошибку сети.
- Убирать таймеры при уходе, ограничить повторные запросы. Уже прошедший срок не должен создавать бесконечный цикл.
- Разрешать подмену только после ответа с нужным capability.

Проверка: экран открыт до границы; время проходит без перезагрузки. Проверить запрос на границе, новый этап, одноэтапный HR, отказ сервера, возвращение во вкладку и ошибку сети.

Готовность: подмена становится доступна после подтверждения сервером без перезагрузки страницы; часы браузера сами не открывают действие.

## F03. Переход от препятствия закрытию к назначению

Ветка: `feature/frontend-workflow-fixes`.

Проблема: препятствие с `assignment_id` ведёт в общую очередь, где может не быть уже принятого назначения без оценки.

- Разрешить связь назначения с задачей через доступные данные существующего контракта.
- Открывать конкретную задачу и нужное назначение/форму оценивания, с выделением и правильным фокусом.
- Обработать недоступный объект и изменение прав без перехода в посторонний пустой список.
- Проверить остальные типы препятствий: предыдущий сезон, задача, final главного мероприятия и подмероприятия.

Готовность: незавершённое и принятое без оценки назначения приводят к своим действиям; недоступное даёт понятное сообщение. Прямой переход и возврат к закрытию сохраняют контекст. Если API не позволяет разрешить связь, указан точный недостающий идентификатор/метод; фиктивной ссылки нет.

## F04. Полные формы исправления закрытых итогов

Ветка: `feature/frontend-summary-forms`.

Проблема: команда поддерживает `task_inputs`, `assessment_inputs` и `merit`, но форма отправляет только `assessment_inputs`.

- Добавить выбор типа и объекта: даты/критерии задачи, оценивание назначения, исходные данные особой заслуги/волонтёрства в пределах согласованного DTO.
- Загружать исходные значения, revision объекта и версию закрытой сводной; показывать, что меняется.
- Требовать причину и серверное право председателя. Не добавлять ввод рассчитанного ККР.
- При 409/422 сохранять ввод, объяснять конфликт/ошибки полей, не показывать частичный успех. После успеха перечитывать сводную, источники и затронутые бонусы.

Готовность: все три типа изменений проходят через формы с правильными payload, причиной и версиями, подтверждаются повторным чтением транспорта. Проверены запрет другой роли, конкурентное изменение и повторная отправка. Просмотр старых версий/аудита остаётся отдельной зависимостью API.

## F05. Выбор получателей заслуги

Ветка: `feature/frontend-summary-forms`.

Проблема: индивидуальные поля создаются для всего справочника, а не выбранных людей; прежний получатель может исчезнуть из вариантов после архивирования.

- Добавить поиск и выбор получателей, поля часов/оценки/даты показывать только выбранным.
- Сохранять ввод при временном снятии/возврате выбора; отправлять только выбранных получателей.
- При редактировании сохранять исторических получателей и значения, даже если их нет в текущем справочнике.
- Историческую допустимость участия определять ответом сервера, а не текущим `in_profcom`.

Готовность: из 100 контактов выбраны двое — видны только их шесть индивидуальных полей. Разные значения сохраняются; снятие/возврат выбора не теряет ввод; редактируется запись с архивированным получателем; состав payload точный. На телефоне форма доступна без горизонтального прокручивания всей страницы.

## F06. Цветные отметки решений

Ветка: `feature/frontend-summary-forms`.

Проблема: несколько решений показаны общей текстовой строкой без требуемого цветового выделения.

- Добавить единые метки «Золотой Red Bull», «Предупреждение о кике», «Кик», «Найс» с читаемыми цветами и контрастом.
- Показывать все выбранные решения; прошлые оставлять в отдельной исторической колонке.
- Сохранить явные подписи и пустое состояние, чтобы значение читалось без определения цвета.

Готовность: несколько текущих/прошлых меток, отсутствие меток и длинные подписи проверены на телефоне и компьютере. Ничего не скрыто; прошлое решение не присваивается текущему сезону. Изменение вызывает только команду решений, без архивирования аккаунта и рассылок.

## F07. Фильтры и пустые состояния

Ветка: `feature/frontend-workflow-fixes`.

- В справочнике добавить «Все / Джуниоры / Активисты» вместе с поиском и блоком; бывших оставить отдельно. Не угадывать категорию при загрузке или ошибке.
- Проверить область действия фильтра сезона на рабочем экране: задачи, мероприятия, созвоны, очередь назначений. Глобальные блоки/заявки отличать от сезонной работы.
- Использовать доступные связи контракта. При отсутствии связи явно указать ограничение и нужное поле; не создавать неверный фильтр.
- Добавить метки сезона и корректные сообщения при пустом результате фильтра.

Готовность: проверены два незакрытых сезона, глобальные сущности, совмещение фильтров, пустой поиск и ошибка категории. Результат и пустое состояние соответствуют выбранным условиям; смена текущего сезона не скрывает прежнюю работу.

## F08. Совместимость старых гайдов с материалами

Ветка: `feature/frontend-compatibility-acceptance`.

Проблема: новый редактор имеет черновик/публикацию, а доступный старый редактор гайдов сохраняет текст напрямую.

- Проверить `/guides`, `/docs/:id`, старые административные действия и ссылки из материалов/блоков. Сопоставить чтение, создание, правку и удаление с требованием сохранения функций.
- Установить, определена ли связь guide ID с material ID. При подтверждённой связи направить редактирование в единый сценарий черновика и явной публикации, сохранив ссылки/содержимое.
- Если связи нет, выполнить независимую работу с интерфейсом/маршрутами и записать точное требование к mapping. Не сопоставлять документы по заголовку или случайному равенству ID.
- Проверить Markdown, галереи, контактные вставки и отдельные права ПГАС.

Готовность: каждый старый путь имеет проверенное поведение. Читатель видит прежнюю публикацию при правке, редактор — черновик, публикация явная; старый URL открывает правильный документ. Если это требует миграции API/данных, соответствующий подпункт остаётся открытым с конкретным условием снятия блокера.

## Отдельные зависимости backend

- Read API старых версий закрытой сводной/аудита коррекций. Условие снятия: версии и изменения получаются по ID, с автором/временем/причиной и проверкой прав.
- Реальные сессия, capabilities, revisions, сохранение. Условие снятия: реальные ролевые сценарии, повторный GET, запрет доступа и конкурентный 409.
- Настоящие upload/complete/download, аватары и VK. Условие снятия: успешный поток, повторное чтение и отрицательная проверка доступа.
- Настоящая XLSX-выгрузка. Условие снятия: открывается файл с двумя согласованными листами и значениями серверного расчёта.
- Связь старых гайдов с материалами — потенциальная зависимость F08; подтвердить в аудите, а не заранее считать решённой или непреодолимой.

## A02 · P2 · Старые формы неправильно разбирают структурированные ошибки API

Уверенность: высокая. Требования: FE-01 (понятные отказы/конфликты), общий формат ошибок.

[Form.tsx](../../../frontend/src/components/Form/Form.tsx):53–62 присваивает `data.detail` в текст ошибки. При `detail: {code, message, fields}` настоящий `AxiosError` приводит к передаче объекта в React и падению формы. Если ошибка адаптера не проходит `instanceof AxiosError`, теряется серверное сообщение и показывается общий `Request failed with status code 422`. Это касается сохранённых форм `useForm`, включая вход и ПГАС; новый `ActionForm` уже использует нормализацию.

Подтверждение: A02a — потеря сообщения на ошибке адаптера; A02b — падение на настоящем `AxiosError` со структурированным `detail`.

Исправление: применить общий `normalizeApiError` и обработку ошибок полей в старом `useForm`; не использовать объект как текст и не полагаться только на идентичность конструктора ошибки.

Критерий закрытия: достижимые старые формы при 403/409/422 показывают строковое сообщение и ошибки полей, сохраняют ввод и не падают.

## A03 · P2 · Вход обходит проверку состояния сессии, возврат ко входу не завершает сессию

Уверенность: высокая для порядка запросов и очистки; сбой входа воспроизведён при 403 профиля. Требования: FE-01, AUTH-01; сохранение login/refresh/logout/VK, до одобрения только состояние регистрации.

[Greeting.tsx](../../../frontend/src/pages/Greeting/Greeting.tsx):81–87 после получения токена сначала обязательно читает `/profile/me`, затем обновляет `/session` и переходит дальше. Аналогичный порядок у VK (107–115). При 403 собственного профиля pending-аккаунта успешная аутентификация заканчивается ошибкой формы: чтение состояния регистрации не начинается. Ошибки VK остаются только в console.

В [SessionPages.tsx](../../../frontend/src/pages/Workspace/SessionPages.tsx):62–67 действие «Ко входу» удаляет лишь access-cookie; не вызывает существующий logout и не очищает частный кеш. Серверная refresh-сессия этим не завершается.

Подтверждение: A03a фиксирует отсутствие `/session` после отказа профиля; A03b — отсутствие logout и сохранение кеша после клика.

Исправление: общий переход после обычного входа/регистрации/VK с очисткой частного кеша и чтением `/session` первым; профиль читать только для активного аккаунта. Для pending/rejected использовать общий полноценный выход, выводить пользователю ошибки VK.

Критерий закрытия: pending/rejected после входа попадает на состояние регистрации без запросов рабочих данных; активный — на рабочий экран. Возврат ко входу завершает серверную сессию и очищает кеш; refresh не возвращает прежний аккаунт.

## A04 · P2 · У руководителей нет обычного входа в формы заслуг; неверная проверка доступа

Уверенность: высокая. Требования: FE-02 (строки 94–96), формы особых заслуг главорга и волонтёрства мастера/ответственного, объектные capabilities без доступа к расчёту.

[WorkspaceLayout.tsx](../../../frontend/src/components/Workspace/WorkspaceLayout.tsx):46–48 показывает сезоны только при `view_summary`. Вход в неё есть со страницы сезона, до которой мастер без доступа к сводной не доходит из обычной навигации.

В [MeritPages.tsx](../../../frontend/src/pages/Workspace/MeritPages.tsx):389–399 чтение и сама страница требуют глобальный `create_volunteer_merit` либо `view_summary`; форма создания (425–428) — только глобальный volunteer-флаг. Объектный `create_head_merit` мероприятия сам по себе не открывает форму.

Подтверждение: A04a проверяет отсутствие перехода из блока и основной навигации для уполномоченного руководителя без сводной; A04b — отказ страницы при `create_head_merit` события без постороннего volunteer-флага.

Исправление: добавить входы из соответствующих областей с выбором допустимого сезона; допускать фактически разрешённый тип заслуги и контекст по capabilities. Не выдавать ради формы чтение рассчитанного ККР.

Критерий закрытия: мастер без `view_summary` находит и отправляет волонтёрскую запись своего блока; главорг с `create_head_merit` — свою форму без volunteer-флага. Читателю/редактору без права создание не показывается; сезон и источник верны.

## A05 · P2 · Обновление конфликтующей версии всё ещё стирает ввод в части форм

Уверенность: высокая для воспроизведения мероприятия; остальные перечисленные места требуют отдельных регрессионных сценариев. Требования: FE-01 и общий контракт revisions/409; сохранность ввода при конфликте.

В [EventPages.tsx](../../../frontend/src/pages/Workspace/EventPages.tsx):311–326 форма описания имеет `key={event.revision}`. После правки пользователем, конкурентного изменения, ответа 409 и нажатия «Обновить данные» форма пересоздаётся и заменяет введённый текст серверным значением. Предыдущее исправление ключей охватило задачу/отчёт/материал, но не все формы.

Сходные ключи по версии остаются в формах назначения/подмероприятия EventPages, блока MembershipPages, RegistrationForm, созвона ReportPages и управления сезоном SeasonPages, а также LeadershipPage. У части форм нет действия обновления после конфликта — его тоже надо проверить.

Подтверждение: A05 воспроизводит потерю описания мероприятия через отправку формы, 409 и явное обновление данных.

Исправление: хранить черновик независимо от revision и применять новую серверную версию явно, с возможностью сравнить/повторить отправку. Проверить все формы с таким же ключом и отсутствие действий восстановления.

Критерий закрытия: для мероприятия, блока, регистрации, созвона и сезонных форм сценарий «ввод → 409 → обновление» сохраняет введённые значения; новый expected_revision используется после явного обновления. Смена самого объекта корректно меняет форму.

## A06 · P2 · Обновление справочника скрывает поля выбранного получателя новой заслуги

Уверенность: высокая. Требования: FE-02, F05; сохранность ввода и исторических получателей.

[MeritPages.tsx](../../../frontend/src/pages/Workspace/MeritPages.tsx):75–88 дополняет варианты отсутствующими получателями только из уже сохранённой записи (`existing`). Для новой несохранённой заслуги выбранный человек, исчезнувший из свежего справочника, пропадает из списка полей: счётчик выбранных остаётся 1, но его часы/оценка/дата не видны. Значения внутри формы не доказаны потерянными; дефект — скрытый и недоступный для правки выбранный получатель.

Подтверждение: A06 выбирает человека, меняет справочник в QueryClient и фиксирует исчезновение индивидуальных полей при сохранённом выборе.

Исправление: удерживать снимки выбранных получателей и их черновые значения независимо от текущего справочника, помечать недоступного/архивного, удалять только по явному снятию выбора. Допустимость сохранения решает сервер.

Критерий закрытия: после выбора и ввода обновление контактов не скрывает человека и его значения; показана причина недоступности. Payload содержит ровно явно выбранные ID.

## A07 · P2 · Фото ограничено 5 MiB вместо согласованных 10 MiB

Уверенность: высокая. Требование: общий контракт файлов `CODEX_FRONTEND.md`:2306.

Подтверждение: A07 фиксирует локальную ошибку и отсутствие вызова `filesApi.upload`.

Исправление: согласовать локальную границу и подсказку с 10 MiB, сохранив ограничения MIME.

Критерий закрытия: разрешённый тип чуть меньше и ровно 10 MiB проходит к upload intent; больше 10 MiB отклоняется локально. Реальная загрузка/декодирование проверяется отдельно с API.

## A08 · P3 · Селекторы руководства не исключают неодобренного кандидата

Уверенность: высокая для обработки указанного ответа; требование одинаковой фильтрации руководства — вывод из модели действующих участников, ROLE-06 прямо проверяет pending для мастера/зама. Само назначение на сервере не проверялось.

[SessionPages.tsx](../../../frontend/src/pages/Workspace/SessionPages.tsx):122–128 исключает из кандидатов только действующего председателя. Контакт с `in_profcom: false`, если он присутствует в ответе/кеше, предлагается в передаче поста и назначении замов. Другие новые селекторы уже используют отбор действующих участников.

Подтверждение: A08 подаёт такой контакт в кеш и фиксирует его option в форме. Это не утверждение, что согласованный live API обязательно вернёт pending или разрешит назначение.

Исправление: применять отбор одобренных действующих участников и обрабатывать устаревший выбор. Сохранить возможность назначения действующего участника вне текущего состава области; окончательный запрет — на сервере.

Критерий закрытия: pending не предлагается при таком ответе, действующий участник вне области доступен, серверный 422 отображается без потери ввода.

## A09 · P3 · Пустой результат поиска материалов оставляет пустую область

Уверенность: высокая. Требования: понятные состояния списков, приёмка фильтров и пустых состояний.

[MaterialPages.tsx](../../../frontend/src/pages/Workspace/MaterialPages.tsx):72–103 фильтрует карточки, но проверяет пустоту по исходному `items.length`. При существующих материалах и несовпадающем поиске нет ни карточек, ни сообщения, ни действия сброса.

Подтверждение: A09 вводит несовпадающий запрос при непустом исходном списке и фиксирует пустую выдачу без объяснения.

Исправление: вычислять отфильтрованный список отдельно, показывать «Ничего не найдено» и сброс условий; отличать это от глобального отсутствия материалов и ошибки загрузки.

Критерий закрытия: отдельно проверены пустой исходный список, пустая фильтрованная выдача, совпадения, загрузка и ошибка; сброс возвращает доступные карточки.

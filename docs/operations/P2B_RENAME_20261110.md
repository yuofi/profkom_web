# Переименование блока «Спонсоры» в P2B

Статус: **выполнено на новом production 10 ноября 2026, 20:59 МСК** после
явного разрешения владельца. Один штатный PATCH, revision1→2; UUID, гайд,
связи и13 защищённых таблиц проверены. Логотип и алиасы опубликованы вместе
с переездом. Backup API до/после: `/opt/profkom/backups/p2b-20261110/` на новом
сервере. Подробный факт поставки — [MIGRATION_20261110.md](MIGRATION_20261110.md).
Ниже сохранена процедура для воспроизводимости; примеры revision не являются
указанием повторять выполненную запись.

Итоговое название: **P2B (Profkom to Business)**. Переименовывается существующий
блок, новый блок не создаётся. Его UUID, участники, руководство, гайд и очереди
должны сохраниться. Прежний логотип остаётся через явные алиасы в
`frontend/src/utils/teamLogos.ts`.

## Штатный API

Операцию выполняет авторизованный председатель, заместитель председателя либо
сервисный аккаунт. Право `edit_block` само по себе недостаточно: сервер отдельно
проверяет `block.rename`.

1. `GET /api/blocks` — найти ровно один блок с точным именем `Спонсоры`.
   Убедиться, что отдельного блока с именем `P2B (Profkom to Business)` нет.
   Если старого имени нет, а новое найдено, проверить ожидаемый UUID и закончить
   без повторной записи; неоднозначность — повод остановить операцию.
2. `GET /api/blocks/{block_id}` — перечитать карточку непосредственно перед
   изменением. Зафиксировать UUID, прежнее имя и `revision`; приватно сохранить
   карточку для сравнения. Сравнивать руководство и участников по ID, без вывода
   имён, профилей и других персональных данных в отчёт.
3. Отправить **один** запрос:

   ```http
   PATCH /api/blocks/{block_id}
   Content-Type: application/json

   {
     "expected_revision": 17,
     "name": "P2B (Profkom to Business)"
   }
   ```

   `17` — только пример. Подставляется точная версия из шага 2. Другие поля,
   в частности аватар, описание, состав и руководство, в PATCH не передаются.
4. `GET /api/blocks/{block_id}` и `GET /api/blocks` — проверить результат и
   отсутствие второго блока. При сетевом таймауте сначала выполнить эти GET,
   не повторять запись автоматически.

Реализация: `backend/membership.py::patch_block`, маршрут в `backend/main.py`.
Она сохраняет стабильный UUID и обновляет связанные legacy-имена в ролях,
задачах, очередях, вкладах, бонусах мастера, старых гайдах и контактах внутри
одной транзакции; учитывает архивные назначения. История переименования
сохраняется штатным механизмом аудита. Исторические тексты КМБ этой операцией
не переписываются.

## Безопасный шаблон локальной репетиции

Использовать только одноразовый localhost-стенд с синтетическими данными.
Ниже приведён шаблон запросов, а не команда подключения к production.
`AUTH_CONFIG` — уже подготовленный локальный curl config с авторизацией
синтетического пользователя, права файла `600`. Не выводить его содержимое,
не передавать секреты в аргументах shell и не включать `set -x`, `curl -v` или
`--trace`. Ответы могут содержать персональные данные на реальном окружении,
поэтому также сохраняются только в приватный каталог и не печатаются в чат.

```sh
umask 077
API_BASE='http://127.0.0.1:<порт одноразового стенда>'
AUTH_CONFIG='/абсолютный/локальный/путь/auth.curl'
EVIDENCE_DIR='/абсолютный/локальный/путь/p2b-rename'
mkdir -p "$EVIDENCE_DIR"
chmod 700 "$EVIDENCE_DIR"

curl --silent --show-error --fail --connect-timeout 5 --max-time 15 \
  --config "$AUTH_CONFIG" \
  --output "$EVIDENCE_DIR/blocks-before.json" "$API_BASE/api/blocks"

# После проверки уникальности старого/нового имени берём UUID из ответа.
BLOCK_ID='<проверенный UUID существующего блока>'
curl --silent --show-error --fail --connect-timeout 5 --max-time 15 \
  --config "$AUTH_CONFIG" \
  --output "$EVIDENCE_DIR/block-before.json" "$API_BASE/api/blocks/$BLOCK_ID"

# rename.json содержит только name и expected_revision из block-before.json.
curl --silent --show-error --fail --connect-timeout 5 --max-time 15 \
  --config "$AUTH_CONFIG" --request PATCH \
  --header 'Content-Type: application/json' \
  --data-binary "@$EVIDENCE_DIR/rename.json" \
  --output "$EVIDENCE_DIR/patch-result.json" "$API_BASE/api/blocks/$BLOCK_ID"

curl --silent --show-error --fail --connect-timeout 5 --max-time 15 \
  --config "$AUTH_CONFIG" \
  --output "$EVIDENCE_DIR/block-after.json" "$API_BASE/api/blocks/$BLOCK_ID"
```

Не ставить `--retry` на PATCH. Ответ `409` требует перечитать карточку и оценить
чужое изменение; не подменять версию без этой проверки. `401`/`403` не обходить
изменением БД или ролей. Если отсутствует прежний блок либо имя занято,
остановиться без записи. Этот шаблон не получает и не создаёт учётные данные.

## Критерии успешности

- Имя стало `P2B (Profkom to Business)`, UUID и `guide_material_id` прежние;
  версия выросла на один, если между проверками не было других команд.
- Состав, ID мастера/заместителей/HR, `is_hr`, описание, ссылка сообщества и
  аватар не изменились; логотип отображается и для нового имени.
- Прежние ссылки на блок, гайд и ранее выбранную контрольную задачу открываются
  с теми же правами. ID очереди, ключ и номер контрольной задачи прежние.
- В каталоге и контактах отображается новое имя; старого действующего блока нет.
  Исторические названия в аудите могут и должны остаться.
- Ошибок API нет. В отчёте только результат проверок, без карточек, секретов
  и персональных данных.

## Откат

Перечитать `GET /api/blocks/{block_id}`. Проверить, что это тот же UUID с новым
именем, а `Спонсоры` не занято другим блоком. Отправить тот же штатный PATCH:

```json
{
  "expected_revision": 18,
  "name": "Спонсоры"
}
```

`18` также пример: использовать актуальную прочитанную версию. После отката
повторить критерии сохранности, ожидая старое имя. История обеих операций
сохраняется. Не восстанавливать всю БД ради обратимого переименования: это
затёрло бы чужие изменения. Если сохранность не подтверждается, прекратить
дальнейшие записи и отдельно согласовать восстановление.

## Локальные регрессии

Используются существующие TestClient-тесты на синтетической SQLite с подменами
VK/S3; реальные окружения и существующие локальные стенды не затрагиваются:

```text
tests/test_blocks.py::test_block_rename_preserves_id_material_and_member_history
tests/test_tracker_queues.py::test_block_rename_keeps_private_queue_identity_and_access
tests/test_local_scope_access.py::test_block_rename_keeps_members_access_revision
```

Они проверяют сохранение UUID/гайда, очереди/ключа/нумерации задачи, прав
участника и ревизии доступа мастера/участника. Это проверка общего механизма
переименования; она не заменяет перечисленные выше проверки конкретной записи
после разрешённой операции на целевом окружении.
